## The question every product team asks

"We changed the signup button. Signups went from 10.0% to 10.9%. Ship it?" Everything in this course meets here: chance (chapter 1), distributions (chapters 4–6), sampling error (chapter 7), confidence intervals and tests (chapters 8–9), Bayes (chapter 11) and simulation. The hard part of A/B testing isn't the formula. It's not fooling yourself. Start with the most common way people do.

```viz
name: ps-abtest
title: The peeking problem
goal: In the **A/A** test, run at least **200** experiments and see peeking declare at least twice as many winners as one planned look.
height: 450
Bars are the z-score at each look as visitors arrive; the red glass is ±1.96 (p < 0.05). The towers count how often each policy called a winner.
```

```quiz
In the A/A test the two pages are identical, yet peeking after every 100 visitors declared a winner about a quarter of the time. Why?
- The random number generator is biased
* The z-score wobbles as data arrives; each look is another chance for it to wander past 1.96 by luck, and stopping at the first crossing keeps that lucky moment
- 5% is only an approximation
- Identical pages can't be tested
> "p < 0.05" promises a 5% false-alarm rate for **one** look decided in advance. Twenty looks with "stop when it's significant" gives about 25%. Fix the sample size before you start, or use a method designed for repeated looks.
```

## Two proportions, one z

Page A: c_A conversions out of n_A visitors. Page B: c_B out of n_B. If the pages were really the same, both rates would estimate one shared rate p̂ = (c_A + c_B) / (n_A + n_B), and the gap between them would have standard error

    SE = √( p̂(1 − p̂)(1/n_A + 1/n_B) )

so z = (rate_B − rate_A) / SE. The two-sided p-value is `math.erfc(abs(z) / math.sqrt(2))`, the chance of a gap at least this big in either direction if nothing is going on.

```predict
cA, nA, cB, nB = 100, 1000, 120, 1000
p = (cA + cB) / (nA + nB)
se = math.sqrt(p * (1 - p) * (1 / nA + 1 / nB))
z = (cB / nB - cA / nA) / se
print(round(z, 3), round(math.erfc(abs(z) / math.sqrt(2)), 4))
```

A two-point lift on a thousand visitors each isn't significant. That surprises people every time.

```exercise
title: two_prop_test
kind: write
---prompt
Write `two_prop_test(cA, nA, cB, nB)` returning `(z, p_value)` using the pooled standard error above and `math.erfc` for the two-sided p-value.
---starter
def two_prop_test(cA, nA, cB, nB):
    return 0.0, 1.0
---solution
def two_prop_test(cA, nA, cB, nB):
    p = (cA + cB) / (nA + nB)
    se = math.sqrt(p * (1 - p) * (1 / nA + 1 / nB))
    z = (cB / nB - cA / nA) / se
    return z, math.erfc(abs(z) / math.sqrt(2))
---tests
z, p = two_prop_test(100, 1000, 120, 1000)
assert abs(z - 1.4293) < 1e-3 and abs(p - 0.1529) < 1e-3, f"z about 1.44, p about 0.15; got {z:.4f}, {p:.4f}"
z, p = two_prop_test(1000, 10000, 1200, 10000)
assert z > 4 and p < 1e-4, "the same lift with ten times the data is decisive"
z2, _ = two_prop_test(120, 1000, 100, 1000)
assert abs(z2 + 1.4293) < 1e-3, "swapping A and B flips the sign of z, not the p-value"
---hint
Pool the rate, compute the SE from it, divide the difference in rates by the SE. `math.erfc(abs(z) / math.sqrt(2))` is the two-sided p-value.
```

## Decide the size before you start

How many visitors do you need? It depends on the smallest lift you care about and how sure you want to be of catching it. The standard planning formula per page, for a 5% false-alarm rate and 80% **power** (the chance of detecting a real lift of that size):

    n = (1.96 + 0.84)² × (p₁(1 − p₁) + p₂(1 − p₂)) / (p₁ − p₂)²

```exercise
title: sample_size
kind: write
---prompt
Write `sample_size(p1, p2, z_alpha=1.96, z_power=0.84)` returning the visitors needed **per page**, rounded **up** to a whole number (`math.ceil`).
---starter
def sample_size(p1, p2, z_alpha=1.96, z_power=0.84):
    return 0
---solution
def sample_size(p1, p2, z_alpha=1.96, z_power=0.84):
    var = p1 * (1 - p1) + p2 * (1 - p2)
    return math.ceil((z_alpha + z_power) ** 2 * var / (p1 - p2) ** 2)
---tests
assert sample_size(0.10, 0.12) == 3834, f"10% vs 12% needs 3834 per page; got {sample_size(0.10, 0.12)}"
assert sample_size(0.10, 0.11) > 3.5 * sample_size(0.10, 0.12), "halving the lift needs about four times the visitors"
assert sample_size(0.10, 0.12) == sample_size(0.12, 0.10), "order doesn't matter"
---hint
Add the two variances `p(1 - p)`, multiply by `(z_alpha + z_power) ** 2`, divide by the squared gap, then `math.ceil`.
```

Don't trust a formula you haven't checked. Simulate many experiments of that size and count how often the test finds the lift.

```exercise
title: simulate_power
kind: write
---prompt
Write `simulate_power(pA, pB, n, trials=4000, seed=0)` that runs `trials` experiments with `n` visitors per page (draw conversions with `rng.binomial(n, pA, trials)` and likewise for B), computes each experiment's pooled z, and returns the fraction with `abs(z) > 1.96`.
---starter
def simulate_power(pA, pB, n, trials=4000, seed=0):
    rng = np.random.default_rng(seed)
    return 0.0
---solution
def simulate_power(pA, pB, n, trials=4000, seed=0):
    rng = np.random.default_rng(seed)
    cA, cB = rng.binomial(n, pA, trials), rng.binomial(n, pB, trials)
    p = (cA + cB) / (2 * n)
    z = (cB - cA) / n / np.sqrt(p * (1 - p) * 2 / n)
    return float((np.abs(z) > 1.96).mean())
---tests
pw = simulate_power(0.10, 0.12, 3834)
assert 0.76 < pw < 0.84, f"the planned size gives about 80% power; got {pw:.3f}"
fa = simulate_power(0.10, 0.10, 3834)
assert 0.035 < fa < 0.065, f"with no real lift it fires about 5% of the time; got {fa:.3f}"
assert simulate_power(0.10, 0.12, 1000) < 0.4, "too few visitors usually misses a real lift"
---hint
Vectorise: draw all `trials` experiments at once, compute arrays of z, then `(np.abs(z) > 1.96).mean()`.
```

## Testing many things at once

Ten button colours, each against the original. Even if none of them does anything, the chance that at least one shows p < 0.05 is 1 − 0.95¹⁰ ≈ 40%. The simplest fix, **Bonferroni**: with m tests, only call one significant if p < 0.05 / m. It's strict, but it's honest.

```exercise
title: bonferroni_bug
kind: bug
---prompt
`winners(p_values, alpha=0.05)` should return the indices of tests that stay significant after a Bonferroni correction. It forgot the correction. Fix it.
---starter
def winners(p_values, alpha=0.05):
    return [i for i, p in enumerate(p_values) if p < alpha]
---solution
def winners(p_values, alpha=0.05):
    m = len(p_values)
    return [i for i, p in enumerate(p_values) if p < alpha / m]
---tests
assert winners([0.03, 0.2, 0.001, 0.04, 0.5]) == [2], "with 5 tests the bar is 0.01: only the third survives"
assert winners([0.03]) == [0], "with one test nothing changes"
---hint
Divide alpha by the number of tests.
```

## The Bayesian view

Managers rarely want a p-value. They ask "how likely is it that B is better?" Bayes answers that directly. With a flat prior, each page's rate has a Beta(1 + conversions, 1 + misses) posterior (chapter 11). Draw many samples from both and count how often B's sample beats A's.

```exercise
title: prob_b_better
kind: write
---prompt
Write `prob_b_better(cA, nA, cB, nB, draws=200000, seed=0)` returning the fraction of draws where a sample from Beta(1 + cB, 1 + nB − cB) exceeds one from Beta(1 + cA, 1 + nA − cA). Use `rng.beta`.
---starter
def prob_b_better(cA, nA, cB, nB, draws=200000, seed=0):
    rng = np.random.default_rng(seed)
    return 0.5
---solution
def prob_b_better(cA, nA, cB, nB, draws=200000, seed=0):
    rng = np.random.default_rng(seed)
    a = rng.beta(1 + cA, 1 + nA - cA, draws)
    b = rng.beta(1 + cB, 1 + nB - cB, draws)
    return float((b > a).mean())
---tests
p = prob_b_better(100, 1000, 120, 1000)
assert 0.9 < p < 0.95, f"about 92% likely B is better; got {p:.3f}"
assert abs(prob_b_better(50, 500, 50, 500) - 0.5) < 0.01, "identical data: a coin flip"
---hint
Two `rng.beta(...)` arrays of length `draws`, then `(b > a).mean()`.
```

```quiz
The same data gives p = 0.15 and "P(B better) = 92%". Which is a fair summary for a manager?
- The test failed, so B is no better
- B is 92% better than A
* B is probably better, but the evidence is weak: with a flat prior, about a 1-in-12 chance A is actually better, and the lift could be tiny
- The two numbers contradict each other, so the test is broken
> They answer different questions. The p-value says a gap this size would turn up 15% of the time by chance alone. The Bayesian number says how plausible "B is better" is, given the data and a flat prior. Neither says *how much* better: report an interval for the lift too.
```

## Real-world project: run the whole test

```project
title: An honest A/B test report for a signup page
client: A startup that wants to know whether its new signup page is worth shipping
skills: sample size planning, two-proportion test, power simulation, Bonferroni, Bayesian A/B
---brief
Write a pre-registration first: the metric, the smallest lift worth shipping, the sample size and the stopping rule. Then simulate the experiment (or use real logs), analyse it exactly as planned, and write a one-page report: the lift with a 95% interval, the p-value, P(B better), and a recommendation. Add an appendix that shows, by simulation, what would have happened if you had peeked.
---why
A/B testing is how most product decisions at online companies get made, and most mistakes come from process, not maths: peeking, changing the metric afterwards, testing twenty things and reporting the one that worked. Writing the plan before seeing the data is the single habit that makes results trustworthy, in product work and in science.
---milestones
- Write the pre-registration: metric, minimum lift, alpha, power, sample size
- Simulate visitors for both pages with a seeded generator
- Run the planned two-proportion test once, at the planned end
- Compute a 95% interval for the lift and P(B better)
- Simulate 1,000 A/A experiments with peeking and report the real false-alarm rate
- Write the recommendation in plain words a manager would understand
---stretch
- Add a guardrail metric (say, refunds) that must not get worse
- Analyse revenue per visitor instead of conversion, with a bootstrap interval (chapter 9)
- Read about sequential tests and implement a simple one that allows safe peeking
```

## Rebuild it and explain it

```exercise
title: ab_report
kind: rebuild
---prompt
From memory: write `ab_report(cA, nA, cB, nB)` returning a dict with keys `"lift"` (rate B − rate A), `"z"`, `"p"` (two-sided, pooled), and `"ci"`: a 95% interval for the lift as a tuple, using the **unpooled** standard error √(rA(1 − rA)/nA + rB(1 − rB)/nB) and ±1.96.
---starter
def ab_report(cA, nA, cB, nB):
    pass
---solution
def ab_report(cA, nA, cB, nB):
    rA, rB = cA / nA, cB / nB
    p = (cA + cB) / (nA + nB)
    z = (rB - rA) / math.sqrt(p * (1 - p) * (1 / nA + 1 / nB))
    se = math.sqrt(rA * (1 - rA) / nA + rB * (1 - rB) / nB)
    lift = rB - rA
    return {"lift": lift, "z": z, "p": math.erfc(abs(z) / math.sqrt(2)), "ci": (lift - 1.96 * se, lift + 1.96 * se)}
---tests
r = ab_report(100, 1000, 120, 1000)
assert abs(r["lift"] - 0.02) < 1e-12, "a 2-point lift"
assert abs(r["p"] - 0.1529) < 1e-3, "p about 0.15"
lo, hi = r["ci"]
assert lo < 0 < hi and abs(lo + 0.0074) < 1e-3, f"the interval includes zero: about (-0.007, 0.047); got ({lo:.4f}, {hi:.4f})"
---hint
Two rates, a pooled SE for z and p, an unpooled SE for the interval.
```

```recall
Q: Explain how to run an A/B test honestly: what you decide before starting, how you analyse it, and the two classic ways people fool themselves.
A: Before starting, choose one metric, the smallest lift worth acting on, the false-alarm rate (usually 5%) and the power (usually 80%), and from those compute the sample size; write down the stopping rule. Run until that size, then do one two-proportion test: z is the gap in rates divided by its standard error, giving a p-value, and report the lift with a confidence interval (and, if useful, the Bayesian probability B is better). The classic traps: peeking (checking repeatedly and stopping at the first significant result inflates false alarms far above 5%) and multiple comparisons (testing many variants or metrics and reporting the winner); fix the second with a correction like Bonferroni, dividing alpha by the number of tests.
```

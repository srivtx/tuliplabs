## Iterate: one small improvement at a time

Chapter 2's model let stations go negative. The book's approach: don't redesign everything; make the **smallest change** that fixes the problem, run it, check it. That's **iterative modeling**.

```quiz
Why does the book build the bike model in many small steps instead of writing the whole thing at once?
- It's faster to type
* Each small change can be tested immediately, so when something breaks you know which change caused it
- Python requires it
- Big programs can't use random numbers
> Small steps keep the program working at every stage. When a test fails, the bug is in the few lines you just changed.
```

## Comparison operators

The fix needs a test: "is the station empty?" Python's comparison operators return True or False: `==`, `!=`, `<`, `<=`, `>`, `>=`. Careful: `=` assigns, `==` compares.

```predict
olin = 0
print(olin == 0, olin != 0, olin > 0)
olin = 3
print(olin >= 3 and olin < 10)
```

## Metrics: count unhappy customers

To compare designs we need a number that says how well the system works: a **metric**. The book adds two counters to the state: `olin_empty` and `wellesley_empty`, the number of customers who found an empty station.

```exercise
title: Count the disappointed
kind: write
---prompt
Write both ride functions with guards **and** metrics: when a customer finds an empty station, add 1 to that station's `_empty` counter and return without moving a bike. Include a one-line docstring in each function.
---starter
def bike_to_wellesley(state):
    pass

def bike_to_olin(state):
    pass
---solution
def bike_to_wellesley(state):
    """Move one bike from Olin to Wellesley, or count an unhappy customer."""
    if state.olin == 0:
        state.olin_empty += 1
        return
    state.olin -= 1
    state.wellesley += 1

def bike_to_olin(state):
    """Move one bike from Wellesley to Olin, or count an unhappy customer."""
    if state.wellesley == 0:
        state.wellesley_empty += 1
        return
    state.wellesley -= 1
    state.olin += 1
---tests
s = State(olin=1, wellesley=0, olin_empty=0, wellesley_empty=0)
bike_to_olin(s)
assert s.wellesley_empty == 1 and (s.olin, s.wellesley) == (1, 0), "Empty Wellesley: count it, move nothing"
bike_to_wellesley(s); bike_to_wellesley(s)
assert (s.olin, s.wellesley, s.olin_empty) == (0, 1, 1), "One ride, then one unhappy customer at Olin"
assert bike_to_olin.__doc__ and bike_to_wellesley.__doc__, "Add a docstring to each function"
---hint
A docstring is a string literal on the first line of the function body: `"""What it does."""`.
```

## Run an afternoon

```run
title: Two hours, with metrics
def bike_to_wellesley(state):
    if state.olin == 0:
        state.olin_empty += 1
        return
    state.olin -= 1; state.wellesley += 1

def bike_to_olin(state):
    if state.wellesley == 0:
        state.wellesley_empty += 1
        return
    state.wellesley -= 1; state.olin += 1

def step(state, p1, p2):
    if flip(p1):
        bike_to_wellesley(state)
    if flip(p2):
        bike_to_olin(state)

bikeshare = State(olin=10, wellesley=2, olin_empty=0, wellesley_empty=0)
olin, wellesley = TimeSeries(), TimeSeries()
for i in range(120):
    step(bikeshare, 0.4, 0.2)
    olin[i], wellesley[i] = bikeshare.olin, bikeshare.wellesley
plot(olin, label="Olin"); plot(wellesley, label="Wellesley")
decorate(xlabel="Time step (min)", ylabel="Number of bikes")
print("unhappy at Olin:", bikeshare.olin_empty, "  unhappy at Wellesley:", bikeshare.wellesley_empty)
```

```recall
Q: What is a metric, and which metrics does the bike model use?
A: - A metric is a number computed from a simulation that measures how well the system works, so you can compare designs or parameters.
- The bike model counts `olin_empty` and `wellesley_empty`: customers who arrived at an empty station.
```

## Real-world project: drivers turned away at an EV charging hub

An empty bike station and a full car charger are the same problem in disguise: a customer shows up and the thing they want isn't there. The fix is the same too: guard against the impossible state (more cars charging than there are chargers) and **count** the people you had to turn away, because that count is the number the business decides with.

```project
title: How many chargers does the motorway services need?
client: A motorway service station installing electric-car chargers
skills: guards with early return, counters in a State, docstrings, iterating a model
---brief
The operator has a log from a busy Saturday: a string where `A` means a car arrived wanting to charge and `L` means a car finished and left. Build a model with a `State` holding free chargers and a `turned_away` counter, replay the log, and report how many drivers left without charging for 4, 6 and 8 chargers.
---why
Counting failed requests is the core metric of real systems: "requests dropped" on a web server, "calls that got a busy signal" at a call centre, "orders we couldn't fill" in a warehouse. Every capacity decision (servers, staff, chargers, parking spaces) starts with a guard and a counter like the ones you just wrote.
---milestones
- Write `arrive(state)`: take a free charger, or count a driver turned away
- Write `leave(state, chargers)`: free a charger, but never more than exist
- Write `run_log(log, chargers)` that replays a day and returns the turned-away count
- Replay the Saturday log for 4, 6 and 8 chargers and pick the smallest number that keeps losses under 5
- Write a docstring for every function that says what it does and what it guards against
---stretch
- Add a waiting bay: up to 2 drivers will wait for a charger before giving up
- Generate random logs with `flip` and average the turned-away count over 100 days
- Track the busiest minute: the longest run of time with zero free chargers
```

```exercise
title: arrive and leave at the charging hub
kind: write
---prompt
Write `arrive(state)` and `leave(state, chargers)`. `state` has `free` (chargers not in use) and `turned_away`.
- `arrive`: if no charger is free, add 1 to `turned_away` and return; otherwise take one (`free` goes down by 1).
- `leave`: a car finishes and frees its charger, but `free` can never go above `chargers` (if it's already full, do nothing).

Give each function a one-line docstring.
---starter
def arrive(state):
    state.free -= 1

def leave(state, chargers):
    state.free += 1
---solution
def arrive(state):
    """A car arrives: take a free charger, or count the driver as turned away."""
    if state.free == 0:
        state.turned_away += 1
        return
    state.free -= 1

def leave(state, chargers):
    """A car leaves: free its charger, never more chargers than exist."""
    if state.free == chargers:
        return
    state.free += 1
---tests
s = State(free=1, turned_away=0)
arrive(s)
assert (s.free, s.turned_away) == (0, 0), "One free charger: the car takes it"
arrive(s)
assert (s.free, s.turned_away) == (0, 1), f"No free charger: count one driver turned away and don't go negative. Got free={s.free}, turned_away={s.turned_away}"
leave(s, 1); leave(s, 1)
assert s.free == 1, f"With 1 charger, free can't go above 1, got {s.free}"
assert arrive.__doc__ and leave.__doc__, "Add a docstring to each function"
```

```exercise
title: run_log for a day of charging
kind: write
---prompt
Write `run_log(log, chargers)`: start with all chargers free and nobody turned away, then go through the string `log` one letter at a time, calling `arrive` for `"A"` and `leave` for `"L"`. Return the number of drivers turned away. Both helper functions are provided.
---setup
def arrive(state):
    if state.free == 0:
        state.turned_away += 1
        return
    state.free -= 1

def leave(state, chargers):
    if state.free == chargers:
        return
    state.free += 1
---starter
def run_log(log, chargers):
    state = State(free=chargers, turned_away=0)
    return 0
---solution
def run_log(log, chargers):
    state = State(free=chargers, turned_away=0)
    for event in log:
        if event == "A":
            arrive(state)
        elif event == "L":
            leave(state, chargers)
    return state.turned_away
---tests
assert run_log("AAA", 2) == 1, f"Three cars, two chargers: one turned away. Got {run_log('AAA', 2)}"
assert run_log("AALA", 2) == 0, "A car left in time, so the third driver gets a charger"
saturday = "AAAAALAAALLAAAALAALLLAAAA"
assert run_log(saturday, 4) == 7, f"Saturday with 4 chargers: 7 drivers turned away, got {run_log(saturday, 4)}"
assert run_log(saturday, 8) < run_log(saturday, 4), "More chargers should never turn more people away"
---hint
Each call to `run_log` should start from a fresh `State`, so different charger counts don't share results.
```

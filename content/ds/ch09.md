## Halving

On a sorted list, looking at the middle tells you which half can't hold the answer. Throw that half away and repeat: n → n/2 → n/4 → … → 1 takes about **log₂ n** looks.

```viz

title: Scanning against binary search on 32 sorted numbers
goal: Run **scan from the left** to the end, then run **binary search** and compare the looks.
height: 440
Try **target 50** too: it isn't in the list, but binary search still says exactly where it would go.
```

The safest way to think about binary search: don't search for "the target"; search for **the first position where a condition becomes true**. On a sorted list, `A[i] >= x` is false, false, …, false, true, true, …, true. Binary search finds the boundary. That position is called **lower_bound**:

```run
title: The one template to remember
def lower_bound(a, x):
    lo, hi = 0, len(a)          # the answer is somewhere in [lo, hi]; hi = len(a) means "after everything"
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:          # condition false at mid: the boundary is to the right
            lo = mid + 1
        else:                   # condition true at mid: the boundary is mid or to the left
            hi = mid
    return lo

a = [2, 4, 4, 4, 7, 9]
print(lower_bound(a, 4), lower_bound(a, 5), lower_bound(a, 1), lower_bound(a, 10))
```

Python ships this as `bisect_left(a, x)`. Its sibling `bisect_right(a, x)` is the first position with `a[i] > x`. Between them sit all copies of `x`:

```predict
from bisect import bisect_left, bisect_right
a = [1, 3, 3, 3, 5, 8]
print(bisect_left(a, 3), bisect_right(a, 3), bisect_right(a, 3) - bisect_left(a, 3))
print(bisect_left(a, 4), bisect_right(a, 4))
```

```quiz
`lower_bound` uses `lo, hi = 0, len(a)` and `while lo < hi`. Why is `hi` set to `len(a)` and not `len(a) - 1`?
- It's a typo that happens to work
* The answer can be "after the last item" (x bigger than everything), which is position len(a)
- So that `mid` is never 0
- Because Python lists start at 1
> The answer space has n + 1 positions, 0..n. Using len(a) − 1 makes inserting at the end impossible.
```

## Sorted in pieces

Binary search doesn't need the whole list sorted; it needs a question whose answer flips **once** from false to true. A rotated sorted list (`[4, 5, 6, 7, 0, 1, 2]`) still has one: "is this item ≤ the last item?"

```exercise
title: rotated_min
kind: write
---prompt
*LeetCode 153.* A sorted list of distinct numbers was rotated (`[4, 5, 6, 7, 0, 1, 2]`). Return its smallest number in O(log n). The items that are ≤ the last item form the right part, which starts with the minimum.
---starter
def rotated_min(a):
    return a[0]
---solution
def rotated_min(a):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] > a[-1]:
            lo = mid + 1
        else:
            hi = mid
    return a[lo]
---tests
assert rotated_min([4, 5, 6, 7, 0, 1, 2]) == 0
assert rotated_min([3, 4, 5, 1, 2]) == 1
assert rotated_min([11, 13, 15, 17]) == 11
assert rotated_min([2, 1]) == 1
assert rotated_min([5]) == 5
---hint
Condition "a[mid] ≤ a[-1]" is false for the left part, true for the right part. Find the first true.
```

```exercise
title: rotated_search
kind: write
---prompt
*LeetCode 33, asked constantly.* Find `target`'s index in a rotated sorted list of distinct numbers, or -1, in O(log n). At every `mid`, one of the two halves is properly sorted; check whether the target lies inside that half's range.
---starter
def search(a, target):
    for i, v in enumerate(a):
        if v == target:
            return i
    return -1
---solution
def search(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == target:
            return mid
        if a[lo] <= a[mid]:
            if a[lo] <= target < a[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:
            if a[mid] < target <= a[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1
---tests
assert search([4, 5, 6, 7, 0, 1, 2], 0) == 4
assert search([4, 5, 6, 7, 0, 1, 2], 3) == -1
assert search([1], 0) == -1
assert search([1], 1) == 0
assert search([3, 1], 1) == 1
assert search([5, 1, 3], 5) == 0
big = list(range(10000, 20000)) + list(range(10000))
def many():
    return [search(big, x) for x in range(9800, 10000)]
r, secs = timed(many)
assert r == list(range(19800, 20000)) and secs < 0.02, f"{secs:.2f}s for 200 searches: binary search the sorted half"
---hint
If `a[lo] <= a[mid]`, the left half `lo..mid` is sorted: go left only if `a[lo] <= target < a[mid]`. Otherwise the right half `mid..hi` is sorted: go right only if `a[mid] < target <= a[hi]`.
```

```quiz

- 1 and 3
* 1 and 4
- 2 and 2
- 0 and 4
> bisect_left: the first position ≥ 2 (index 1). bisect_right: the first position > 2 (index 4). Their difference, 3, is how many 2s there are.
```

```quiz
In `while lo < hi`, why `hi = mid` (not `mid − 1`) when `a[mid] >= x`?
* mid itself might be the answer, so it has to stay in the range
- To make the loop run faster
- `mid − 1` would go negative
- It doesn't matter
> The condition is true at mid, so mid is a candidate. `lo = mid + 1` is safe on the other side, because the condition is false at mid.
```

```quiz
What does binary search really need?
- The numbers to be distinct
- An array of length 2ᵏ
* A yes/no question whose answer goes no, no, …, no, yes, yes, …, yes along the range
- The target to be in the list
> Sortedness is just the most common way to get that shape. Rotated lists and peaks have it too, and chapter 10 uses it on answers, not indices.
```

```quiz
`mid = (lo + hi) // 2` in Python, versus `lo + (hi - lo) // 2` in C++/Java. Why do those languages prefer the second?
- It's faster
* `lo + hi` can overflow a 32-bit int; Python's integers can't overflow
- It rounds differently
- It avoids negative indices
> A famous bug that lived in Java's library for years. In Python both are fine.
```

## Rebuild it and explain it

```recall
Q: Explain binary search as "find the first position where a condition becomes true", with the lower_bound template and its pitfalls.
A: Binary search works on any range where a yes/no condition goes false, false, …, true, true: on a sorted list, "a[i] ≥ x" has that shape. Keep the answer inside [lo, hi] with hi = len(a) (the answer can be past the end). While lo < hi, look at mid: if the condition is false there, the boundary is to the right, so lo = mid + 1; if true, mid could be the answer, so hi = mid. The loop ends with lo = hi at the first true position, after about log₂ n looks (30 for a billion). Python's bisect_left is this lower_bound and bisect_right is the first position > x; their difference counts copies. Pitfalls are off-by-ones: hi = len(a) − 1 forgets the end, hi = mid − 1 can skip the answer, and lo = mid can loop forever. The same template handles rotated lists (condition: a[i] ≤ a[−1]) and peaks (condition: a[i] > a[i+1]).
```

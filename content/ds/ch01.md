```prelude
import time

def timed(fn, *args):
    """Run fn(*args) and return (result, seconds)."""
    t = time.perf_counter()
    out = fn(*args)
    return out, time.perf_counter() - t
```

## Why count steps at all

Two correct programs can differ by a factor of a million in speed. Timing them on your laptop with 10 items tells you nothing: both finish instantly. What matters is how the work **grows** when the input gets bigger. That's what Big-O describes: drop the constants, keep the shape.

A computer does roughly **10⁸ simple steps a second** (pure Python is slower, nearer 10⁷). Every problem on LeetCode or Codeforces states its limits, like `1 ≤ n ≤ 200 000`, and a time limit of 1 or 2 seconds. Put those together and you know what kind of solution the setter expects before you've read the rest.

## Counting a loop

Count how many times the innermost line runs. A loop over `range(n)` runs n times; a loop inside a loop multiplies.

```predict
n = 6
count = 0
for i in range(n):
    for j in range(i + 1, n):
        count += 1
print(count, n * (n - 1) // 2)
```

Every pair (i, j) with i < j is counted once: n(n−1)/2 pairs. That's about n²/2, and Big-O drops the ½: it's **O(n²)**.

```quiz
How many times does the loop body run, as a function of n?
`while n > 1: n = n // 2`
- n
- n / 2
* about log₂ n
- n²
> Each step halves n. Starting from a million, you reach 1 after about 20 halvings, because 2²⁰ ≈ 10⁶. Halving is the signature of O(log n).
```

```quiz
`for i in range(n): for j in range(0, n, 2): ...` What's the Big-O?
- O(n)
* O(n²)
- O(n log n)
- O(n² / 2), which is different from O(n²)
> The inner loop runs n/2 times for each of n values of i: n²/2 steps. Constant factors like ½ are dropped, so it's O(n²). (They still matter in practice, but they never change which bar you're on.)
```

```quiz
`for i in range(n): j = 1; while j < n: j *= 2`. What's the Big-O?
- O(n²)
- O(log n)
* O(n log n)
- O(n)
> The outer loop runs n times; the inner one doubles j, so it runs about log₂ n times. n × log n.
```

## Reading the limits

This table is worth memorising. It's the first thing strong competitors look at.

| Largest n | Most work you can afford | What it usually means |
|---|---|---|
| n ≤ 10 | O(n!) | try every ordering |
| n ≤ 20 | O(2ⁿ · n) | try every subset |
| n ≤ 500 | O(n³) | three nested loops |
| n ≤ 5 000 | O(n²) | every pair |
| n ≤ 10⁶ | O(n log n) | sort, heap, binary search |
| n ≤ 10⁸ | O(n) | one pass |
| n ≤ 10¹⁸ | O(log n) or O(1) | maths, or halving |

```exercise
title: allowed
kind: write
---prompt
Write `allowed(n)` that returns the most work you can afford for that largest input size, as one of these strings, using the table: `"n!"`, `"2^n"`, `"n^3"`, `"n^2"`, `"n log n"`, `"n"`, `"log n"`.
---starter
def allowed(n):
    return "n"
---solution
def allowed(n):
    for limit, kind in ((10, "n!"), (20, "2^n"), (500, "n^3"), (5000, "n^2"), (10**6, "n log n"), (10**8, "n")):
        if n <= limit:
            return kind
    return "log n"
---tests

assert allowed(18) == "2^n"
assert allowed(400) == "n^3"
assert allowed(2000) == "n^2"
assert allowed(200_000) == "n log n"
assert allowed(10**6) == "n log n"
assert allowed(5 * 10**7) == "n"
assert allowed(10**18) == "log n"
---hint
Check the thresholds from smallest to largest and return the first one that n fits under. A list of `(limit, kind)` pairs keeps it short.
```

## One pass instead of two loops

The most common speed-up in all of DSA: instead of looking back at every earlier item, **remember a summary** of what you've seen so far (the smallest, the sum, the count). Then each new item costs O(1).

```exercise
title: best_profit
kind: write
---prompt
*An interview classic.* `prices[i]` is a share's price on day i. You may buy on one day and sell on a **later** day, once. Write `best_profit(prices)` returning the most money you can make (0 if every choice loses money). n can be 200 000, so trying every pair (buy day, sell day) is too slow.
---starter
def best_profit(prices):
    best = 0
    for i in range(len(prices)):
        for j in range(i + 1, len(prices)):
            best = max(best, prices[j] - prices[i])
    return best
---solution
def best_profit(prices):
    lowest = float("inf")
    best = 0
    for p in prices:
        lowest = min(lowest, p)
        best = max(best, p - lowest)
    return best
---tests
assert best_profit([7, 1, 5, 3, 6, 4]) == 5, "buy at 1, sell at 6"
assert best_profit([7, 6, 4, 3, 1]) == 0, "prices only fall: don't trade"
assert best_profit([2]) == 0
assert best_profit([3, 3, 3]) == 0
assert best_profit([1, 9, 0, 5]) == 8, "the later low (0) doesn't beat 9 - 1"
big = list(range(5000, 0, -1))
r, secs = timed(best_profit, big)
assert r == 0
assert secs < 0.25, f"took {secs:.2f}s on 5 000 days: that's the O(n²) double loop. Keep the lowest price so far instead."
---hint
On each day, the best sale is today's price minus the **lowest price before today**. Keep that lowest price in a variable as you walk.
---hint
Two variables, one loop: `lowest = min(lowest, p)` and `best = max(best, p - lowest)`.
```

## Let maths do the loop

```exercise
title: missing_number
kind: write
---prompt
*An interview classic.* `nums` holds n different numbers from `0..n`, so exactly one number in that range is missing. Return it, in O(n) time and O(1) extra space (no set, no sorting).
---starter
def missing_number(nums):
    for k in range(len(nums) + 1):
        if k not in nums:
            return k
---solution
def missing_number(nums):
    n = len(nums)
    return n * (n + 1) // 2 - sum(nums)
---tests
assert missing_number([3, 0, 1]) == 2
assert missing_number([0, 1]) == 2
assert missing_number([1]) == 0
assert missing_number([9, 6, 4, 2, 3, 5, 7, 0, 1]) == 8
big = list(range(20000)); big.remove(12345)
r, secs = timed(missing_number, big)
assert r == 12345
assert secs < 0.2, f"{secs:.2f}s: `k not in nums` scans the whole list each time, so this is O(n²)"
---hint
`0 + 1 + … + n = n(n+1)/2`. The total of what's there is `sum(nums)`. The difference is the missing number.
```

`k not in nums` *looks* like one step but it's a hidden loop over the list. Spotting hidden loops (`in` on a list, `list.index`, `list.remove`, slicing, string `+=` in a loop) is half of Big-O in Python.

```quiz
Which of these is **not** O(1) in Python?
- `d[key]` on a dict
- `a[-1]` on a list
- `a.append(x)` on a list
* `x in a` on a list
> `in` on a list checks items one by one: O(n). On a set or dict it's O(1) on average, because they hash. That's the whole of chapter 3.
```

```exercise
title: pair_products
kind: write
---prompt
*Codeforces style.* Given a list `a` of up to 2·10⁵ integers, return the sum of `a[i] * a[j]` over all pairs `i < j`. The double loop is 2·10¹⁰ steps. Find an O(n) way.
---starter
def pair_products(a):
    total = 0
    for i in range(len(a)):
        for j in range(i + 1, len(a)):
            total += a[i] * a[j]
    return total
---solution
def pair_products(a):
    total = 0
    seen = 0
    for x in a:
        total += x * seen
        seen += x
    return total
---tests
assert pair_products([1, 2, 3]) == 1*2 + 1*3 + 2*3
assert pair_products([5]) == 0
assert pair_products([]) == 0
assert pair_products([-1, 4, 2, -3]) == -4 - 2 + 3 + 8 - 12 - 6
big = list(range(1, 4001))
r, secs = timed(pair_products, big)
s = sum(big); assert r == (s * s - sum(x * x for x in big)) // 2
assert secs < 0.25, f"{secs:.2f}s: too slow, that's the O(n²) double loop"
---hint
Each `x` gets multiplied by every number **before** it. That's `x * (sum of the earlier numbers)`. Keep the running sum.
---hint
Another route: `(a₁ + … + aₙ)² = Σaᵢ² + 2·Σ_{i<j} aᵢaⱼ`, so the answer is `(sum(a)**2 - sum of squares) // 2`.
```

```predict
calls = 0
def f(n):
    global calls
    calls += 1
    if n > 1:
        f(n // 2)
        f(n // 2)
f(16)
print(calls)
```

Each call makes two calls on half the size. The levels have 1, 2, 4, 8, 16 calls: 31 in total, about 2n. Not every recursion is slow; it depends how fast the problem shrinks. (Chapter 5 builds this from scratch.)

```quiz
A problem: "1 ≤ n ≤ 18. Choose some of the n items so their weights sum to exactly W." What does the limit tell you?
- It needs dynamic programming
- It needs a greedy rule
* Trying every subset is allowed: 2¹⁸ ≈ 260 000 subsets
- It needs sorting first
> n ≤ 20 is the setter saying "brute force over subsets is fine." Small limits are a hint, not an accident.
```

## Real-world project: will it scale?

```project
title: A "will it scale?" checker for a team's code
client: A start-up whose search page was fast in testing and timed out on launch day with 50 000 users
skills: timing, log-log fits, Big-O, performance testing
---brief
Build `scale.py` that takes a function and an input generator, runs the function at sizes n = 1 000, 2 000, 4 000, 8 000, … (stopping when one run takes more than 2 seconds), and reports the growth: "looks like O(n²): at your production size of 50 000 this takes about 40 s". Fit the slope of log(time) against log(n): a slope near 1 is linear, near 2 quadratic. Add it to the test suite so a slow change fails the build.
---why
Performance bugs pass every functional test and only show up at real sizes. Doubling the input and watching the time is how engineers spot O(n²) before users do; the same idea (benchmarks in CI) runs at every large tech company.
---milestones
- Time a function at doubling sizes, with a cut-off
- Estimate the exponent from the timings
- Predict the time at a production size
- Fail loudly when the exponent jumps between two versions
---stretch
- Repeat each timing a few times and take the minimum (noise only ever makes things slower)
- Tell n log n apart from n (it needs a wider range of sizes)
```

```exercise
title: growth_exponent
kind: write
---prompt
Write `growth_exponent(sizes, seconds)`: given input sizes and how long each run took, return the slope of the best straight line through the points `(log n, log t)` (least squares), rounded to 1 decimal. A slope of 2.0 means time grows like n².
---starter
import math

def growth_exponent(sizes, seconds):
    return 0.0
---solution
import math

def growth_exponent(sizes, seconds):
    xs = [math.log(n) for n in sizes]
    ys = [math.log(t) for t in seconds]
    mx, my = sum(xs) / len(xs), sum(ys) / len(ys)
    slope = sum((x - mx) * (y - my) for x, y in zip(xs, ys)) / sum((x - mx) ** 2 for x in xs)
    return round(slope, 1)
---tests
assert growth_exponent([1000, 2000, 4000, 8000], [0.01, 0.04, 0.16, 0.64]) == 2.0
assert growth_exponent([1000, 2000, 4000], [0.5, 1.0, 2.0]) == 1.0
assert growth_exponent([10, 100, 1000], [1, 1000, 1e6]) == 3.0
assert growth_exponent([100, 200, 400, 800], [0.011, 0.039, 0.17, 0.62]) == 2.0, "noisy, but about quadratic"
---hint
On a log-log plot, `t = c·nᵏ` is a straight line with slope k. Least-squares slope: `Σ(x−x̄)(y−ȳ) / Σ(x−x̄)²`.
```

```exercise
title: predict_time
kind: write
---prompt
Write `predict_time(n0, t0, k, n)`: a run at size `n0` took `t0` seconds and time grows like nᵏ. Return the predicted seconds at size `n`, rounded to 2 decimals.
---starter
def predict_time(n0, t0, k, n):
    return t0
---solution
def predict_time(n0, t0, k, n):
    return round(t0 * (n / n0) ** k, 2)
---tests
assert predict_time(8000, 0.64, 2, 50000) == 25.0
assert predict_time(1000, 0.5, 1, 4000) == 2.0
assert predict_time(100, 0.01, 3, 1000) == 10.0
---hint
Ten times the input with k = 2 is a hundred times the time: `t0 * (n / n0) ** k`.
```

## Quick-fire: lock it in

```quiz
`s = ""` then `for w in words: s += w`. In the worst case, what can this cost for n words?
- O(1) per word, so O(n)
* O(n²) characters copied, because strings can't be changed in place
- O(log n)
- O(n log n)
> Each `+=` may build a brand-new string and copy everything so far. `"".join(words)` copies each character once: O(total length).
```

```quiz
An O(n²) solution takes 1 second at n = 10 000. About how long at n = 100 000?
- 10 seconds
* 100 seconds
- 1 000 seconds
- 2 seconds
> 10× the input, squared: 100× the time. Doubling n doubles an O(n) program and quadruples an O(n²) one.
```

```quiz
Which grows fastest as n gets large?
- n³
- n² log n
* 2ⁿ
- n¹⁰
> Any exponential beats any polynomial in the end. 2ⁿ passes n¹⁰ at about n = 59 and never looks back.
```

```quiz
`a.sort()` followed by one loop over `a`. Total?
- O(n)
* O(n log n)
- O(n²)
- O(n log n + n²)
> Add the steps: n log n + n. Keep only the biggest term: O(n log n).
```

```quiz
`for i in range(n): if i in seen_set: ...` where `seen_set` is a Python `set`. Total?
* O(n) on average
- O(n²)
- O(n log n)
- O(log n)
> A set lookup is O(1) on average (it hashes), so n lookups cost O(n). With a list instead of a set, the same line would be O(n²).
```

```quiz
A problem allows n ≤ 10¹⁸. What kind of solution is it asking for?
- One pass over the input
- Sorting
* A formula, or something that halves (O(log n)) like binary search or fast power
- Trying every subset
> You can't even loop to 10¹⁸. The answer must come from maths or from cutting the problem in half each step.
```

```recall
Q: What does Big-O measure, and how do you use a problem's limits to choose an algorithm?
A: Big-O describes how the number of steps grows as the input size n grows, ignoring constant factors: a loop over n items is O(n), two nested loops over all pairs O(n²), halving each step O(log n), trying every subset O(2ⁿ). A computer does roughly 10⁸ simple steps a second (pure Python closer to 10⁷), so the limit on n tells you the most work you can afford: n ≤ 20 allows 2ⁿ, n ≤ 5 000 allows n², n up to about 10⁶ needs n log n or better, and huge n needs O(log n) maths. To speed something up, keep a running summary (lowest so far, running sum) instead of looking back at every earlier item, and watch for hidden loops like `x in list`.
```

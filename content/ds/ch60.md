## Your tests have your blind spots

You wrote a fast solution and three tests, and they pass. The judge says "wrong answer on test 17". The tests you write by hand check the cases you **thought of**, and bugs live in the cases you didn't.

A **stress test** is four parts:

1. **A slow solution** that's obviously right: brute force, every subset, every pair. It only has to handle tiny inputs.
2. **A generator** of small random inputs. Small matters: a failing input of 4 numbers is easy to debug, and small ranges (values 0–9, lengths 1–6) hit duplicates, negatives and empty cases often.
3. **A loop** that runs both and stops at the first disagreement.
4. **Shrinking**: remove pieces of the failing input while it still fails, to get the smallest example.

Seeding the random generator makes a failure repeatable: rerun with the same seed and you get the same input. Use your own generator, or Python's `random.Random(seed)`.

```run
title: A ten-line stress test
rng = random.Random(1)
for trial in range(1, 10001):
    a = [rng.randint(-5, 5) for _ in range(rng.randint(1, 6))]
    if best_run_buggy(a) != best_run_slow(a):
        print("trial", trial, "input", a, "fast", best_run_buggy(a), "slow", best_run_slow(a))
        break
else:
    print("no difference in 10,000 trials")
```

```quiz
Why test with tiny inputs (length 1–6, values 0–9) rather than big ones?
- Big inputs are slower to generate
* Small ranges hit edge cases (duplicates, negatives, empty, all-equal) often, and a failing case is short enough to debug by hand
- The judge only uses small inputs
- Big inputs never find bugs
> Most bugs show on tiny inputs. Use big inputs separately, to test speed.
```

```exercise
title: shrink_it
kind: write
---prompt
Write `shrink(xs, fails)`: `fails(list)` returns True when a list still shows the bug. Repeatedly try removing one element; whenever the shorter list still fails, keep it and start over. Stop when no single removal still fails, and return that list.
---starter
def shrink(xs, fails):
    return xs
---solution
def shrink(xs, fails):
    changed = True
    while changed:
        changed = False
        for i in range(len(xs)):
            c = xs[:i] + xs[i + 1:]
            if fails(c):
                xs, changed = c, True
                break
    return xs
---tests
def minimal(xs, fails):
    assert fails(xs), "the result must still fail"
    for i in range(len(xs)):
        assert not fails(xs[:i] + xs[i + 1:]), f"removing index {i} still fails, so keep shrinking"
f1 = lambda a: len(a) > 0 and best_run_buggy(a) != best_run_slow(a)
r = shrink([-2, -7, -5, -1, -5], f1)
minimal(r, f1)
assert len(r) == 1
f2 = lambda a: sum(a) > 10
minimal(shrink([5, 1, 7, 2], f2), f2)
f3 = lambda a: len(set(a)) < len(a)
assert shrink([4, 1, 9, 1, 3], f3) == [1, 1]
---hint
A `while changed` loop around a `for` over positions. Restart the `for` after every successful removal.
```

```exercise
title: break_it
kind: write
---prompt
`count_pairs_fast(a)` is meant to count pairs i < j with `a[i] > a[j]` (inversions), but it has a bug. Write `counterexample()`: return any list where it disagrees with `count_pairs_slow`. Write a stress loop to find one rather than guessing.
---setup
def count_pairs_slow(a):
    return sum(1 for i in range(len(a)) for j in range(i + 1, len(a)) if a[i] > a[j])

def count_pairs_fast(a):
    if len(a) < 2:
        return 0
    m = len(a) // 2
    L, R = sorted(a[:m]), sorted(a[m:])
    count, j = count_pairs_fast(a[:m]) + count_pairs_fast(a[m:]), 0
    for x in L:
        while j < len(R) and R[j] <= x:
            j += 1
        count += j
    return count
---starter
def counterexample():
    return [3, 1, 2]
---solution
def counterexample():
    rng = random.Random(0)
    while True:
        a = [rng.randint(0, 3) for _ in range(rng.randint(1, 5))]
        if count_pairs_fast(a) != count_pairs_slow(a):
            return a
---tests
c = counterexample()
assert isinstance(c, list) and len(c) <= 50
assert count_pairs_fast(c) != count_pairs_slow(c), f"both give {count_pairs_slow(c)} on {c}"
---hint
[3, 1, 2] has no repeated values. The bug shows up with equal numbers: use a small value range so repeats are common.
---hint
`R[j] <= x` also counts right-half values equal to x, but equal values aren't inversions. [1, 1] gives 1 instead of 0.
```

## Quick-fire: lock it in

```quiz

- Always the fast one
- Always the slow one
```

## Real-world project: checking a teammate's binary search

```project
title: A test harness for binary search
client: A team whose services all carry their own hand-rolled "first position not less than x" search, and a reviewer who wants each one checked automatically before merge
skills: a trusted reference (bisect), random sorted inputs with duplicates, stress loops, shrinking
---brief
Build `harness.py`. Given a function `search(a, x)`, generate thousands of small sorted lists (lengths 0–8, values 0–9, so duplicates and misses are common) and target values just outside the range too. Compare against `bisect_left`. Report pass or the smallest failing case.
---why
This is property-based testing, the idea behind Hypothesis (Python) and QuickCheck (Haskell). Companies stress-test parsers, compilers, databases and network protocols the same way, under the name fuzzing.
---milestones
- Random sorted lists with duplicates
- Compare against bisect_left
- Catch empty lists and targets past either end
- Shrink the failing case
---stretch
- Time each implementation on big inputs, too
- Test `bisect_right` behaviour as well
```

```exercise
title: check_search
kind: write
---prompt
Write `is_correct(search)`: stress-test `search(a, x)`, which should return the first index i with `a[i] >= x` in sorted list `a` (`len(a)` if none). Return `True` if it agrees with `bisect_left` on at least 2,000 random cases, `False` as soon as one disagrees. Make sure your cases include empty lists, duplicates, and targets below the smallest and above the largest value.
---setup
def good(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1
        else:
            hi = mid
    return lo

def bad_high(a, x):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1
        else:
            hi = mid
    return lo

def bad_equal(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] <= x:
            lo = mid + 1
        else:
            hi = mid
    return lo

def linear_scan(a, x):
    if a and x > a[-1]:
        return len(a)
    return next((i for i, v in enumerate(a) if v >= x), 0)
---starter
def is_correct(search):
    return search([1, 2, 3], 2) == 1
---solution
def is_correct(search):
    rng = random.Random(0)
    for _ in range(2000):
        a = sorted(rng.randint(0, 9) for _ in range(rng.randint(0, 8)))
        x = rng.randint(-1, 10)
        if search(a, x) != bisect_left(a, x):
            return False
    return True
---tests
assert is_correct(good) is True
assert is_correct(bisect_left) is True
assert is_correct(bad_high) is False, "fails when x is bigger than everything"
assert is_correct(bad_equal) is False, "fails on duplicates equal to x"
assert is_correct(linear_scan) is True, "slow but correct, so it should pass"
---hint
The starter checks a single case, which every version passes. Generate many random sorted lists.
---hint
```

```recall
Q: Explain stress testing: the four parts, why inputs should be small with small value ranges, why to seed the generator, how shrinking works, and what to do when fast and slow disagree.
A: Hand-written tests only cover the cases you thought of. A stress test has four parts. A slow solution that's obviously correct, usually brute force, which only needs to handle tiny inputs. A generator of small random inputs. A loop that runs both and stops at the first disagreement. And shrinking. Small lengths and value ranges make duplicates, negatives, empty lists and boundary values common, and a short failing case is easy to debug by hand. Seeding the generator makes the same inputs come back, so a failure can be rerun after a fix. Shrinking repeatedly removes one element while the input still fails, until no single removal fails; the result points at the condition that breaks, like all-negative arrays or equal values. When fast and slow disagree, the fast one is usually wrong, but check the slow one too, which is why it should be as simple as possible. The same idea scaled up is property-based testing (Hypothesis, QuickCheck) and fuzzing.
```

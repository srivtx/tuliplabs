This is the project people build when they learn Express: a small **REST API**, grown one feature at a time. It's about plants, so every request reads like something real: `GET /api/plants?water=weekly`, `POST /api/plants {"name": "Rose", "water": "weekly"}`.

**Express** is the web framework most Node backends use, and the sandbox has it built in: `require("express")` works with nothing to install. The terminal is a client: **client.js** starts your server, then sends each line you type as a real HTTP request. Add `-i` to any request to see the response headers too.

```ticket
---brief
Press **Run** and type `GET /` in the terminal. The answer is `404 Not Found` and `Cannot GET /`: the server is running, but it has no routes yet, so Express answers for you.

An Express app is a list of routes. **`app.get(path, handler)`** says: when a `GET` request comes in for this path, call `handler(req, res)`. `req` is the request; `res` is how you answer. **`res.send(text)`** sends the answer and finishes it.

Add two routes:

| Request | Answer |
|---|---|
| `GET /` | `Hello from Express!` |
| `GET /about` | a sentence about the API that mentions `Greenhouse` |

**`app.listen(3000)`** at the bottom starts the server on port 3000, where client.js sends its requests. Try `GET / -i` once it works, and look at the headers Express added for you.
---why
Every Express app you'll ever read starts with these four lines: create the app, add routes, answer with `res.send`, listen on a port. The headers you see with `-i` are Express doing work for you. `content-type` tells the client it's HTML. `etag` is a fingerprint of the body, so a browser can ask *"has it changed?"* instead of downloading it again. `x-powered-by` just advertises Express; real apps often turn it off with `app.disable("x-powered-by")`.

// client.js: the terminal. It starts your server, then turns each line you type into an HTTP request
// and sends it with fetch(), the way a browser, curl or another service would. You don't need to change it.
//
//   GET /notes                         a request
//   POST /notes {"text": "milk"}       with a JSON body
//   GET /notes -i                      -i shows the response's headers too
//   GET /me -H "Authorization: abc"    -H adds a request header
require("./app");

const PORT = 3000;
// headers Node adds to every response, left out so the ones your code sets stand out
const HIDDEN = new Set(["connection", "content-length", "date", "keep-alive", "transfer-encoding"]);

function parse(line) {
  const m = /^(\S+)\s+(\S+)\s*(.*)$/.exec(line.trim());
  if (!m) return null;
  let [, method, path, rest] = m;
  const headers = {};
  let verbose = false;
  rest = rest.replace(/(^|\s)-H\s+"([^"]*)"/g, (_, space, h) => {
    const i = h.indexOf(":");
    headers[h.slice(0, i).trim()] = h.slice(i + 1).trim();
    return space;
  });
  rest = rest.replace(/(^|\s)-i(?=\s|$)/g, () => { verbose = true; return ""; }).trim();
  if (rest && !Object.keys(headers).some((k) => k.toLowerCase() === "content-type")) {
    headers["Content-Type"] = /^[[{]/.test(rest) ? "application/json" : "text/plain";
  }
  return { method: method.toUpperCase(), path, headers, body: rest || undefined, verbose };
}

async function handle(line) {
  if (!line.trim()) return null;
  const r = parse(line);
  if (!r || !r.path.startsWith("/")) return 'usage: METHOD /path [body] [-i] [-H "Name: value"]';
  let res;
  try {
    res = await fetch(`http://localhost:${PORT}${r.path}`, {
      method: r.method, headers: r.headers, body: r.body, redirect: "manual", signal: AbortSignal.timeout(2000),
    });
  } catch (err) {
    if (err.name === "TimeoutError") return "(no response in 2 s: the server never finished its answer)";
    return `(no response: ${err.cause ? err.cause.message : err.message})`;
  }
  const out = [`${res.status} ${res.statusText}`];
  if (r.verbose) for (const [k, v] of res.headers) if (!HIDDEN.has(k)) out.push(`${k}: ${v}`);
  const text = await res.text();
  if (text) out.push(...(r.verbose ? ["", text] : [text]));
  return out.join("\n");
}

module.exports = { handle };
```

```ticket
  { id: 2, name: "Fern", water: "daily" },

];
```

```ticket
title: Route parameters
files: app.js
---brief
`GET /api/plants/2` should answer just the Fern. You can't write a route for every id, so Express routes can have **parameters**: in `/api/plants/:id`, the `:id` part matches any value, and the handler finds it in **`req.params.id`**.

Add:

- **`GET /api/plants/:id`**: the plant with that id. If there isn't one, answer **404** with `{"error": "Plant not found"}`: `res.status(404).json(...)`.
- **`GET /hello/:name`**: answers `Hello, Ada!` for `/hello/Ada`.

Careful: `req.params.id` is always a **string**, `"2"`, while the ids in your array are numbers. Turn it into a number before you compare.
---why
Paths that name a thing, `/api/plants/2`, are the heart of **REST**: every resource has its own URL. The status code is part of the answer, not decoration. A client checks for `404` before it reads the body, so a missing plant must never come back as `200` with an empty body. And the string-versus-number trap is real: `"2" === 2` is `false`, so `find` quietly finds nothing.

     found      ─▶ 200 {"id":2,"name":"Fern","water":"daily"}
     not found  ─▶ 404 {"error":"Plant not found"}
```

```ticket
id: t4
title: Query strings
files: app.js
---brief
Lists need filters. The part of a URL after `?` is the **query string**, and Express parses it into **`req.query`**: for `/api/plants?water=weekly&sort=name`, `req.query` is `{ water: "weekly", sort: "name" }`.

Make `GET /api/plants` understand three optional filters, in any combination:

| Query | Keeps |
|---|---|
| `?water=weekly` | plants with exactly that watering |
| `?search=c` | plants whose name contains the text, ignoring case |
| `?sort=name` | all of them, sorted by name A to Z |

With no query at all, it's the whole list in its usual order, as before.
---why
Filtering in the query string, not in the path, is the REST convention: `/api/plants` is still the one collection, and the query only narrows the view of it. Every filter is optional, so the code starts from the whole list and narrows it one step at a time. Sort a **copy** (`[...result]`): `sort` changes the array in place, and sorting `plants` itself would quietly reorder your data for every later request.
---picture
  GET /api/plants?water=daily&search=f

  plants ──water=daily──▶ [Fern] ──search "f"──▶ [Fern] ──no sort──▶ res.json
---todo
- `?water=` keeps an exact match
- `?search=` matches part of the name, ignoring case
- `?sort=name` sorts a copy by name
- No query: everything, in order
---solution app.js
// app.js: your first Express server. client.js starts it and sends it what you type in the terminal.
const express = require("express");

const app = express();

// the data: in memory for now, so it starts fresh every time the server does
const plants = [
  { id: 1, name: "Tulip", water: "weekly" },
  { id: 2, name: "Fern", water: "daily" },
  { id: 3, name: "Cactus", water: "monthly" },
];

app.get("/", (req, res) => {
  res.send("Hello from Express!");
});

app.get("/about", (req, res) => {
  res.send("Greenhouse: a small API about plants, built one ticket at a time.");
});

app.get("/hello/:name", (req, res) => {
  res.send(`Hello, ${req.params.name}!`);
});

// ?water=weekly  ?search=c  ?sort=name, in any combination
app.get("/api/plants", (req, res) => {
  let result = plants;
  if (req.query.water) result = result.filter((p) => p.water === req.query.water);
  if (req.query.search) {
    const text = req.query.search.toLowerCase();
    result = result.filter((p) => p.name.toLowerCase().includes(text));
  }
  if (req.query.sort === "name") result = [...result].sort((a, b) => a.name.localeCompare(b.name));
  res.json(result);
});

app.get("/api/plants/:id", (req, res) => {
  const plant = plants.find((p) => p.id === Number(req.params.id));
  if (!plant) return res.status(404).json({ error: "Plant not found" });
  res.json(plant);
});

app.get("/api/stats", (req, res) => {
  const byWater = {};
  for (const plant of plants) byWater[plant.water] = (byWater[plant.water] || 0) + 1;
  res.json({ count: plants.length, byWater });
});

app.listen(3000, () => console.log("Server running on http://localhost:3000"));
```

```ticket
id: t5
title: Create with POST
files: app.js
---brief
Now clients can add plants. `POST /api/plants {"name": "Rose", "water": "weekly"}` sends the new plant as JSON in the request **body**. Express doesn't read bodies until you ask: add **`app.use(express.json())`** near the top, and the parsed body appears in **`req.body`**.

Add **`POST /api/plants`**:

- Check the body before trusting it. If `name` isn't a non-empty string, answer **400** `{"error": "name is required"}`. If `water` isn't `daily`, `weekly` or `monthly`, answer **400** `{"error": "water must be daily, weekly or monthly"}`.
- Otherwise make the plant with the next id (4, then 5…) and the name trimmed, add it to `plants`, and answer **201 Created** with the plant and a **`Location`** header: `/api/plants/4`. `res.status(201).location(url).json(plant)` does all three.

A request with no body at all leaves `req.body` **undefined**, so read it as `req.body || {}`.
---why
**Never trust the body.** Anything can arrive: a missing field, a number where a string should be, a script. ---brief
```
```ticket
Look at the five plant routes: most of them start with the same three lines to find the plant, and three repeat the same checks. Express's answer to repeated code is **middleware**: a function `(req, res, next)` that does one job, then calls **`next()`** to hand the request on, or answers and stops.

- A **logger**, added with `app.use` before everything: when each response finishes (`res.on("finish", ...)`), `console.log` the method, URL and status, like `GET /api/plants/1 200`. Use `req.originalUrl`.
```

```ticket
---brief
Three things still go wrong in ways a client can't use:

- `POST /api/plants {"name": ` (broken JSON) gets Express's default 400 page, as plain text, in the middle of a JSON API.
- `GET /api/nothing` gets `Cannot GET /api/nothing`, also plain text.
- `GET /api/plants/abc` says `Plant not found`, when the real problem is that `abc` isn't an id at all.

Fix them with Express's error handling:

1. Write **`httpError(status, message)`**: it makes an `Error` with a `status` property. Now middleware can **`throw httpError(404, "Plant not found")`** instead of answering itself. Make `findPlant` throw `400 "id must be a number"` for an id that isn't digits, and the 404 for a missing plant. Make `validate` throw its 400.
2. After all the routes, **`app.use("/api", ...)`** answers anything left under `/api` with **404** `{"error": "No such route: GET /api/nothing"}`.

Throwing lets the code that finds the problem stop right there, and lets one place, the error handler, decide what every error looks like. That's how real APIs stay consistent. The 500 message is deliberately vague: the client can't fix your bug, and details like stack traces and SQL tell attackers about your internals, so they go to your logs instead. Express 5 also catches errors from `async` handlers, which Express 4 didn't. That's why `careTip` can fail without taking the server down.

  if (!/^\d+$/.test(req.params.id)) throw httpError(400, "id must be a number");
  req.plant = plants.find((p) => p.id === Number(req.params.id));
  if (!req.plant) throw httpError(404, "Plant not found");
  next();
}

// middleware factory: a check of the body, whole (POST, PUT) or partial (PATCH)
function validate(partial) {
  return (req, res, next) => {
    const bad = problem(req.body || {}, partial);
    if (bad) throw httpError(400, bad);
    next();
  };
}

app.use((err, req, res, next) => {
  if (err.type === "entity.parse.failed") return res.status(400).json({ error: "Invalid JSON" });
  const status = err.status || 500;
  if (status >= 500) console.error(`${req.method} ${req.originalUrl} failed: ${err.message}`);
```

## What a physics engine does

Every game with things that fall, bounce or swing runs the same loop, 60 times a second:

1. Work out the **forces** on every body (gravity, springs, contacts).
2. **Integrate**: turn forces into new velocities, and velocities into new positions, over a small time step `dt`.
3. Fix **collisions**: nothing may sink into the floor or into each other.

Step 2 sounds like one line of code. It isn't. The obvious version slowly *adds energy* that came from nowhere, until your bridge flies apart. Go and break one.

```quiz
- stays exactly the same, because the physics is right
- slowly drains away, like friction
* creeps up every step, so the motion grows until it explodes
- jumps randomly up and down
> Explicit Euler moves the ball using the velocity from the *start* of the step, so it always overshoots a little outward. Each step adds a sliver of energy, and the slivers compound.
```

## State, and one step of time

A body's **state** is where it is and how fast it's moving: `x` and `v`. A time step of length `dt` says: velocity moves the position, acceleration moves the velocity.

    x_new = x + v * dt
    v_new = v + a * dt

That's **explicit Euler**, the first thing everyone writes. For a falling ball, `a = -9.8` all the time.

```predict
x, v, dt = 10.0, 0.0, 0.5
for step in range(3):
    x, v = x + v * dt, v - 9.8 * dt
    print(step + 1, round(x, 2), round(v, 2))
```

Notice that in step 1 the ball didn't move at all: the position used the *old* velocity, 0. Euler is always one step behind.

## Springs, and the energy leak

A spring pulls back toward its rest position with force `-k * x` (Hooke's law), so the acceleration is `a = -k/m * x`. Its total energy is the kinetic energy plus the energy stored in the spring:

    E = ½ m v² + ½ k x²

A perfect simulation keeps `E` constant forever.


## The fix: update velocity first

Swap the order: update the velocity first, then move with the **new** velocity. This is **semi-implicit (symplectic) Euler**, and it's the integrator most game engines (Box2D, Unity's PhysX setup) use. It costs exactly the same, but its energy wobbles around the true value instead of drifting away.

```parsons
title: Semi-implicit Euler
---lines
def semi_step(x, v, k, m, dt):
    a = -k / m * x
    v = v + a * dt
    x = x + v * dt
    return x, v
?? x = x + v * dt * 0.5
---tests
x, v = semi_step(1.0, 0.0, 1.0, 1.0, 0.1)
assert abs(v + 0.1) < 1e-12 and abs(x - 0.99) < 1e-12, "velocity first, then the position moves with the new velocity"
```

```exercise
---hint
The only change from explicit Euler: the position uses the velocity you *just* computed.
```

**Verlet** goes one step further and doesn't store velocity at all. It remembers the previous position and uses `x_new = 2x - x_prev + a·dt²`. That's what cloth and ragdolls use, because it makes constraints (like "these two points stay 1 m apart") easy, as you'll see in the project.

```exercise
title: verlet_bug
kind: bug
---prompt
This Verlet step makes a spring grow without limit. One sign is wrong. Fix it.
---starter
def verlet_step(x, x_prev, k, m, dt):
    a = -k / m * x
    x_new = 2 * x - x_prev - a * dt * dt
    return x_new, x
---solution
def verlet_step(x, x_prev, k, m, dt):
    a = -k / m * x
    x_new = 2 * x - x_prev + a * dt * dt
    return x_new, x
---tests
x, xp = 1.0, 1.0
peak = 0
for _ in range(5000):
    x, xp = verlet_step(x, xp, 1.0, 1.0, 0.05)
    peak = max(peak, abs(x))
assert peak < 1.01, f"a spring released from x=1 should never go past 1; it reached {peak:.3g}"
---hint
Acceleration should push the position the same way it pushes the velocity: it's *added*.
```

## Bouncing off the ground

Integration lets things fall *through* the floor; the engine has to notice and fix it. When a ball (radius `r`) goes below the floor, put it back on the floor and flip its vertical velocity, losing some speed. The fraction kept is the **coefficient of restitution** `e`: 1 is a superball, 0 is a lump of clay.

```exercise
title: bounce
kind: write
---prompt
Write `bounce(y, vy, r, e)`: if the ball's centre is below `r` (it's poking into the floor at y=0), return `(r, -vy * e)` when it's moving down, or `(r, vy)` if it's already moving up. Otherwise return `(y, vy)` unchanged.
---starter
def bounce(y, vy, r, e):
    return y, vy
---solution
def bounce(y, vy, r, e):
    if y < r:
        return r, (-vy * e if vy < 0 else vy)
    return y, vy
---tests
assert bounce(0.1, -4.0, 0.3, 0.5) == (0.3, 2.0), "into the floor at speed 4 with e=0.5: back on the surface, going up at 2"
assert bounce(2.0, -4.0, 0.3, 0.5) == (2.0, -4.0), "in the air: nothing happens"
assert bounce(0.2, 1.0, 0.3, 0.5) == (0.3, 1.0), "already leaving the floor: don't flip it back down"
---hint
Why check the direction? If a ball is still overlapping the floor on the frame after a bounce, flipping again would send it back *into* the floor, and it would get stuck vibrating there.
```

## Two balls colliding

Two equal spheres collide when the distance between centres is less than `2r`. Resolving it takes two steps:

1. **Separate** them: push each one back by half the overlap, along the line between the centres (the **normal** `n`).
2. **Exchange momentum along the normal**: take the part of their relative velocity that points along `n`. If they're approaching, swap it. The sideways parts are untouched, which is why a glancing hit sends balls off at angles.

```exercise
title: collide
kind: write
---prompt
Write `collide(p1, v1, p2, v2, r)` for two equal-mass balls (numpy arrays). If `|p2 - p1| < 2r`: push them apart equally so they just touch, and if they're approaching (`(v1 - v2)·n > 0`, with `n` the unit vector from 1 to 2), move that component from ball 1 to ball 2 (`v1 -= vn*n; v2 += vn*n`). Return the four new arrays.
---starter
def collide(p1, v1, p2, v2, r):
    return p1, v1, p2, v2
---solution
def collide(p1, v1, p2, v2, r):
    d = p2 - p1
    dist = np.linalg.norm(d)
    if dist >= 2 * r or dist == 0:
        return p1, v1, p2, v2
    n = d / dist
    push = (2 * r - dist) / 2
    p1, p2 = p1 - push * n, p2 + push * n
    vn = np.dot(v1 - v2, n)
    if vn > 0:
        v1, v2 = v1 - vn * n, v2 + vn * n
    return p1, v1, p2, v2
---tests
a = np.array
p1, v1, p2, v2 = collide(a([0.0, 0.0]), a([1.0, 0.0]), a([0.5, 0.0]), a([-1.0, 0.0]), 0.3)
assert np.allclose(v1, [-1, 0]) and np.allclose(v2, [1, 0]), "head-on with equal masses: they swap velocities"
assert np.isclose(np.linalg.norm(p2 - p1), 0.6), "after separating they exactly touch (distance 2r)"
P1, V1, P2, V2 = collide(a([0.0, 0.0]), a([2.0, 1.0]), a([0.4, 0.3]), a([0.0, -1.0]), 0.3)
assert np.allclose(V1 + V2, [2.0, 0.0]), "momentum before = momentum after"
S = collide(a([0.0, 0.0]), a([-1.0, 0.0]), a([0.5, 0.0]), a([1.0, 0.0]), 0.3)
assert np.allclose(S[1], [-1, 0]), "balls already flying apart keep their velocities"
---hint
`n = d / dist`, then `vn = np.dot(v1 - v2, n)` is how fast they approach each other along the line of centres.
```

## Real-world project: a rope for a game

Ropes, chains, hair and cloth are all the same trick: lots of points moved by **Verlet**, plus **constraints** that keep neighbours a fixed distance apart. No spring forces at all, so nothing can explode, even with big time steps.

```project
title: A swinging rope bridge for a platformer game
client: A two-person indie studio making a jungle platformer
skills: Verlet integration, constraints, fixed time step, numpy arrays
---brief
The bridge is a chain of points. Each frame: move every point with Verlet under gravity, then run a few passes of **constraint solving**: for each pair of neighbours, move both points so they're exactly the rest length apart. The two end points are pinned to the cliffs. Then let the player's weight pull down on one point and watch the bridge sag and swing.
---why
This is Jakobsen's method from the game *Hitman: Codename 47*, and it's still how most games do ropes, cloth, ragdolls and soft bodies, because it's fast and never blows up. "Solve constraints a few times per frame" (position-based dynamics) is also what PhysX and Unity's cloth use under the hood.
---milestones
- Store the rope as two arrays: positions and previous positions
- Write the Verlet step for every point at once with numpy
- Write `satisfy(points, rest, pinned, iters)` to enforce segment lengths
- Pin both ends and add a heavy point where the player stands
- Animate it with `flipbook` or matplotlib and tune the number of iterations
---stretch
- Let segments break when stretched too far (a snapping bridge)
- Turn the chain into a grid of points: that's cloth
- Add wind as a small random sideways force
```

```exercise
title: satisfy
kind: write
---prompt
Write `satisfy(pts, rest, iters=20)`: `pts` is an `(n, 2)` array of rope points, point 0 is **pinned** (never moves). For `iters` passes, for each segment `i → i+1`: find the current length, and move the two points along the segment so its length becomes `rest`: each moves half the error, except a pinned point, whose share goes entirely to the other one. Return the array.
---starter
def satisfy(pts, rest, iters=20):
    pts = pts.copy()
    return pts
---solution
def satisfy(pts, rest, iters=20):
    pts = pts.copy()
    for _ in range(iters):
        for i in range(len(pts) - 1):
            d = pts[i + 1] - pts[i]
            L = np.linalg.norm(d)
            if L == 0:
                continue
            fix = (L - rest) / L * d
            if i == 0:
                pts[i + 1] -= fix
            else:
                pts[i] += fix / 2
                pts[i + 1] -= fix / 2
    return pts
---tests
rng = np.random.default_rng(0)
pts = np.cumsum(rng.normal(0, 1, (10, 2)), axis=0)
out = satisfy(pts, 0.5, iters=200)
lengths = np.linalg.norm(np.diff(out, axis=0), axis=1)
assert np.allclose(lengths, 0.5, atol=1e-3), f"every segment should end up the rest length 0.5; got {lengths.round(3)}"
assert np.allclose(out[0], pts[0]), "the pinned point must not move"
---hint
`fix = (L - rest) / L * d` is the vector by which the segment is too long. Split it between the two ends.
---show
n, rest, dt = 20, 0.25, 1 / 60
pts = np.array([[i * rest, 0.0] for i in range(n)])
prev = pts.copy()
frames = []
for t in range(240):
    vel = pts - prev
    prev = pts.copy()
    pts = pts + vel + np.array([0, -9.8]) * dt * dt
    pts = satisfy(pts, rest, iters=10)
    if t % 4 == 0:
        img = np.zeros((60, 60))
        for x, y in pts:
            img[int(np.clip(-y * 10, 0, 59)), int(np.clip(x * 10 + 5, 0, 59))] = 1
        frames.append(img)
print("A rope pinned at one end, swinging down under YOUR satisfy():")
flipbook(frames, cmap="Greys", fps=15)
```

## Rebuild it and explain it

```exercise
title: simulate_ball
kind: rebuild
---prompt
From memory: write `simulate_ball(y0, steps, dt, r=0.1, e=0.8)`: a ball dropped from height `y0` with gravity 9.8, stepped with **semi-implicit Euler**, bouncing off the floor with restitution `e`. Return the list of heights after each step.
---starter
def simulate_ball(y0, steps, dt, r=0.1, e=0.8):
    return []
---solution
def simulate_ball(y0, steps, dt, r=0.1, e=0.8):
    y, v, out = y0, 0.0, []
    for _ in range(steps):
        v -= 9.8 * dt
        y += v * dt
        if y < r and v < 0:
            y, v = r, -v * e
        out.append(y)
    return out
---tests
hs = simulate_ball(2.0, 2000, 0.005)
assert len(hs) == 2000, "one height per step"
assert min(hs) >= 0.1 - 1e-9, "the ball never sinks into the floor"
first_peak = max(hs[150:330])
assert 1.0 < first_peak < 2.0 * 0.8 ** 2 + 0.15, f"each bounce keeps e^2 of the height: after one bounce it should peak near {2 * 0.64:.2f}, got {first_peak:.2f}"
---hint
Velocity first, then position, then the floor check.
```

```recall
Q: Why do game engines use semi-implicit Euler or Verlet instead of the "obvious" explicit Euler, even though they cost the same?
A: Explicit Euler moves bodies with the velocity from the start of the step, so on anything that oscillates (springs, orbits, pendulums) it always overshoots outward and adds a little energy each step. The error compounds until the simulation explodes. Updating the velocity first (semi-implicit) or using positions directly (Verlet) makes the error oscillate around the true energy instead of drifting, so the simulation stays stable for as long as you run it, with the same work per step.
```

```puzzle

---why

```

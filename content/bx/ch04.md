```prelude
OPS = {"+": "ADD", "-": "SUB", "*": "MUL", "<": "LT", "<=": "LE"}

def ref_compile_expr(node, code):
    if node[0] == "num":
        code.append(("PUSH", node[1]))
    elif node[0] == "var":
        code.append(("LOAD", node[1]))
    else:
        ref_compile_expr(node[2], code)
        ref_compile_expr(node[3], code)
        code.append((OPS[node[1]],))

def ref_run(code):
    pc, stack, env, out = 0, [], {}, []
    while True:
        op = code[pc]
        pc += 1
        name = op[0]
        if name == "PUSH":
            stack.append(op[1])
        elif name == "LOAD":
            stack.append(env[op[1]])
        elif name == "STORE":
            env[op[1]] = stack.pop()
        elif name == "PRINT":
            out.append(stack.pop())
        elif name == "JUMP":
            pc = op[1]
        elif name == "JUMP_IF_FALSE":
            if not stack.pop():
                pc = op[1]
        elif name == "HALT":
            return out
        else:
            b, a = stack.pop(), stack.pop()
            if name == "ADD":
                stack.append(a + b)
            elif name == "SUB":
                stack.append(a - b)
            elif name == "MUL":
                stack.append(a * b)
            elif name == "LT":
                stack.append(a < b)
            else:
                stack.append(a <= b)
```

## From a calculator to a language

The calculator in chapter 2 turned `2+3*4` into a tree and walked it to get one number. Add three things and you have a real (tiny) programming language:

1. **variables**: `x = 3` remembers a value under a name;
2. **statements**: things that *do* something (assign, print) rather than produce a value;
3. **control flow**: `while` repeats statements while a condition holds.

There are two classic ways to run that. A **tree-walking interpreter** visits the tree directly, every time. A **compiler + virtual machine** first flattens the tree into a list of tiny instructions (**bytecode**), then a simple loop runs the list. Python does the second: `import dis; dis.dis(f)` shows you a function's bytecode. Watch one run before building either.

## Programs as trees

We'll skip the parser (you built one in chapter 2) and write program trees directly as tuples:

- expressions: `("num", 3)`, `("var", "x")`, `("bin", "+", left, right)` with `+ - * < <=`;
- statements: `("set", "x", expr)`, `("print", expr)`, `("while", cond, [statements])`.

So `x = 3; print(x * x)` is `[("set", "x", ("num", 3)), ("print", ("bin", "*", ("var", "x"), ("var", "x")))]`.

```exercise
def evaluate(node, env):
    kind = node[0]
    if kind == "num":
        return node[1]
    if kind == "var":
```

```exercise
---solution
def execute(stmts, env, out):
    for s in stmts:
        if s[0] == "set":

        elif s[0] == "print":
```

That's a working interpreter in about 20 lines. Its weakness: every time the loop goes round, it walks the same tree nodes again, checks their kinds again, follows the same pointers again. For a loop that runs a million times, that's a million re-walks.

## Flattening into bytecode

A **stack machine** needs no tree. To compute `a + b`, push `a`, push `b`, then `ADD` pops both and pushes the sum. So compiling an expression is a **post-order walk**: children first, then the operator. The order of instructions now *is* the order of evaluation; precedence was settled by the tree's shape.

## The virtual machine

The VM is one loop: fetch the instruction at the **program counter** (pc), move pc on by one, then do what the instruction says. Jumps are the only instructions that set pc to something else.

## Compiling a while loop

A `while` loop becomes: the test, a `JUMP_IF_FALSE` to "after the loop", the body, and a `JUMP` back to the test. The catch: when you emit the `JUMP_IF_FALSE`, you don't know yet where "after the loop" is. So emit it with a placeholder and **patch** it once the body is compiled. Every real compiler does this (it's called backpatching).


## Why bother with bytecode?

The tree-walker and the VM print the same thing, so why do CPython, the JVM, Lua and JavaScript engines all compile to bytecode?

- **No re-walking**: the tree is flattened once; the loop body is just a range of addresses run again and again.
- **Small, simple steps**: one `if` per instruction instead of recursion and tuple-unpacking per node.
- **A target for optimisation**: constant folding, peephole rewrites and JIT compilers all work on flat instruction lists.
- **Portable**: the same bytecode runs anywhere a VM exists (that was Java's whole pitch).

```quiz
Why does `ADD` need no operands, while `PUSH` and `LOAD` do?
- ADD is implemented in hardware
* ADD always takes its inputs from the top of the stack, so there's nothing to name; PUSH and LOAD bring new values in from outside the stack
- Operands are stored in a separate table
- It's an arbitrary design choice
> That's the stack machine's big trade: instructions are tiny and the compiler never has to allocate registers, at the cost of more instructions shuffling values on and off the stack. Register machines (Lua 5, Dalvik) make the opposite trade.
```

```recall
Q: Explain the difference between a tree-walking interpreter and a bytecode VM, and how a while loop becomes bytecode.
A: A tree-walking interpreter runs a program by recursively visiting its syntax tree every time code executes: evaluate the children, combine them. A compiler instead walks the tree once and emits a flat list of small instructions; a VM then runs that list with a program counter and a stack (fetch, advance, dispatch), which avoids re-walking the tree and is easy to optimise. A while loop compiles to: the condition's instructions, a JUMP_IF_FALSE to just after the loop, the body, and a JUMP back to the condition. The exit target isn't known when the JUMP_IF_FALSE is emitted, so it gets a placeholder that's patched after the body and the backwards jump are emitted.
```

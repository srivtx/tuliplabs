## Who frees the memory?

In C you call `free()` yourself: forget and you leak, free too early and you crash. In Python, Java, JavaScript and Go, you never free anything. A **garbage collector** does it for you. Its whole job rests on one idea:

> An object the program can no longer **reach** can never be used again, so its memory can be reused.

"Reach" starts from the **roots**: the variables on the stack, plus globals. Follow references from there, and everything you touch is alive. Everything else is garbage.

There are two classic ways to find it. Try both:


```quiz
After deleting `tmp` under reference counting, why did the two nodes stay in memory?
- Reference counting is buggy in this simulation
- They were still reachable from `user`
* They point at each other, so each has a count of 1, even though nothing reachable points at them
- Freeing objects is slow, so it's postponed
> Counting only sees "how many arrows point here", not "can the program get here". A cycle keeps every count above zero. Tracing from the roots asks the right question.
```

## A heap you can hold in your hands

In the exercises a heap is a dict mapping an object's id to the list of ids it references, and the roots are a list of ids:

    heap  = {"user": ["name"], "name": [], "n1": ["n2"], "n2": ["n1"]}
    roots = ["user"]

Here `n1` and `n2` are an unreachable cycle.

```exercise
title: reachable
kind: write
---prompt
Write `reachable(heap, roots)` returning the set of ids reachable from the roots by following references. References to ids that aren't in the heap should be ignored.
---starter
def reachable(heap, roots):
    return set()
---solution
def reachable(heap, roots):
    seen, todo = set(), list(roots)
    while todo:
        k = todo.pop()
        if k in seen or k not in heap:
            continue
        seen.add(k)
        todo.extend(heap[k])
    return seen
---tests
heap = {"user": ["name"], "name": [], "n1": ["n2"], "n2": ["n1"]}
assert reachable(heap, ["user"]) == {"user", "name"}, "the cycle isn't reachable"
assert reachable(heap, ["user", "n2"]) == {"user", "name", "n1", "n2"}, "a root into the cycle keeps both alive"
assert reachable({"a": ["a"]}, ["a"]) == {"a"}, "a self-reference must not loop forever"
assert reachable({}, []) == set(), "empty"
---hint
A graph traversal: a `todo` list starting with the roots, and a `seen` set so cycles don't loop forever.
```

## Mark and sweep

1. **Mark**: from every root, traverse references and mark each object you reach.
2. **Sweep**: go through the whole heap and free every object that isn't marked.

That's the whole algorithm. Cycles are no problem: if nothing reachable points into a cycle, nobody marks it.

```parsons
title: The mark phase, with an explicit stack
---lines
def mark(heap, roots):
    marked = set()
    stack = list(roots)
    while stack:
        obj = stack.pop()
        if obj in marked:
            continue
        marked.add(obj)
        for child in heap[obj]:
            stack.append(child)
    return marked
?? marked.add(child)
---tests
heap = {"a": ["b"], "b": ["c", "a"], "c": [], "d": ["d"]}
assert mark(heap, ["a"]) == {"a", "b", "c"}
assert mark(heap, []) == set()
```

Why an explicit stack instead of recursion? A collector often runs exactly when memory is tight, and a long linked list would need one recursive call per node. Real collectors avoid deep recursion for the same reason.

```exercise
title: mark_and_sweep
kind: write
---prompt
Write `mark_and_sweep(heap, roots)` that removes every unreachable object from `heap` **in place** and returns the set of ids it freed. `reachable` is provided.
---setup
def reachable(heap, roots):
    seen, todo = set(), list(roots)
    while todo:
        k = todo.pop()
        if k in seen or k not in heap:
            continue
        seen.add(k)
        todo.extend(heap[k])
    return seen
---starter
def mark_and_sweep(heap, roots):
    return set()
---solution
def mark_and_sweep(heap, roots):
    live = reachable(heap, roots)
    freed = {k for k in heap if k not in live}
    for k in freed:
        del heap[k]
    return freed
---tests
heap = {"user": ["name"], "name": [], "n1": ["n2"], "n2": ["n1"], "old": []}
assert mark_and_sweep(heap, ["user"]) == {"n1", "n2", "old"}, "frees the cycle and the orphan"
assert heap == {"user": ["name"], "name": []}, "the heap is changed in place"
assert mark_and_sweep(heap, ["user"]) == set(), "running again frees nothing"
---hint
Mark with `reachable`, then collect the unmarked ids into a set **before** deleting (you can't delete from a dict while looping over it).
```

## Reference counting

The other approach: every object keeps a **count** of references pointing at it. Creating a reference adds one; removing one subtracts one. When a count hits zero, free the object at once, and since its own references disappear too, decrement each of its children's counts, which may free them as well (a cascade).

The good: memory comes back the instant it's garbage, with no pauses. The bad: every assignment does extra work, and cycles leak.

```exercise
title: refcounts
kind: write
---prompt
Write `refcounts(heap, roots)` returning a dict from every id in the heap to how many references point at it: one for each time it appears in `roots`, plus one for each time it appears in any object's reference list.
---starter
def refcounts(heap, roots):
    return {}
---solution
def refcounts(heap, roots):
    counts = {k: 0 for k in heap}
    for r in roots:
        counts[r] += 1
    for refs in heap.values():
        for k in refs:
            counts[k] += 1
    return counts
---tests
heap = {"cart": ["i1", "i2"], "i1": ["p"], "i2": ["p"], "p": [], "n1": ["n2"], "n2": ["n1"]}
assert refcounts(heap, ["cart"]) == {"cart": 1, "i1": 1, "i2": 1, "p": 2, "n1": 1, "n2": 1}, "the unreachable cycle still counts 1 each"
---hint
Start every count at 0, then add one per appearance in `roots` and per appearance in each reference list.
```

```exercise

kind: bug
---prompt
`RcHeap.decref(k)` should lower `k`'s count and, if it reaches zero, free `k` **and release its references** (which may free more). Right now deleting the cart frees only the cart, and its items stay in memory forever. Fix it.
---starter
class RcHeap:
    def __init__(self, heap, roots):

        for r in roots:

---solution
class RcHeap:
    def __init__(self, heap, roots):
        self.heap = heap
        self.count = {k: 0 for k in heap}
        for r in roots:
            self.count[r] += 1
        for refs in heap.values():
            for k in refs:
                self.count[k] += 1

    def decref(self, k):
        self.count[k] -= 1
        if self.count[k] == 0:
            children = self.heap.pop(k)
            for child in children:
                self.decref(child)
---tests
h = RcHeap({"cart": ["i1", "i2"], "i1": ["p"], "i2": ["p"], "p": []}, ["cart"])
h.decref("cart")
assert h.heap == {}, f"everything should cascade away, left: {sorted(h.heap)}"
h = RcHeap({"a": ["b"], "b": [], "c": ["b"]}, ["a", "c"])
h.decref("a")
assert sorted(h.heap) == ["b", "c"], "b is still referenced by c, so it stays"
h = RcHeap({"t": ["n1"], "n1": ["n2"], "n2": ["n1"]}, ["t"])
h.decref("t")
assert sorted(h.heap) == ["n1", "n2"], "and the classic leak: the cycle survives"
---hint
When an object dies, the references **it** held die with it. Each of those children should get a `decref` too.
```

Python itself does reference counting, so you can watch a cycle survive and then be rescued by its backup cycle collector, `gc`:

```predict
import gc, weakref

class Node:
    pass

a, b = Node(), Node()
a.other, b.other = b, a      # a cycle
alive = weakref.ref(a)       # watches a without keeping it alive
del a, b
print(alive() is not None)   # still in memory?
gc.collect()
print(alive() is not None)
```

## The trade-offs real collectors make

- **Pauses.** A simple mark & sweep stops the program while it traces. Modern collectors (Go, Java's ZGC) trace *concurrently*, in small steps, with clever bookkeeping so the running program can't hide an object from them.
- **Generations.** Most objects die young: temporary lists, strings in a loop. So collectors keep a small **young generation** that's scanned often and cheaply, and promote survivors to an old generation that's scanned rarely. Python's `gc` has three generations.
- **Compaction.** Sweeping leaves holes. A **copying** collector moves live objects next to each other, which makes allocation as cheap as bumping a pointer.

```quiz
Why does a generational collector scan the young generation more often than the old one?
* Most objects die soon after they're created, so scanning young objects frees the most memory for the least work
- Old objects are read-only
- Young objects are smaller
- The old generation can't contain garbage
> This is the *generational hypothesis*, and it holds remarkably well in practice. Survivors of a few young collections are probably long-lived (caches, config, the main data structures), so checking them often would be wasted effort.
```

## Real-world project: a memory leak finder

```project
title: A leak finder for a long-running server
client: A small team whose web server's memory grows every hour until it crashes overnight
skills: graph traversal, reachability, heap snapshots, reporting
---brief
Write a tool that takes a heap snapshot (objects with ids, sizes in bytes, and references) plus the list of roots, and answers: how much memory is live, which objects are garbage, and for each root, its **retained size**: how many bytes would be freed if that root disappeared. Run it on two snapshots taken an hour apart and report which root's retained size grew: that's your leak.
---why
This is exactly what the Memory tab in Chrome DevTools, Python's `tracemalloc` and Java's heap analysers do. Leaks in garbage-collected languages are almost never "the GC failed"; they're "something reachable is still holding on", like a cache or a list of event listeners that only ever grows. Retained size points straight at the culprit.
---milestones
- Load a snapshot and compute total and reachable bytes
- `retained_size` for one root (the exercise below)
- A report of every root sorted by retained size
- A diff between two snapshots showing which roots grew
- Test it on a planted leak: a global cache that never evicts
---stretch
- Shortest path from a root to a given object ("why is this alive?")
- Group objects by type and show counts per type
- A dominator tree, the structure real heap analysers use
```

```exercise
title: retained_size
kind: write
---prompt
Write `retained_size(heap, sizes, roots, root)`: the number of bytes that would be freed if `root` were removed from `roots`. That's the total size of what's reachable from all roots, minus the total size of what's reachable from the others. `reachable` is provided.
---setup
def reachable(heap, roots):
    seen, todo = set(), list(roots)
    while todo:
        k = todo.pop()
        if k in seen or k not in heap:
            continue
        seen.add(k)
        todo.extend(heap[k])
    return seen
---starter
def retained_size(heap, sizes, roots, root):
    return 0
---solution
def retained_size(heap, sizes, roots, root):
    everything = reachable(heap, roots)
    others = reachable(heap, [r for r in roots if r != root])
    return sum(sizes[k] for k in everything - others)
---tests
heap = {"cache": ["e1", "e2"], "e1": [], "e2": ["blob"], "blob": [], "app": ["cfg", "e1"], "cfg": []}
sizes = {"cache": 16, "e1": 100, "e2": 100, "blob": 5000, "app": 16, "cfg": 200}
roots = ["cache", "app"]
assert retained_size(heap, sizes, roots, "cache") == 16 + 100 + 5000, "e1 is shared with app, so cache doesn't retain it"
assert retained_size(heap, sizes, roots, "app") == 16 + 200, "app retains itself and cfg"
assert retained_size(heap, sizes, ["cache"], "cache") == 5216, "the only root retains everything it reaches"
---hint
Compute two reachable sets: with all roots, and with every root except this one. The difference is what only this root keeps alive.
```

## Rebuild it and explain it

```exercise
title: collect_rebuild
kind: rebuild
---prompt
From memory: write `collect(heap, roots)` that performs mark and sweep in place on a heap dict (id → list of referenced ids) and returns the number of objects freed.
---starter
def collect(heap, roots):
    pass
---solution
def collect(heap, roots):
    marked, stack = set(), list(roots)
    while stack:
        k = stack.pop()
        if k in marked or k not in heap:
            continue
        marked.add(k)
        stack.extend(heap[k])
    dead = [k for k in heap if k not in marked]
    for k in dead:
        del heap[k]
    return len(dead)
---tests
heap = {"a": ["b"], "b": [], "c": ["d"], "d": ["c"]}
assert collect(heap, ["a"]) == 2 and sorted(heap) == ["a", "b"], "the c-d cycle is freed"
assert collect(heap, []) == 2 and heap == {}, "no roots: everything is garbage"
---hint
Mark with a stack and a set; then list the unmarked ids before deleting them.
```

```recall
Q: Explain how a garbage collector decides what to free, and compare reference counting with mark and sweep.
A: An object is alive if the program can reach it by following references from the roots: variables on the stack and globals. Anything unreachable can never be used again, so its memory can be reclaimed. Reference counting stores a count of incoming references on each object and frees it the moment the count hits zero, cascading to its children; it's immediate and needs no pauses, but every assignment costs a little, and cycles leak because their counts never reach zero. Mark and sweep traces from the roots, marking everything reachable, then sweeps the heap and frees whatever wasn't marked; it handles cycles naturally but has to pause or run concurrently with the program. Real systems combine ideas: Python uses reference counting plus a cycle collector; Java and Go use tracing collectors, often generational because most objects die young, and sometimes copying to compact memory.
```

## The two lies an OS tells

Your laptop runs hundreds of programs on a handful of CPU cores, and each program believes two things that aren't true:

1. **"I have the CPU to myself."** In fact the OS **scheduler** hands out the CPU in slices of a few milliseconds, switching between programs so fast it looks simultaneous.
2. **"I have all the memory to myself, starting at address 0."** In fact the OS and the hardware **translate** every address a program uses into a real location, through a **page table** per program.

These two illusions are most of what an operating system is. This chapter builds both.

## Who runs next?

Five processes share one CPU. Two of them are keypresses: tiny jobs that someone is waiting on.

```quiz
Shortest-remaining-first had the lowest average waiting time. Why doesn't a real OS just use it?
- It causes too many context switches
* It needs to know how long each job will run, which the OS can't know in advance, and long jobs can starve
- It only works with one CPU
- It makes keypresses slower
> It's provably optimal for average waiting, but it needs the future. Real schedulers *estimate* it (a process that used little CPU recently probably will again), and add rules so long jobs eventually get their turn.
```

A process here is a tuple `(name, arrives_at_tick, ticks_of_work)`. A **timeline** is a list with one entry per tick: the name of the process on the CPU, or `None` when it's idle.

```exercise
title: fifo
kind: write
---prompt
Write `fifo(jobs)` returning the timeline under **first come, first served**: when the CPU is free, it takes the process that arrived earliest (ties: list order) and runs it to completion. If nothing has arrived yet, the tick is `None`. Stop once every process is done.
---starter
def fifo(jobs):
    return []
---solution
def fifo(jobs):
    rem = {n: b for n, a, b in jobs}
    queue, out, cur, t = [], [], None, 0
    while any(rem.values()):
        for n, a, b in jobs:
            if a == t:
                queue.append(n)
        if cur is None or rem[cur] == 0:
            cur = queue.pop(0) if queue else None
        out.append(cur)
        if cur is not None:
            rem[cur] -= 1
        t += 1
    return out
---tests
jobs = [("A", 0, 3), ("B", 1, 2), ("C", 2, 1)]
assert fifo(jobs) == ["A", "A", "A", "B", "B", "C"], fifo(jobs)
assert fifo([("A", 0, 1), ("B", 3, 1)]) == ["A", None, None, "B"], "idle ticks are None"
---hint
Keep a ready queue (a list). Each tick: add the processes arriving now to its back; if nothing is running (or the running one is done), take the front; record who runs; subtract one tick of work.
```

**Round robin** gives each process a **time slice** of `q` ticks. When the slice is used up, the process goes to the back of the queue, even if it isn't finished. That's what kept the keypresses responsive.

```exercise
title: round_robin
kind: write
---prompt
Write `round_robin(jobs, q)`. Each tick, in this order: (1) processes arriving this tick join the back of the queue, in list order; (2) if the running process has finished it leaves, or if it has run `q` ticks in a row it goes to the back of the queue; (3) if nothing is running, take the front of the queue; (4) record who runs (or `None`) and do one tick of its work.
---starter
def round_robin(jobs, q):
    return []
---solution
def round_robin(jobs, q):
    rem = {n: b for n, a, b in jobs}
    queue, out, cur, used, t = [], [], None, 0, 0
    while any(rem.values()):
        for n, a, b in jobs:
            if a == t:
                queue.append(n)
        if cur is not None and (rem[cur] == 0 or used == q):
            if rem[cur] > 0:
                queue.append(cur)
            cur = None
        if cur is None and queue:
            cur, used = queue.pop(0), 0
        out.append(cur)
        if cur is not None:
            rem[cur] -= 1
            used += 1
        t += 1
    return out
---tests
jobs = [("A", 0, 3), ("B", 1, 2), ("C", 2, 1)]
assert round_robin(jobs, 1) == ["A", "B", "A", "C", "B", "A"], round_robin(jobs, 1)
assert round_robin(jobs, 2) == ["A", "A", "B", "B", "C", "A"], round_robin(jobs, 2)
assert round_robin(jobs, 100) == ["A", "A", "A", "B", "B", "C"], "a huge slice is just FIFO"
assert round_robin([("A", 0, 1), ("B", 3, 1)], 2) == ["A", None, None, "B"], "idle ticks"
---hint
Track the running process `cur` and how many ticks in a row it has run (`used`). Reset `used` to 0 whenever a new process takes the CPU.
---hint
Order matters: new arrivals join the queue **before** a preempted process goes to the back.
```

Write `waiting_times(jobs, timeline)` returning a dict from name to **waiting time**: finish tick − arrival − work, where the finish tick is one past the last tick it ran.

        if name is not None:

    return {n: finish[n] - a - b for n, a, b in jobs}
---tests

```quiz
Why not make the time slice tiny, say one microsecond?
- The CPU can't count that fast
* Every switch costs time (saving and loading registers, cold caches), so with tiny slices the CPU spends most of its time switching instead of working
- Programs would run out of memory
- It would make keypresses slower
> A context switch costs a few microseconds of pure overhead plus slower code afterwards, because the caches are full of the previous process's data. Real slices are a few milliseconds: short enough to feel instant to a human, long enough that switching is a small fraction of the time.
```

## Virtual memory: every program gets its own address 0

Programs use **virtual addresses**. The OS splits memory into **pages** (usually 4096 bytes) and keeps a **page table** per process mapping each virtual page number to a physical **frame**. The hardware translates every single memory access:

    virtual address  →  (page number, offset inside the page)
    physical address =  page_table[page] * page_size + offset

So two programs can both use address 1000 and never touch each other's data: their page tables point to different frames. If a page isn't in the table, the hardware raises a **page fault** and the OS steps in: maybe to load the page from disk, maybe to kill a program that touched memory it doesn't own (a "segmentation fault").

## When memory is full: page replacement

There are more pages than physical frames, so some pages live on disk. On a fault with every frame full, the OS must **evict** one page. Which one? Two classic answers:

- **FIFO**: evict the page that was loaded longest ago.
- **LRU** (least recently used): evict the page that hasn't been *used* for the longest time. Pages you used recently, you'll probably use again soon.

```exercise
title: fifo_faults
kind: write
---prompt
Write `fifo_faults(refs, frames)`: given a list of page numbers in the order they're used, and the number of frames, return how many page faults FIFO replacement causes. Memory starts empty, and loading a page into an empty frame counts as a fault too.
---starter
def fifo_faults(refs, frames):
    return 0
---solution
def fifo_faults(refs, frames):
    mem, faults = [], 0
    for p in refs:
        if p in mem:
            continue
        faults += 1
        if len(mem) == frames:
            mem.pop(0)
        mem.append(p)
    return faults
---tests
assert fifo_faults([1, 2, 3, 1, 2, 3], 3) == 3, "everything fits: only the first loads fault"
assert fifo_faults([1, 2, 3, 1, 2, 3], 2) == 6, "two frames, three pages in a cycle: every access faults"
refs = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
assert fifo_faults(refs, 3) == 9 and fifo_faults(refs, 4) == 10, "Belady's anomaly: more frames, more faults"
---hint
Keep memory as a list in load order. On a hit, do nothing. On a miss, count it, drop `mem[0]` if full, and append.
```

That last test is famous: with FIFO, **adding memory made things worse** (Belady's anomaly). LRU never does that, which is one reason real systems approximate it.

```exercise
title: lru_bug
kind: bug
---prompt
This `lru_faults` is supposed to evict the **least recently used** page, but it behaves exactly like FIFO. Fix it.
---starter
def lru_faults(refs, frames):

            continue

---solution
def lru_faults(refs, frames):
    mem, faults = [], 0
    for p in refs:
        if p in mem:
            mem.remove(p)
            mem.append(p)
            continue
        faults += 1
        if len(mem) == frames:
            mem.pop(0)
        mem.append(p)
    return faults
---tests
assert lru_faults([1, 2, 1, 3, 1, 4], 2) == 4, "1 is used constantly, so LRU keeps it"
refs = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
assert lru_faults(refs, 3) == 10 and lru_faults(refs, 4) == 8, "LRU: more frames never hurts"
---hint
The list should be ordered by **last use**, not by load time. What should happen to a page's position when it's used again?
---hint
On a hit, move the page to the end: `mem.remove(p)` then `mem.append(p)`.
```

## Sharing is dangerous: race conditions

The scheduler can switch processes **between any two instructions**. Say two processes each add 1 to a shared counter with three steps: read it, add 1, write it back. Here's one possible interleaving, written out by hand:

```predict
counter = 0
a = counter     # process 1 reads
b = counter     # switch! process 2 reads
a = a + 1
b = b + 1
counter = a     # process 1 writes
counter = b     # process 2 writes
print(counter)
```

Two increments, but the counter only went up by one: an update was **lost**. It only happens with unlucky timing, so it's the kind of bug that passes every test and then breaks in production. The fix is a **lock** (mutex): an OS-provided way to say "only one process may run these lines at a time". Locks need help from the hardware: an atomic instruction like *compare-and-swap*, which reads and writes in one step that can't be interrupted.

## Real-world project: a toy kernel

```project
title: A process simulator for an OS course
client: A university lecturer who wants students to experiment with schedulers without writing C
skills: queues, simulation, scheduling policies, page tables, measuring trade-offs
---brief
Build a small simulated kernel in Python. Processes are scripts of steps like `("cpu", 3)`, `("io", 5)` (wait for the disk) and `("touch", page)`. The kernel runs a scheduler (pluggable: FIFO, round robin, priority), moves processes between **ready**, **running** and **blocked** while they wait for I/O, keeps a page table per process with LRU replacement, and prints a timeline plus statistics at the end.
---why
Real kernels are huge, but every one of them has this loop at its core: pick a process, run it until it finishes, blocks or its slice ends, handle what happened, repeat. Building it once makes words like "context switch", "blocked on I/O" and "thrashing" concrete.
---milestones
- A `Kernel` with `spawn` and `tick` running round robin (the exercise below)
- I/O steps: a process waiting on the disk is **blocked** and isn't scheduled; it rejoins the queue when the I/O completes
- Statistics: waiting time, response time, CPU utilisation, context switches
- A page table per process with a fixed number of frames and LRU eviction, counting page faults
- A comparison report: the same workload under three schedulers
---stretch
- A multi-level feedback queue: processes that use their whole slice drop to a lower priority
- Two CPU cores
- Show thrashing: give processes more pages than fit, and watch useful work collapse
```

```exercise
title: Kernel
kind: write
---prompt
Write a class `Kernel(q=2)` with `spawn(name, work)` (the process joins the back of the ready queue) and `tick()`, which runs one tick of round robin and returns the name of the process that ran, or `None` if nothing is ready. A process that has run `q` ticks in a row goes to the back of the queue before the next one is picked. When a process finishes, append its name to `self.exited`.
---starter
class Kernel:
    def __init__(self, q=2):
        self.exited = []

    def spawn(self, name, work):
        pass

    def tick(self):
        return None
---solution
class Kernel:
    def __init__(self, q=2):
        self.q, self.ready, self.rem = q, [], {}
        self.cur, self.used, self.exited = None, 0, []

    def spawn(self, name, work):
        self.rem[name] = work
        self.ready.append(name)

    def tick(self):
        if self.cur is not None and self.used == self.q:
            self.ready.append(self.cur)
            self.cur = None
        if self.cur is None:
            if not self.ready:
                return None
            self.cur, self.used = self.ready.pop(0), 0
        name = self.cur
        self.rem[name] -= 1
        self.used += 1
        if self.rem[name] == 0:
            self.exited.append(name)
            self.cur = None
        return name
---tests
k = Kernel(2)
k.spawn("A", 3); k.spawn("B", 2)
assert [k.tick() for _ in range(6)] == ["A", "A", "B", "B", "A", None], "round robin with a slice of 2"
assert k.exited == ["B", "A"], "B finished first"
k = Kernel(2)
k.spawn("A", 4)
seq = [k.tick()]
k.spawn("B", 1)
seq += [k.tick() for _ in range(5)]
assert seq == ["A", "A", "B", "A", "A", None], seq
---hint
Keep `cur` (running process), `used` (ticks in a row) and `rem` (work left per name). At the start of `tick`, preempt if the slice is used up; then, if nothing is running, take the front of the queue.
---hint
When the process's work reaches 0, record it in `exited` and set `cur` to `None` so the next tick picks someone else.
```

## Rebuild it and explain it

```exercise
title: finish_order
kind: rebuild
---prompt
From memory: every job in `jobs` (a list of `(name, work)`) arrives at time 0. Under round robin with slice `q`, return the names in the order they **finish**.
---starter
def finish_order(jobs, q):
    pass
---solution
def finish_order(jobs, q):
    queue, order = list(jobs), []
    while queue:
        name, left = queue.pop(0)
        if left <= q:
            order.append(name)
        else:
            queue.append((name, left - q))
    return order
---tests
assert finish_order([("A", 5), ("B", 2), ("C", 3)], 2) == ["B", "C", "A"], "short jobs finish first"
assert finish_order([("A", 5), ("B", 2), ("C", 3)], 10) == ["A", "B", "C"], "a big slice is FIFO"
assert finish_order([], 3) == [], "nothing to run"
---hint
Treat the queue as a list of `(name, work_left)`. Pop the front: if it fits in one slice, it finishes; otherwise it goes to the back with `q` less work.
```

```recall
Q: Explain how an operating system shares one CPU and one memory between many programs, and the main trade-offs in each.
A: The scheduler keeps a ready queue and gives the CPU to one process at a time. First-come-first-served is simple but short jobs get stuck behind long ones. Shortest-first minimises average waiting but needs to know the future and can starve long jobs. Round robin gives each process a time slice and sends it to the back of the queue, so interactive work stays responsive without knowing job lengths; smaller slices mean better response but more context switches, each of which costs time and cache warmth. For memory, each process uses virtual addresses split into a page number and an offset; a per-process page table maps pages to physical frames, which isolates programs from each other. A missing page causes a page fault; when memory is full the OS evicts a page, and LRU (evict the least recently used) works well because recent use predicts future use, while FIFO can even get worse with more memory. Because the scheduler can switch between any two instructions, shared data needs locks to avoid lost updates.
```

## A ledger with no one in charge

A bank keeps one ledger, and you trust the bank not to edit it. What if a group of strangers has to share one ledger, nobody is in charge, and some of them would happily cheat? Everyone can keep a copy, but then two questions remain: **how do you notice if someone changes an old entry**, and **when copies disagree, which one wins?**

A **blockchain** answers both with one tool, the **cryptographic hash**: a function that turns any input into a short fingerprint (SHA-256 gives 64 hex digits). Three properties make it useful:

- the same input always gives the same fingerprint;
- changing one character changes the whole fingerprint unpredictably (the **avalanche effect**);
- nobody knows how to find an input that gives a chosen fingerprint, except by trying inputs one at a time.

The same idea, without the mining, protects Git commits (chapter 8), certificate-transparency logs and many audit logs.

## Proof of work

Anyone can compute a hash in a microsecond, so a chain of hashes alone stops nobody: a cheater would just recompute every hash after their change. **Proof of work** makes each block expensive. A block counts only if its hash starts with `difficulty` zeros, and the only way to get one is to change a number in the block, the **nonce**, and try again, and again.

Checking the work takes one hash. Doing it takes about 16<sup>difficulty</sup>. That asymmetry is the whole trick.

## Many transactions, one fingerprint

A real block holds thousands of transactions. Instead of hashing them all as one long string, Bitcoin builds a **Merkle tree**: hash each transaction, then hash pairs of hashes, then pairs of those, until one hash is left, the **Merkle root**, which goes in the block. A phone wallet can then check that one transaction is in a block with just a handful of hashes (one per level) instead of downloading the whole block.

```exercise
title: merkle_root
kind: write
---prompt
Write `merkle_root(txs)` for a non-empty list of strings. Use `h(s) = sha256(s.encode()).hexdigest()`:

1. The first level is `[h(tx) for tx in txs]`.
2. While more than one hash remains: if the level has an odd length, repeat its last hash; then replace each pair `a, b` with `h(a + b)`.
3. Return the one hash left.
---starter
def merkle_root(txs):
    pass
---solution
def merkle_root(txs):
    h = lambda s: hashlib.sha256(s.encode()).hexdigest()
    level = [h(tx) for tx in txs]
    while len(level) > 1:
        if len(level) % 2:
            level.append(level[-1])
        level = [h(level[i] + level[i + 1]) for i in range(0, len(level), 2)]
    return level[0]
---tests
h = lambda s: hashlib.sha256(s.encode()).hexdigest()
assert merkle_root(["a"]) == h("a"), "one transaction is its own root"
assert merkle_root(["a", "b"]) == h(h("a") + h("b"))
ab, cc = h(h("a") + h("b")), h(h("c") + h("c"))
assert merkle_root(["a", "b", "c"]) == h(ab + cc), "an odd level repeats its last hash"
assert merkle_root(["a", "b", "c"]) != merkle_root(["a", "c", "b"]), "order matters"
---hint
Each loop pass halves the level. `range(0, len(level), 2)` walks the pairs.
```

## When copies disagree

Two miners can find a block at almost the same moment, so the network briefly has two different chains. Every node follows the same rule: **among valid chains, keep the one with the most work** (with a fixed difficulty, the longest). The tie soon breaks, because the next block lands on one side, and everyone switches to that side.

This is why rewriting history is so hard. To replace a block 6 deep, a cheater must re-mine those 6 blocks **and** overtake the honest miners, who keep extending their chain all the while. With less than half the network's computing power, the chance of ever catching up shrinks exponentially with depth.

```exercise
title: choose_chain
kind: write
---prompt
Write `choose_chain(chains, is_valid)` that returns the longest chain for which `is_valid(chain)` is `True`. If two valid chains have the same length, keep the one that came **first** in `chains` (a node doesn't switch on a tie). Return `None` if no chain is valid.
---starter
def choose_chain(chains, is_valid):
    return None
---solution
def choose_chain(chains, is_valid):
    best = None
    for c in chains:
        if is_valid(c) and (best is None or len(c) > len(best)):
            best = c
    return best
---tests

Strictly greater (`>`) is what keeps the first chain on a tie.
```

```exercise
title: balances
kind: write
---prompt
The chain only stores transactions; the balances are what you get by **replaying** them in order, like the state machine in the Raft chapter. Write `balances(txs, start)` where each transaction is `"Ana->Ben:5"` and `start` is a dict of opening balances. ---starter

---solution
def balances(txs, start):
    bal, skipped = dict(start), []
    for tx in txs:
        who, amount = tx.split(":")
        src, dst = who.split("->")
        amount = int(amount)
        if bal.get(src, 0) < amount:
            skipped.append(tx)
            continue
        bal[src] -= amount
        bal[dst] = bal.get(dst, 0) + amount
    return bal, skipped
---tests

```

Real coins add one more ingredient: **digital signatures**. Each transaction is signed with the sender's private key, and everyone checks it with their public key, so nobody can spend someone else's coins even though the ledger is public. The hashing and the work you built here are what stop anyone from rewriting the history afterwards.

```quiz
Why does a blockchain need proof of work at all, if the hash links already reveal tampering?
- To make the hashes longer
- To encrypt the transactions so nobody can read them
* Because a cheater could otherwise recompute every hash after their change in a moment; the work makes each rewritten block expensive
- Because SHA-256 is slow
> The links make a change visible unless the cheater rebuilds everything after it. Without proof of work that rebuild is instant. With it, every block costs as much work as the honest network spent on it, and the honest network keeps going.
```

## Real-world project: a tamper-evident audit log

```project

client: A small clinic that must prove to an inspector that nobody edited or deleted old access records

Build an append-only audit log in Python: each line is a JSON record (`who`, `what`, `when`) plus the hash of the previous line, and the hash of itself. - Anchor: save the head hash daily and check the log against every saved anchor

---stretch
- A Merkle tree over each day's records, so one record can be proved without revealing the others
```

## Rebuild it and explain it

```exercise
title: mine_rebuild
kind: rebuild
---prompt
From memory: write `mine(text, difficulty)` that returns the smallest nonce `n` such that the SHA-256 hex digest of `f"{text}{n}"` starts with `difficulty` zeros.
---starter
def mine(text, difficulty):
    pass
---solution
def mine(text, difficulty):
    n = 0
    while not hashlib.sha256(f"{text}{n}".encode()).hexdigest().startswith("0" * difficulty):
        n += 1
    return n
---tests
n = mine("block", 3)
assert hashlib.sha256(f"block{n}".encode()).hexdigest().startswith("000")
assert all(not hashlib.sha256(f"block{k}".encode()).hexdigest().startswith("000") for k in range(n))
assert mine("x", 0) == 0, "no zeros needed: the first nonce works"
---hint
A `while not ...startswith(...)` loop that adds one to `n` each time.
```

```recall
Q: Explain how a blockchain lets strangers share a ledger that nobody can quietly rewrite.
A: Each block holds its data, the hash of the previous block and a nonce, and its own hash covers all three. Because a hash changes completely when any input changes, editing an old block changes its hash, which breaks the link stored in the next block, and so on to the end: tampering is visible. Proof of work makes repairing it expensive: a block only counts if its hash starts with a number of zeros, which takes about 16^d tries to find but one hash to check. So a cheater must redo the work for the changed block and every block after it. Nodes keep the valid chain with the most work, and honest miners keep extending theirs, so a cheater with less than half the computing power falls further behind; the chance of rewriting a block k deep shrinks exponentially in k. Merkle roots summarise a block's transactions in one hash, balances come from replaying the transactions in order, and signatures (not built here) prove who authorised each payment.
```

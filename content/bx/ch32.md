## Waiting is most of the work

A web server spends most of its life waiting: for the database, for another service, for the network. With **blocking** calls, a program that sends a request sits idle until the answer arrives, and only then starts the next request. Ten requests of 100 ms each take a second.

An **event loop** keeps one thread busy differently. Each task runs until it has to wait, then **gives control back** (that's what `await` does). The loop parks it with a timer or an I/O watch and runs some other task that's **ready**. When the wait is over, the parked task becomes ready again. Waits overlap, so ten requests take about 100 ms.

The parts are small:

- a **ready queue** of tasks that can run now,
- a **heap of timers** ordered by wake-up time,
- **futures** (promises in JavaScript): a box for a result that isn't there yet, with callbacks to run when it arrives,
- a loop: run everything ready, then sleep until the next timer.

```viz

title: Three jobs, one CPU

```

There's still only one thread, so CPU work never overlaps. Async helps with waiting, not with heavy computing; and one blocking call inside a task (like `time.sleep` instead of `await asyncio.sleep`) freezes every other task too.

Python generators are enough to build it: a task `yield`s how long it wants to sleep, and the loop decides when to resume it. That's how asyncio started.

```predict
def task():
    print("start")
    yield 3
    print("after 3")
    yield 1
    print("done")

t = task()
print(next(t))
print(next(t))
```

## The loop

```exercise
title: event_loop
kind: write
---prompt
Write `run(tasks)`. `tasks` is a dict of name → generator; each generator yields a number of seconds to sleep. Use a **virtual** clock starting at 0 (no real sleeping) and a heap of `(wake_time, seq, name, gen)`, where `seq` is a counter so ties go first-come first-served. Every task starts at time 0. Pop the earliest, set the clock to its time, resume it; if it yields d, push it back for `clock + d`; if it finishes, record `(name, clock)`. Return the finish records in order.
---starter
def run(tasks):
    clock, out = 0, []
    for name, gen in tasks.items():
        for d in gen:
            clock += d
        out.append((name, clock))
    return out
---solution
import heapq

def run(tasks):
    heap, seq, clock, out = [], 0, 0, []
    for name, gen in tasks.items():
        heap.append((0, seq, name, gen))
        seq += 1
    heapq.heapify(heap)
    while heap:
        clock, _, name, gen = heapq.heappop(heap)
        try:
            d = next(gen)
        except StopIteration:
            out.append((name, clock))
            continue
        heapq.heappush(heap, (clock + d, seq, name, gen))
        seq += 1
    return out
---tests
def job(*waits):
    for w in waits:
        yield w
assert run({"a": job(3), "b": job(1, 1), "c": job(2)}) == [("c", 2), ("b", 2), ("a", 3)], "c set its timer for 2 before b did"
assert run({"x": job()}) == [("x", 0)]
assert run({"p": job(5), "q": job(5)}) == [("p", 5), ("q", 5)], "ties: first come, first served"
r = run({f"t{i}": job(1, 2, 3) for i in range(1000)})
assert r[-1] == ("t999", 6) and len(r) == 1000, "1000 tasks of 6 seconds each still finish at 6"
---hint
The starter runs each task to the end before the next, like blocking code: 1000 tasks would take 6000 seconds.
---hint
`heapq` pops the smallest tuple. Put the wake time first and a counter second, so equal times never compare the generators.
```

```exercise
title: tie_breaker
kind: bug
---prompt
This timer heap stores `(when, callback)`. When two timers are due at the same moment, Python compares the callbacks to break the tie and raises `TypeError` (functions can't be compared with `<`). Add a sequence number so ties keep the order they were scheduled in.
---starter
import heapq

class Timers:
    def __init__(self):
        self.heap = []

    def call_later(self, when, fn):
        heapq.heappush(self.heap, (when, fn))

    def run(self):
        while self.heap:
            when, fn = heapq.heappop(self.heap)
            fn()
---solution
import heapq
from itertools import count

class Timers:
    def __init__(self):
        self.heap = []
        self.seq = count()

    def call_later(self, when, fn):
        heapq.heappush(self.heap, (when, next(self.seq), fn))

    def run(self):
        while self.heap:
            when, _, fn = heapq.heappop(self.heap)
            fn()
---tests
log = []
t = Timers()
t.call_later(2, lambda: log.append("b"))
t.call_later(1, lambda: log.append("a"))
t.call_later(2, lambda: log.append("c"))
t.call_later(2, lambda: log.append("d"))
t.run()
assert log == ["a", "b", "c", "d"]
---hint
Make the tuple `(when, seq, fn)` with a counter that only goes up. Tuples compare left to right and stop at the first difference.
```

## Futures and gather

```exercise
title: future
kind: write
---prompt
Write a class `Future` (a promise): `done()`, `result()` (raises `RuntimeError` if not done yet), `set_result(v)` (raises `RuntimeError` if already set; otherwise stores v and calls every registered callback with the future, in order), and `add_done_callback(fn)` (if already done, call `fn(self)` straight away; otherwise remember it).
---starter
class Future:
    def __init__(self):
        self.value = None

    def done(self):
        return self.value is not None

    def result(self):
        return self.value

    def set_result(self, v):
        self.value = v

    def add_done_callback(self, fn):
        pass
---solution
class Future:
    def __init__(self):
        self._done, self._value, self._callbacks = False, None, []

    def done(self):
        return self._done

    def result(self):
        if not self._done:
            raise RuntimeError("result is not ready")
        return self._value

    def set_result(self, v):
        if self._done:
            raise RuntimeError("result already set")
        self._done, self._value = True, v
        for fn in self._callbacks:
            fn(self)
        self._callbacks = []

    def add_done_callback(self, fn):
        if self._done:
            fn(self)
        else:
            self._callbacks.append(fn)
---tests
seen = []
f = Future()
assert not f.done()
try:
    f.result()
    assert False, "result() before set_result should raise"
except RuntimeError:
    pass
f.add_done_callback(lambda fut: seen.append(("first", fut.result())))
f.add_done_callback(lambda fut: seen.append(("second", fut.result())))
f.set_result(None)
assert f.done() and f.result() is None, "None is a valid result"
assert seen == [("first", None), ("second", None)]
f.add_done_callback(lambda fut: seen.append("late"))
assert seen[-1] == "late", "a callback added after completion runs immediately"
try:
    f.set_result(1)
    assert False, "setting twice should raise"
except RuntimeError:
    pass
---hint
The starter uses `None` to mean "not done", which breaks when the result really is `None`. Keep a separate `_done` flag.
---hint
`set_result` stores the value and then runs the saved callbacks; `add_done_callback` runs the callback at once if the future is already done.
```

```exercise
title: gather
kind: write
---prompt
Write `gather(gens)`: run a list of generator tasks concurrently on a virtual clock (they yield sleep times, as in `run`) and collect each task's **return value** (a generator's `return x` arrives as `StopIteration.value`). Return `(results, finish_time)` with results in the **same order as the input**, not the order they finished.
---starter
def gather(gens):
    results, clock = [], 0
    for g in gens:
        try:
            while True:
                clock += next(g)
        except StopIteration as e:
            results.append(e.value)
    return results, clock
---solution
import heapq

def gather(gens):
    heap = [(0, i, i, g) for i, g in enumerate(gens)]
    heapq.heapify(heap)
    results, clock, seq = [None] * len(gens), 0, len(gens)
    while heap:
        clock, _, i, g = heapq.heappop(heap)
        try:
            d = next(g)
        except StopIteration as e:
            results[i] = e.value
            continue
        heapq.heappush(heap, (clock + d, seq, i, g))
        seq += 1
    return results, clock
---tests
def fetch(name, latency):
    yield latency
    return f"{name}:{latency}"
r, t = gather([fetch("a", 3), fetch("b", 1), fetch("c", 2)])
assert r == ["a:3", "b:1", "c:2"], "results in input order"
assert t == 3, "the slowest request decides the total"
r, t = gather([fetch(str(i), 1 + i % 5) for i in range(500)])
assert t == 5 and r[7] == "7:3"
assert gather([]) == ([], 0)
---hint
The starter runs the tasks one after another, so the times add up. Use a heap, as in `run`.
---hint
Keep each task's input index with it in the heap, so its return value goes into the right slot of `results`.
```

## Quick-fire: lock it in

```quiz
Inside an async task you call `time.sleep(2)` instead of `await asyncio.sleep(2)`. What happens?
- Only that task pauses
* The whole event loop stops for 2 seconds: no other task can run, because the one thread is stuck
- Python converts it automatically
- It raises an error
> `await` hands control back to the loop. A blocking call never does.
```

```quiz
You have 8 CPU-heavy image resizes. Will asyncio make them faster?
- Yes, about 8 times faster
* No: they don't wait on anything, and one thread still does them one at a time. Use processes for CPU work
- Yes, if you add more awaits
- Only on Linux
> Async overlaps waiting. It can't overlap computing on one thread.
```

## Real-world project: a polite web crawler

```project

Build `crawl.py` on asyncio (or your own loop). Keep at most 8 requests in flight: start the next URL only when one finishes. Give each request a timeout and retry failed ones up to 3 times with growing delays. Report the total time and compare it with 1 at a time and with no limit.

---milestones
- Many requests concurrently
- At most N in flight
- Timeouts and retries
```

```exercise
title: crawl_time
kind: write
---prompt
Write `crawl(latencies, limit)`: URLs are fetched in list order, each taking `latencies[i]` seconds, with at most `limit` in flight. A new fetch starts the moment a slot frees up (if several finish at the same time, they all free their slots then). Return `(total_time, order)` where `order` lists the indices in the order they finished (ties: lower index first).
---starter
def crawl(latencies, limit):
    return sum(latencies), list(range(len(latencies)))
---solution
import heapq

def crawl(latencies, limit):
    heap, order, nxt, clock = [], [], 0, 0
    while nxt < len(latencies) and len(heap) < limit:
        heapq.heappush(heap, (latencies[nxt], nxt))
        nxt += 1
    while heap:
        clock, i = heapq.heappop(heap)
        order.append(i)
        if nxt < len(latencies):
            heapq.heappush(heap, (clock + latencies[nxt], nxt))
            nxt += 1
    return clock, order
---tests
assert crawl([3, 1, 2], 1) == (6, [0, 1, 2])
assert crawl([3, 1, 2], 3) == (3, [1, 2, 0])
assert crawl([3, 1, 2, 1], 2) == (4, [1, 0, 2, 3])
assert crawl([], 4) == (0, [])
lat = [1 + (i * 7919) % 10 for i in range(10000)]
t, order = crawl(lat, 8)
assert t == 6877 and len(order) == 10000
assert crawl(lat, 10000)[0] == 10
---hint
The starter fetches one at a time. Keep a heap of in-flight finish times; when the earliest finishes, start the next URL from that moment.
---hint
Fill the heap with the first `limit` URLs, then loop: pop `(finish, i)`, record i, push the next URL with finish time `finish + latency`.
```

```recall
Q: Explain how an async runtime works: what problem it solves, the ready queue, timers, futures and await, why it uses one thread, and what it can't speed up.
A: Programs that talk to networks and disks spend most of their time waiting. Blocking calls leave the thread idle during each wait, so total time is the sum of all waits. An event loop runs many tasks on one thread. Each task runs until it needs to wait, then awaits: it registers interest in a future (a placeholder for a result not yet available) and hands control back. The loop keeps a queue of ready tasks and a heap of timers ordered by wake time (with a sequence number to break ties); it runs the ready tasks, then sleeps until the next timer or I/O event, and callbacks on completed futures put the waiting tasks back in the ready queue. Waits overlap, so ten 100 ms requests take about 100 ms. One thread means no locks are needed between awaits, but also that CPU work never overlaps, and a single blocking call (time.sleep, a slow loop) freezes every task. CPU-heavy work needs processes or threads instead. A semaphore limits how many operations are in flight at once.
```

## What git really stores

Most people picture git as "a list of changes". It isn't. Every commit is a **full snapshot** of your project. That sounds wasteful: 1,000 commits of a 1,000-file project would be a million files. Yet a `.git` folder is usually small.

The trick is one idea: **name every piece of data by a fingerprint of its content.** If a file didn't change, its fingerprint didn't change, so the new snapshot just points at the old copy. Nothing is stored twice.

There are only three kinds of object:

1. **Blob:** the contents of one file.
2. **Tree:** a folder, written as a list of `name → blob id`.
3. **Commit:** a tree id, the id of the commit before it (its **parent**), and a message.

Play first. Each column is a commit (top), its tree (middle) and its file blobs (bottom).

## Same content, same name

A **hash function** turns any amount of data into a short fixed-size fingerprint. SHA-1 gives 40 hex characters. Two promises matter:

- **Same input → same hash**, on every computer, forever.
- **Change one byte → a completely different hash.** And nobody knows how to find two different files with the same SHA-1 by accident.

So the hash can be the file's *name*. That's called **content addressing**. Git hashes a small header (`blob <length>`, then a zero byte) followed by the content. This is exactly what `git hash-object` does.

```predict
def oid(kind, body):
    data = f"{kind} {len(body)}\0{body}".encode()
    return hashlib.sha1(data).hexdigest()

print(oid("blob", "hello\n"))
print(oid("blob", "hello\n") == oid("blob", "hello\n"))
print(oid("blob", "Hello\n")[:12])
print(len(oid("blob", "a whole novel " * 1000)))
```

Two things fall out for free. **Dedupe:** storing the same content twice writes the same key twice, so the dictionary still holds one copy. **Tamper-evidence:** if someone edits a stored object, its contents no longer match its name, and you can check that.

## Trees: a folder is a list of names

A blob has no filename. That's on purpose: two files with identical content (two copies of a licence, say) share one blob. The **name** lives one level up, in a **tree**: one line per file, `name blob-id`, sorted by name so the same folder always produces the same text, and so the same tree id.

## Commits, branches and HEAD

A **commit** is a tiny text object:

```
tree 3b18e5...
parent 9f2c41...

add banana price
```

Because the commit's text includes its parent's id, its own id depends on the parent, which depends on *its* parent, all the way back. Change anything in old history and every later id changes. That's why you can't quietly rewrite a published commit.

A **branch** is not a copy of anything. It's a name pointing at one commit id: `refs = {"main": "9f2c41..."}`. Committing moves the pointer forward. **HEAD** says which branch you're on.

```run
title: a tiny repo and its log
store, refs = {}, {}

    oid = hashlib.sha1(f"{kind} {len(body)}\0{body}".encode()).hexdigest()

    return oid

        if key == "tree": info["tree"] = value
```

## Diff: compare two trees

To show what changed between two commits, you don't compare file contents line by line first. Compare the **trees**: if a name has the same blob id on both sides, the file is identical and you skip it without reading it. Only names whose ids differ need a closer look.

```exercise
title: diff_trees
kind: write
---prompt
Write `diff_trees(old, new)`. Both are dicts `{name: blob_id}` (a tree already read back). Return a dict with three **sorted** lists: `"added"` (only in new), `"removed"` (only in old) and `"changed"` (in both, different id).
---starter
def diff_trees(old, new):
    # your code here
    return {"added": [], "removed": [], "changed": []}
---solution
def diff_trees(old, new):
    return {
        "added": sorted(n for n in new if n not in old),
        "removed": sorted(n for n in old if n not in new),
        "changed": sorted(n for n in old if n in new and old[n] != new[n]),
    }
---tests
old = {"a.txt": "11", "b.txt": "22", "c.txt": "33"}
new = {"a.txt": "11", "b.txt": "99", "d.txt": "44"}
d = diff_trees(old, new)
assert d["added"] == ["d.txt"], f"d.txt is new, got {d['added']}"
assert d["removed"] == ["c.txt"], f"c.txt was removed, got {d['removed']}"
assert d["changed"] == ["b.txt"], f"only b.txt has a different blob id, got {d['changed']}"

---hint
Three comprehensions: names in `new` but not `old`, names in `old` but not `new`, and names in both whose ids differ.
```

In a real repo, trees contain other trees (sub-folders). If a sub-folder's tree id is the same on both sides, git skips the **whole folder** in one comparison. That's why `git diff` is fast even in huge projects.

## Where did two branches split?

Before you can merge `main` and `idea`, you need the commit where they **split**: the newest commit that both histories contain. It's called the **merge base**.

History is a graph where each commit points at its parents (a merge commit has two). The recipe:

1. Collect **every** ancestor of `a` (including `a`) into a set.
2. Walk back from `b` breadth-first (nearest commits first). The first commit you meet that is in the set is the merge base.

```exercise
title: merge_base
kind: write
---prompt
Write `merge_base(parents, a, b)`. `parents` maps each commit id to a list of parent ids (empty for the first commit). Return the closest common ancestor of `a` and `b` (a commit counts as its own ancestor). Return `None` if they share nothing.
---starter
def merge_base(parents, a, b):
    # your code here
    pass
---solution
from collections import deque
def merge_base(parents, a, b):
    seen, stack = set(), [a]
    while stack:
        c = stack.pop()
        if c not in seen:
            seen.add(c)
            stack.extend(parents[c])
    queue, visited = deque([b]), set()
    while queue:
        c = queue.popleft()
        if c in seen:
            return c
        if c not in visited:
            visited.add(c)
            queue.extend(parents[c])
    return None
---tests
#   A - B - C - D        (main)
#        \
#         E - F          (idea)
P = {"A": [], "B": ["A"], "C": ["B"], "D": ["C"], "E": ["B"], "F": ["E"]}
assert merge_base(P, "D", "F") == "B", f"main and idea split at B, got {merge_base(P, 'D', 'F')}"
assert merge_base(P, "F", "D") == "B", "the answer doesn't depend on the order"
assert merge_base(P, "D", "B") == "B", "if one is an ancestor of the other, it IS the merge base"
P2 = dict(P, G=["D", "F"], H=["F"])
assert merge_base(P2, "G", "H") == "F", "after merging idea into main (G), a newer idea commit H splits from G at F"
assert merge_base({"X": [], "Y": []}, "X", "Y") is None, "unrelated histories have no merge base"
---hint
Part 1 is a plain graph walk with a stack and a `seen` set. Part 2 uses `collections.deque` so you look at the nearest commits first.
---hint
Remember a merge commit has **two** parents: always extend with the whole `parents[c]` list.
```

## Three-way merge

Why do you need the base? Picture `a.txt` is different on your branch and on theirs. With only two versions you can't tell who changed it. With the **base** you can:

| base | ours | theirs | result |
|---|---|---|---|
| X | X | Y | Y (only they changed it) |
| X | Y | X | Y (only we changed it) |
| X | Y | Y | Y (we both made the same change) |
| X | Y | Z | **conflict**: a human must decide |

That's the whole idea of a **three-way merge**. A two-way comparison would call every difference a conflict.

```predict
def pick(base, ours, theirs):
    if ours == theirs: return ours
    if ours == base: return theirs
    if theirs == base: return ours
    return "CONFLICT"

print(pick("x", "x", "y"))
print(pick("x", "y", "x"))
print(pick("x", "y", "y"))
print(pick("x", "y", "z"))
print(pick(None, None, "new file"))
```

```exercise
---starter
def merge_files(base, ours, theirs):
    merged, conflicts = {}, []
    # your code here

---solution
def merge_files(base, ours, theirs):
    merged, conflicts = {}, []
    for name in sorted(set(base) | set(ours) | set(theirs)):
        b, o, t = base.get(name), ours.get(name), theirs.get(name)
        if o == t:
            result = o
        elif o == b:
            result = t
        elif t == b:
            result = o
        else:
            conflicts.append(name)
            result = "<<<<<<< ours\n" + (o or "") + "\n=======\n" + (t or "") + "\n>>>>>>> theirs"
        if result is not None:
            merged[name] = result
    return merged, conflicts
---tests

```

A merge then makes a commit with **two parents**: your branch tip and theirs. That's the diamond you made in the simulation.

## Real-world project: version history for a notes app

Notion, Google Docs, Figma and Apple Notes all let you "see version history" and "restore this version". Under the hood, many store versions exactly like git: content-addressed snapshots in a key-value store, chained by parent ids.

```project
title: Version history for a notes app
client: A small team whose shared meeting notes keep getting overwritten
skills: hashing, dictionaries, linked history, three-way merge
---brief
Every time someone presses Save, keep a version. People must be able to list versions newest first, restore any old one, and two people editing from the same version should be merged automatically when they touched different notes. Saving the same text twice must not use any extra storage.
---why
Content-addressed storage is everywhere: git, Docker image layers, IPFS, backup tools like restic and borg, and the deduplicated blob storage behind Dropbox and Google Drive. Three-way merge is what lets two editors (or two phones syncing offline) combine their work without asking you every time.
---milestones
- Store each note's text as a blob with `hash_object`; check that saving identical text adds nothing
- Make each save a commit object with a parent id and a message
- List versions newest first by following parents
- Restore a version by reading back its tree
- Merge two people's versions with `merge_base` and `merge_files`
---stretch
- Show a diff between any two versions using `diff_trees`
- Add a "verify" button that finds tampered objects
- Pack old versions into one compressed file (git's "packfile") and measure the savings
```

```exercise

---solution
class NotesHistory:
    def __init__(self):
        self.store = {}
        self.head = None

    def _read(self, oid):
        top, _, message = self.store[oid][1].partition("\n\n")
        tree, parent = None, None
        for line in top.splitlines():
            key, value = line.split(" ", 1)
            if key == "tree":
                tree = value
            elif key == "parent":
                parent = value
        return tree, parent, message

    def save(self, notes, message):
        body = f"tree {write_tree(self.store, notes)}\n"
        if self.head:
            body += f"parent {self.head}\n"
        self.head = hash_object(self.store, "commit", body + f"\n{message}")
        return self.head

    def versions(self):
        out, oid = [], self.head
        while oid:
            _, oid_parent, message = self._read(oid)
            out.append(message)
            oid = oid_parent
        return out

    def restore(self, steps_back):
        oid = self.head
        for _ in range(steps_back):
            oid = self._read(oid)[1]
        return read_tree(self.store, self._read(oid)[0])
---tests

---hint

---hint
`restore(k)` follows the parent link `k` times, then calls `read_tree` on that commit's tree id.
```

```exercise
    def __init__(self):
        self.store, self.refs, self.head = {}, {}, "main"

    def put(self, kind, body):
        oid = hashlib.sha1(f"{kind} {len(body)}\0{body}".encode()).hexdigest()
        self.store[oid] = (kind, body)
        return oid

    def read(self, oid):
        top, _, msg = self.store[oid][1].partition("\n\n")
        lines = [l.split(" ", 1) for l in top.splitlines()]
        tree = [v for k, v in lines if k == "tree"][0]
        parents = [v for k, v in lines if k == "parent"]
        return tree, parents, msg

    def commit(self, files, message):
        tree = self.put("tree", "\n".join(f"{n} {self.put('blob', files[n])}" for n in sorted(files)))
        body = f"tree {tree}\n"
        if self.head in self.refs:
            body += f"parent {self.refs[self.head]}\n"
        self.refs[self.head] = self.put("commit", body + f"\n{message}")
        return self.refs[self.head]

    def branch(self, name):
        self.refs[name] = self.refs[self.head]

    def checkout(self, name):
        self.head = name
        tree = self.read(self.refs[name])[0]
        out = {}
        for line in self.store[tree][1].splitlines():
            n, b = line.rsplit(" ", 1)
            out[n] = self.store[b][1]
        return out

    def log(self):
        out, oid = [], self.refs.get(self.head)
        while oid:
            _, parents, msg = self.read(oid)
            out.append(msg)
            oid = parents[0] if parents else None
        return out
```

```recall
Q: Why can git keep a full snapshot of your project in every commit without the repository exploding in size, and why does changing an old commit change every commit after it?
A: Every object is named by the SHA-1 hash of its content. An unchanged file has the same hash, so a new tree just points at the existing blob: only changed files, their trees and the commit are new objects. A commit's text includes its parent's id, so its own id depends on the whole chain behind it; edit anything old and its id changes, which changes its child's text and id, and so on to the tip. That makes history deduplicated and tamper-evident.
```

## The lost reply

You tap **Pay**. Your phone sends the request, the server charges your card, and the reply... never arrives: you went into a tunnel. Did the payment fail, or did it work? **Your phone can't know.** Its only safe move is to try again. If the server treats that retry as a fresh purchase, you pay twice.

The fix is an **idempotency key**: the phone makes up one random id per purchase (not per request) and sends it with every retry. The server keeps a table `key → result`. A new key is processed and its result saved; a key it has seen gets the saved result back, and nothing is charged.

```viz
name: bx-pay
title: Five customers, a patchy network
goal: Run **charge every time** to the end, then run **idempotency keys** and compare what was charged.
height: 440
Some replies are lost on the way back, so phones retry.
```

Which results to save matters. A **decline** ("insufficient funds") is a real answer: save it, so a retry gets the same decline. A **network error before reaching the bank** means nothing happened: don't save it, so the retry actually tries.

## The idempotent endpoint

```exercise
title: idempotent_endpoint
kind: write
---prompt
Write `Endpoint(charge)`, where `charge(body)` talks to the bank: it returns a result dict, or raises `ConnectionError` if the bank couldn't be reached. `handle(key, body)`:
- a new key: call `charge(body)`, save `(body, result)` under the key and return the result. If `charge` raises `ConnectionError`, save nothing and let it propagate (so a retry tries again).
- a key seen before with the same body: return the saved result without calling `charge`.
- a key seen before with a **different** body: raise `ValueError` (the client reused a key for another purchase).
---starter
class Endpoint:
    def __init__(self, charge):
        self.charge = charge

    def handle(self, key, body):
        return self.charge(body)
---solution
class Endpoint:
    def __init__(self, charge):
        self.charge = charge
        self.saved = {}

    def handle(self, key, body):
        if key in self.saved:
            old_body, result = self.saved[key]
            if old_body != body:
                raise ValueError("idempotency key reused with a different request")
            return result
        result = self.charge(body)
        self.saved[key] = (body, result)
        return result
---tests
calls = []
outage = {"on": False}
def charge(body):
    if outage["on"]:
        raise ConnectionError("bank unreachable")
    calls.append(body)
    return {"status": "declined" if body["amount"] > 500 else "paid", "amount": body["amount"]}
e = Endpoint(charge)
assert e.handle("k1", {"amount": 20}) == {"status": "paid", "amount": 20}
assert e.handle("k1", {"amount": 20})["status"] == "paid"
assert len(calls) == 1, "a retry doesn't charge again"
assert e.handle("k2", {"amount": 900})["status"] == "declined"
assert e.handle("k2", {"amount": 900})["status"] == "declined" and len(calls) == 2, "declines are saved too"
outage["on"] = True
try:
    e.handle("k3", {"amount": 5})
    assert False
except ConnectionError:
    pass
outage["on"] = False
assert e.handle("k3", {"amount": 5})["status"] == "paid" and len(calls) == 3, "a connection error isn't saved"
try:
    e.handle("k1", {"amount": 99})
    assert False, "same key, different body"
except ValueError:
    pass
---hint
The starter charges every time. Keep a dict `key → (body, result)` and look there first.
---hint
If `self.charge(body)` raises, the line that saves the result never runs, which is exactly what you want.
```

## A payment is a state machine

Card payments happen in two steps. **Authorize** asks the bank to hold the money (a hotel does this at check-in). **Capture** actually takes it, possibly less than was held. Before capture you can **void** the hold; after capture you can only **refund**, and never more than was captured.

```exercise
title: payment_states
kind: write
---prompt
Write `Payment(amount)` in state `"created"`, with:
- `authorize()`: created → `"authorized"`.
- `capture(n)`: authorized → `"captured"`, taking `n` cents, where 0 < n ≤ amount.
- `void()`: authorized → `"voided"`.
- `refund(n)`: captured or `"refunded"` → `"refunded"`, where 0 < n and the total refunded never exceeds what was captured.

Any other move raises `ValueError`. Keep `captured` and `refunded` totals as attributes (both start at 0).
---starter
class Payment:
    def __init__(self, amount):
        self.amount, self.state = amount, "created"
        self.captured = self.refunded = 0

    def authorize(self):
        self.state = "authorized"

    def capture(self, n):
        self.captured = n
        self.state = "captured"

    def void(self):
        self.state = "voided"

    def refund(self, n):
        self.refunded += n
        self.state = "refunded"
---solution
class Payment:
    def __init__(self, amount):
        self.amount, self.state = amount, "created"
        self.captured = self.refunded = 0

    def _need(self, *states):
        if self.state not in states:
            raise ValueError(f"can't do that while {self.state}")

    def authorize(self):
        self._need("created")
        self.state = "authorized"

    def capture(self, n):
        self._need("authorized")
        if not 0 < n <= self.amount:
            raise ValueError("bad capture amount")
        self.captured, self.state = n, "captured"

    def void(self):
        self._need("authorized")
        self.state = "voided"

    def refund(self, n):
        self._need("captured", "refunded")
        if n <= 0 or self.refunded + n > self.captured:
            raise ValueError("refund too large")
        self.refunded += n
        self.state = "refunded"
---tests
def bad(f, *a):
    try:
        f(*a)
        return False
    except ValueError:
        return True
p = Payment(5000)
assert bad(p.capture, 100), "can't capture before authorizing"
p.authorize()
assert bad(p.capture, 6000), "can't capture more than authorized"
p.capture(4200)
assert p.state == "captured" and p.captured == 4200
assert bad(p.void), "too late to void"
p.refund(1000); p.refund(3000)
assert p.state == "refunded" and p.refunded == 4000
assert bad(p.refund, 201), "only 200 left to refund"
p.refund(200)
assert bad(p.authorize)
q = Payment(800); q.authorize(); q.void()
assert q.state == "voided" and bad(q.capture, 800) and bad(q.refund, 1)
---hint
The starter allows every move from every state. Write a small `_need(*states)` helper that raises unless the current state is one of them.
```

## Webhooks arrive twice

The bank tells your server what happened later with **webhooks**: HTTP calls like `payment.succeeded`. They are delivered **at least once**, so the same event can arrive two or three times, and your handler must not ship the order twice.

```exercise
title: webhook_dedupe
kind: bug
---prompt
Every webhook has a unique `id`. This handler ships an order every time `payment.succeeded` arrives, so a re-delivered event ships it again. Fix it so each event id is processed at most once.
---starter
class Shop:
    def __init__(self):
        self.shipped = []

    def on_webhook(self, event):
        if event["type"] == "payment.succeeded":
            self.shipped.append(event["order"])
---solution
class Shop:
    def __init__(self):
        self.shipped = []
        self.seen = set()

    def on_webhook(self, event):
        if event["id"] in self.seen:
            return
        self.seen.add(event["id"])
        if event["type"] == "payment.succeeded":
            self.shipped.append(event["order"])
---tests
s = Shop()
e1 = {"id": "evt_1", "type": "payment.succeeded", "order": "A"}
e2 = {"id": "evt_2", "type": "payment.succeeded", "order": "B"}
for e in (e1, e1, e2, e1, e2):
    s.on_webhook(e)
assert s.shipped == ["A", "B"]
s.on_webhook({"id": "evt_3", "type": "payment.failed", "order": "C"})
assert s.shipped == ["A", "B"]
---hint
Remember the ids you've handled in a set.
```

```exercise
title: payout
kind: write
---prompt
The processor's fee on a payment of `cents` is 2.9% rounded to the nearest cent (halves round up), plus 30 cents. Write `fee(cents)` using only integer arithmetic, and `payout(payments)`: the total the shop receives for a list of payment amounts after fees.
---starter
def fee(cents):
    return round(cents * 0.029) + 30

def payout(payments):
    return sum(payments)
---solution
def fee(cents):
    return (cents * 29 + 500) // 1000 + 30

def payout(payments):
    return sum(p - fee(p) for p in payments)
---tests
assert fee(1000) == 59
assert fee(50) == 31, "1.45 rounds down to 1"
assert fee(1500) == 74, "43.5 rounds up to 44"
assert fee(2500) == 103, "72.5 rounds up to 73"
assert payout([1000, 2000]) == 1000 - 59 + 2000 - 88
assert payout([]) == 0
---hint
2.9% is 29 per 1000. Adding 500 before dividing by 1000 rounds halves up.
---hint
Python's `round` uses banker's rounding (72.5 becomes 72), which is why the starter's fee is off by a cent sometimes.
```

## Rebuild it and explain it

```exercise
title: idem_rebuild
kind: rebuild
---prompt
From memory: `handle(saved, key, body, charge)`, where `saved` is a dict. Return the saved result for a known key (raise `ValueError` if the body differs); otherwise charge, save `(body, result)`, and return the result.
---starter
def handle(saved, key, body, charge):
    pass
---solution
def handle(saved, key, body, charge):
    if key in saved:
        if saved[key][0] != body:
            raise ValueError("key reused")
        return saved[key][1]
    result = charge(body)
    saved[key] = (body, result)
    return result
---tests
n = []
def charge(b):
    n.append(b)
    return "ok"
s = {}
assert handle(s, "k", 5, charge) == "ok" and handle(s, "k", 5, charge) == "ok" and len(n) == 1
try:
    handle(s, "k", 6, charge)
    assert False
except ValueError:
    pass
---hint
Look up the key first; only charge for new keys.
```

```recall
Q: Explain how a payments system avoids charging twice: lost replies and retries, idempotency keys and which results to save, the authorize/capture/void/refund state machine, and webhook deduplication.
A: A client that sends a payment and gets no reply can't tell whether it failed or whether only the reply was lost, so it must retry. To make retries safe, it creates one idempotency key per purchase and sends it with every retry. The server stores key → (request, result): a new key is processed and its result saved, a known key with the same request gets the saved result back without charging, and a known key with a different request is rejected as a client bug. Real outcomes such as paid or declined are saved; failures that never reached the bank are not, so the retry actually runs. A card payment is a state machine: authorize holds money, capture takes up to the authorized amount, void cancels an authorization before capture, and refunds return at most what was captured; any other move is refused. Webhooks from the processor are delivered at least once, so the handler records each event id and ignores repeats. Amounts are integer cents, and fees are computed with integer rounding.
```

## An elevator is a bundle of objects

Press the call button in a lift lobby. Something decides which car comes, which way it goes and when the doors open. That "something" is not one big function. It's a handful of small **objects**, each responsible for one thing:

- the **Building** holds everything together,
- each **Floor** knows who is waiting on it,
- the **Elevator** knows where it is and what it is doing,
- a **Policy** decides where the elevator should go next.

Before any code, play with them. Every block is one object. Click it and it tells you what it is responsible for, and why *it* owns that piece of data and not some other object.


## An object is state plus behaviour

An **object** bundles two things:

- **state**: the data it remembers (an elevator's current floor),
- **behaviour**: the things it can do, written as functions called **methods** (`move_to`).

A **class** is the blueprint. An **instance** is one real thing made from it. `Elevator()` builds a new instance; inside methods, `self` means "the instance this was called on". Two instances made from the same class have their *own* state: moving one doesn't move the other.

```predict
class Elevator:
    def __init__(self, floor=0):
        self.floor = floor

    def move_to(self, target):
        trip = abs(target - self.floor)
        self.floor = target
        return trip

a = Elevator()
b = Elevator(5)
print(a.move_to(3), a.floor)
print(b.move_to(3), b.floor)
print(a is b, a.floor == b.floor)
```

## Composition: a building has floors and elevators

Real systems are built by putting objects *inside* other objects. A Building doesn't inherit from Elevator ("a building is a kind of elevator" makes no sense). It **has** elevators. This is called **composition**, and it's the main way objects are combined.

Objects then talk by **message passing**: calling each other's methods. The building doesn't reach in and set `car.floor = 3`. It sends a message, `car.add_stop(3)`, and the car decides how to get there. The sender only needs to know *what* to ask, not *how* the other object works.


## Encapsulation: every instance owns its own state

**Encapsulation** means each object guards its own data, and everyone else goes through its methods. Python doesn't lock anything; the convention is a leading underscore (`self._stops`) meaning "private: please use my methods".

But there's a sneakier way to break ownership: two objects accidentally **sharing** the same list. A default argument like `stops=[]` is created *once*, when the function is defined, and then reused by every call. Predict what happens.

```predict
class Elevator:
    def __init__(self, stops=[]):
        self._stops = stops

    def add_stop(self, f):
        self._stops.append(f)

a = Elevator()
b = Elevator()
a.add_stop(3)
print(b._stops)
print(a._stops is b._stops)
```

Two cars, one shared to-do list: press a button for car A and car B also heads there. That's exactly the kind of bug encapsulation is meant to prevent, and it hides in plain sight.

## A state machine: four states and clear rules

What is an elevator *doing* right now? At any moment it is in exactly one of four **states**:

| State | Meaning |
|---|---|
| `IDLE` | stopped, doors shut, waiting for work |
| `MOVING_UP` / `MOVING_DOWN` | travelling one floor per tick |
| `DOORS_OPEN` | stopped at a floor, people getting in |

Each **tick** (one second of time), a rule picks the next state from the current state, the floor and the target. Writing the rules as a tiny table, instead of scattering `if`s and flags like `is_moving` and `doors_open` all over the code, makes impossible combinations (moving with the doors open!) impossible to even represent. This is a **state machine**.

```exercise
title: next_state

---prompt
Write `next_state(state, floor, target)`. `target` is the floor to head for, or `None` if there's no work. Rules, checked in this order:

1. If the doors are open, they close: the next state is `"IDLE"`.
2. No target: `"IDLE"`.
3. Target above: `"MOVING_UP"`. Below: `"MOVING_DOWN"`.
4. Already at the target: `"DOORS_OPEN"`.
---starter

    # your code here
    return state
---solution
def next_state(state, floor, target):
    if state == "DOORS_OPEN":
        return "IDLE"
    if target is None:
        return "IDLE"
    if target > floor:
        return "MOVING_UP"
    if target < floor:
        return "MOVING_DOWN"
    return "DOORS_OPEN"
---tests
assert next_state("IDLE", 0, None) == "IDLE", "no work: stay idle"
assert next_state("IDLE", 0, 5) == "MOVING_UP", "target above: go up"
assert next_state("MOVING_UP", 5, 2) == "MOVING_DOWN", "target below: go down"
assert next_state("MOVING_UP", 5, 5) == "DOORS_OPEN", "arrived: open the doors"
assert next_state("DOORS_OPEN", 5, 7) == "IDLE", "doors must close before the car moves again, even if there's more work"
---hint
Check the rules top to bottom with `if ... return`. The order matters: rule 1 must win even when there is a target.
```

Here is the whole elevator ticking with those rules. Read the trace: notice the car never moves in the same tick that its doors are open.

```run
title: An elevator ticking through its states
def next_state(state, floor, target):
    if state == "DOORS_OPEN" or target is None:
        return "IDLE"
    return "MOVING_UP" if target > floor else "MOVING_DOWN" if target < floor else "DOORS_OPEN"

class Elevator:
    def __init__(self):
        self.floor, self.state, self.stops = 0, "IDLE", [3, 1]

    def tick(self):
        target = self.stops[0] if self.stops else None
        self.state = next_state(self.state, self.floor, target)
        if self.state == "MOVING_UP":
            self.floor += 1
        elif self.state == "MOVING_DOWN":
            self.floor -= 1
        elif self.state == "DOORS_OPEN":
            self.stops.pop(0)

e = Elevator()
for t in range(1, 10):
    e.tick()
    print(f"t={t}  floor={e.floor}  {e.state}")
```

## Swap the brain: scheduling policies

Who decides *which* stop comes first? Put that decision in its own object, a **policy** with one method, `choose(floor, direction, requests)`. The elevator just asks it. Then you can swap policies without touching the elevator. This is the **strategy pattern**.

Two policies to compare:

- **FIFO** (first in, first out): go to whoever pressed first. Simple, but blind to where the car already is.
- **SCAN** (the "elevator algorithm"): keep going in your current direction and stop at every request on the way; turn around only when nothing is left ahead.

```exercise
title: scan_policy
kind: write
---prompt
Write the `Scan` policy. `choose(floor, direction, requests)` returns `(target, direction)`:

- No requests: `(None, direction)`.
- "Ahead" means `r >= floor` when going `"up"`, or `r <= floor` when going `"down"`.
- If nothing is ahead, flip the direction; then everything left is ahead.
- Pick the nearest request among those ahead.
---starter

    def choose(self, floor, direction, requests):
        if not requests:
            return None, direction
        return requests[0], direction

    def choose(self, floor, direction, requests):
        # your code here
        return None, direction
---solution
class Fifo:
    def choose(self, floor, direction, requests):
        if not requests:
            return None, direction
        return requests[0], direction

class Scan:
    def choose(self, floor, direction, requests):
        if not requests:
            return None, direction
        ahead = [r for r in requests if (r >= floor if direction == "up" else r <= floor)]
        if not ahead:
            direction = "down" if direction == "up" else "up"
            ahead = list(requests)
        target = min(ahead, key=lambda r: abs(r - floor))
        return target, direction
---tests
s = Scan()
assert s.choose(4, "up", [2, 7, 5]) == (5, "up"), f"going up from 4: the nearest request above is 5, got {s.choose(4, 'up', [2, 7, 5])}"
assert s.choose(4, "up", [2, 1]) == (2, "down"), "nothing above 4: turn around and take the nearest below"
assert s.choose(4, "down", [4, 9]) == (4, "down"), "a request on the current floor counts as ahead"
assert s.choose(0, "up", []) == (None, "up"), "no requests: no target"
assert Fifo().choose(4, "up", [2, 7]) == (2, "up"), "FIFO is unchanged: just the first request"
---hint
Build the `ahead` list with a comprehension. If it's empty, flip `direction` and use all the requests.
---hint
`min(ahead, key=lambda r: abs(r - floor))` picks the nearest one.
```

Now race them on the same burst from the simulation. The `simulate` function only ever talks to `policy.choose`, so it works with *any* policy object, including ones you haven't written yet.

```run
title: FIFO vs SCAN on the same burst
class Fifo:
    def choose(self, floor, direction, requests):
        return (requests[0] if requests else None), direction

class Scan:
    def choose(self, floor, direction, requests):
        if not requests:
            return None, direction
        ahead = [r for r in requests if (r >= floor if direction == "up" else r <= floor)]
        if not ahead:
            direction, ahead = ("down" if direction == "up" else "up"), requests
        return min(ahead, key=lambda r: abs(r - floor)), direction

def simulate(policy, start, requests):
    floor, direction, pending = start, "up", list(requests)
    travelled, clock, waits = 0, 0, []
    while pending:
        target, direction = policy.choose(floor, direction, pending)
        travelled += abs(target - floor)
        clock += abs(target - floor)
        floor = target
        pending.remove(target)
        waits.append(clock)
    return travelled, sum(waits) / len(waits)

burst = [8, 1, 7, 2, 6, 3, 5]
for p in (Fifo(), Scan()):
    floors, wait = simulate(p, 0, burst)
    print(f"{type(p).__name__:5} travelled {floors:2} floors, average wait {wait:.1f}")
```

```quiz
You want to try a third policy, "nearest request first". What has to change?
- The Elevator class and the simulate function
- Every policy class, so they agree on a new interface
* Only a new class with a `choose` method; nothing else changes
- Nothing; Python picks the best policy automatically
> That's the payoff of the strategy pattern: `simulate` (and the elevator) only depend on "something with a `choose` method". A new policy is one new class plugged in.
```

## Real-world project: a parking garage

The same moves you just made (find the objects, decide who owns which data, pull the decision into a swappable policy) work for almost any system: a parking garage, a ride-share dispatcher, a print queue.

```project

Management wants to try different assignment rules (fill the lowest level first, or spread cars out) without rewriting the system.
---why
This is object modeling as it's done in real back-ends: ride-share dispatch (Rider, Driver, Trip, matching policy), warehouse robots (Shelf, Robot, picking policy), and cloud schedulers (Machine, Job, placement policy) all separate *the things* from *the decision*, so the decision can be tuned and A/B-tested.

- Raise a clear error when the garage is full or a plate is unknown
- Compare two policies by how far drivers walk (or drive) on average
---stretch
- Add spot sizes (motorbike, car, van) and only assign spots that fit
- Add a second entrance and a policy that picks the spot nearest to it
- Charge by the hour: add a `Ticket` object that remembers the arrival time
```

```exercise
class Garage:
    def __init__(self, levels, spots_per_level, policy):
        self._policy = policy
        self._spots = {(l, s): None for l in range(levels) for s in range(spots_per_level)}
        self._where = {}

        return sorted(k for k, v in self._spots.items() if v is None)

        free = self.free_spots()
        if not free:
            raise ValueError("full")

        self._spots[spot] = plate
        self._where[plate] = spot
        return spot

        self._spots[spot] = None
        return spot
```

## Rebuild it and explain it

```exercise
title: scan_elevator
kind: rebuild
---prompt
From memory: write an `Elevator(floor=0)` that runs the SCAN policy as a state machine.

- `call(floor)` adds a stop (ignore duplicates).
- `tick()` returns the new state: doors open → `"IDLE"`; no stops → `"IDLE"`; at a stop → remove it, append it to `self.served`, `"DOORS_OPEN"`; otherwise move one floor toward the SCAN target (add 1 to `self.travelled`), `"MOVING_UP"` or `"MOVING_DOWN"`.
- The car starts with direction `"up"`.
---starter
class Elevator:
    def __init__(self, floor=0):
        self.floor = floor
---solution
class Elevator:
    def __init__(self, floor=0):
        self.floor = floor
        self.state = "IDLE"
        self.direction = "up"
        self.stops = []
        self.served = []
        self.travelled = 0

    def call(self, floor):
        if floor not in self.stops:
            self.stops.append(floor)

    def _target(self):
        if not self.stops:
            return None
        ahead = [s for s in self.stops if (s >= self.floor if self.direction == "up" else s <= self.floor)]
        if not ahead:
            self.direction = "down" if self.direction == "up" else "up"
            ahead = self.stops
        return min(ahead, key=lambda s: abs(s - self.floor))

    def tick(self):
        if self.state == "DOORS_OPEN":
            self.state = "IDLE"
            return self.state
        t = self._target()
        if t is None:
            self.state = "IDLE"
        elif t == self.floor:
            self.stops.remove(t)
            self.served.append(t)
            self.state = "DOORS_OPEN"
        elif t > self.floor:
            self.floor += 1
            self.travelled += 1
            self.state = "MOVING_UP"
        else:
            self.floor -= 1
            self.travelled += 1
            self.state = "MOVING_DOWN"
        return self.state
---tests
e = Elevator(0)
e.call(5); e.call(2)
for _ in range(50):
    e.tick()
assert e.served == [2, 5], f"going up from 0, SCAN stops at 2 on the way to 5; served {e.served}"
assert e.travelled == 5, f"0 to 5 is 5 floors, got {e.travelled}"
e = Elevator(3)
e.call(5); e.call(1); e.call(4); e.call(4)
for _ in range(50):
    e.tick()
assert e.served == [4, 5, 1], f"from 3 going up: 4, 5, then turn around for 1; served {e.served}"
assert e.travelled == 6, "3→5 is 2 floors, 5→1 is 4 more"
f = Elevator(0); f.call(1)
assert f.tick() == "MOVING_UP" and f.tick() == "DOORS_OPEN" and f.tick() == "IDLE", "move, open, then close"
---hint
Keep the SCAN choice in a helper method. `tick()` is then the four-state rule from earlier, plus moving one floor.
```

```recall

A: Because "how do I move" and "where should I go next" are different responsibilities. With the policy as a separate object that has one method (`choose`), the elevator only asks it for a target, so you can swap FIFO for SCAN (or a new policy) without editing or re-testing the elevator, and compare them fairly on the same inputs. That's the strategy pattern; composition lets the Building plug in whichever policy it wants.
```

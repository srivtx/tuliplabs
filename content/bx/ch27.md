## Why build tools exist

A big program is thousands of files. Turning them into an app means running thousands of commands: compile each source file, then link the results. Rerunning all of them after every edit could take an hour. A **build system** remembers what each output is made from, and after an edit it reruns only the commands whose inputs changed.

`make` (1976) does it with one rule: **a target is stale if any of its inputs is newer than it.** Modern tools (Bazel, Gradle, Cargo, Vite, Turborepo) refine the idea with content hashes, caches and parallel builds, but the graph is the same.

## Stale or up to date?

Each file has a modified time (`os.path.getmtime` in Python). A **target** has a list of inputs and a command that makes it. It must be rebuilt if it doesn't exist yet, or if any input was modified after it was.

```exercise
title: is_stale
kind: write
---prompt
Write `is_stale(target, inputs, mtime)`. `mtime` is a dict from file name to modified time; a file missing from it doesn't exist. Return `True` if the target doesn't exist or any input is newer than it. An input that doesn't exist is an error: raise `FileNotFoundError` with its name.
---starter
def is_stale(target, inputs, mtime):
    return True
---solution
def is_stale(target, inputs, mtime):
    for i in inputs:
        if i not in mtime:
            raise FileNotFoundError(i)
    if target not in mtime:
        return True
    return any(mtime[i] > mtime[target] for i in inputs)
---tests
m = {"main.c": 5, "util.h": 9, "main.o": 7}
assert is_stale("main.o", ["main.c", "util.h"], m), "util.h is newer"
assert not is_stale("main.o", ["main.c"], m)
assert is_stale("app", ["main.o"], m), "app doesn't exist yet"
try:
    is_stale("main.o", ["gone.c"], m)
    assert False
except FileNotFoundError:
    pass
---hint
Check the inputs exist first, then the target, then compare times with `any(...)`.
```

```predict
mtime = {"util.h": 20, "main.o": 15, "app": 16}
print(mtime["util.h"] > mtime["main.o"])
print(mtime["main.o"] > mtime["app"])
```

That second line is the trap. `app` is built from `main.o`, and right now `main.o` is *older* than `app`, so `app` looks up to date. But `main.o` is stale, and once it's rebuilt it will be newer than `app`. So you must **build the inputs first**, then decide about the target.

A file with no rule is a source file: there's nothing to build, it just has to exist. A target is built only after `build` has been called on each of its inputs, so their times are up to date when you compare.

## Reading a Makefile

A Makefile writes the same rules as text. A rule line is `target: input input ...`, and the command is on the next line, indented with a **tab** (make famously refuses spaces). Lines starting with `#` are comments.

```exercise
title: parse_makefile
kind: write
---prompt
Write `parse_makefile(text)` that returns a dict `{target: (inputs, command)}`. Inputs is a list (it may be empty); the command is the stripped text of the tab-indented line after the rule, or `""` if there isn't one. Skip blank lines and `#` comments.
---starter
def parse_makefile(text):
    return {}
---solution
def parse_makefile(text):
    rules, current = {}, None
    for line in text.split("\n"):
        if not line.strip() or line.lstrip().startswith("#"):
            continue
        if line.startswith("\t"):
            inputs, _ = rules[current]
            rules[current] = (inputs, line.strip())
        else:
            target, rest = line.split(":", 1)
            current = target.strip()
            rules[current] = (rest.split(), "")
    return rules
---tests
mk = "# build the app\napp: main.o util.o\n\tcc -o app main.o util.o\n\nmain.o: main.c util.h\n\tcc -c main.c\nclean:\n\trm -f *.o app\nall: app\n"
r = parse_makefile(mk)
assert r["app"] == (["main.o", "util.o"], "cc -o app main.o util.o")
assert r["main.o"] == (["main.c", "util.h"], "cc -c main.c")
assert r["clean"] == ([], "rm -f *.o app"), "no inputs"
assert r["all"] == (["app"], ""), "no command"
---hint
Remember which target you're in. A line starting with `"\t"` is its command; any other line is a new rule split on the first `:`.
```

## When times lie

```quiz
You run `git checkout` to an older branch and back. Every file you touched now has a brand new modified time, though its content is the same as before. What does make do?
- Nothing: make compares content
* Rebuilds everything those files feed into, because they look newer
- Refuses to build
- Rebuilds only files whose content changed
> make only sees times. Times also break with clocks that differ between machines, or a file restored from a backup with an *old* time (then make wrongly skips it). That's why Bazel, Cargo and ccache key their work on a **hash of the content** instead.
```

```exercise
title: hash_stale
kind: write
---prompt
Write `needs_rebuild(target, inputs, contents, record)` for a hash-based build. `contents` maps each input to its current text. `record` maps each target to the fingerprint it was last built from (missing = never built). The fingerprint is the SHA-256 hex digest of the inputs' contents joined in order with `"\0"`. Return `True` if the target must be rebuilt, and in that case store the new fingerprint in `record`.
---starter
import hashlib

def needs_rebuild(target, inputs, contents, record):
    return True
---solution
import hashlib

def needs_rebuild(target, inputs, contents, record):
    fp = hashlib.sha256("\0".join(contents[i] for i in inputs).encode()).hexdigest()
    if record.get(target) == fp:
        return False
    record[target] = fp
    return True
---tests
rec = {}
c = {"main.c": "int main(){}", "util.h": "#define N 3"}
assert needs_rebuild("main.o", ["main.c", "util.h"], c, rec), "never built"
assert not needs_rebuild("main.o", ["main.c", "util.h"], c, rec), "same content: skip, whatever the times say"
c["util.h"] = "#define N 4"
assert needs_rebuild("main.o", ["main.c", "util.h"], c, rec)
c["util.h"] = "#define N 3"
assert needs_rebuild("main.o", ["main.c", "util.h"], c, rec), "content changed back: differs from the last build"
---hint
`hashlib.sha256(text.encode()).hexdigest()`. Compare it with `record.get(target)` before storing it.
```

## Building in parallel

`make -j8` runs up to 8 commands at once. Two targets can build at the same time when neither needs the other. Group the targets into **levels**: level 0 needs only source files, level 1 needs only level 0 and sources, and so on. Everything in one level can run in parallel.

```exercise
title: build_levels
kind: write
---prompt
Write `levels(rules)` where `rules` maps each target to its list of inputs (inputs without a rule are source files). Return a list of levels, each a **sorted** list of targets, where a target's level is one more than the highest level among its target inputs (0 if its inputs are all sources).
---starter
def levels(rules):
    return []
---solution
def levels(rules):
    memo = {}
    def level(t):
        if t not in memo:
            memo[t] = 1 + max((level(i) for i in rules[t] if i in rules), default=-1)
        return memo[t]
    out = []
    for t in rules:
        lv = level(t)
        while len(out) <= lv:
            out.append([])
        out[lv].append(t)
    return [sorted(l) for l in out]
---tests
rules = {"app": ["main.o", "util.o", "net.o"], "main.o": ["main.c"], "util.o": ["util.c"], "net.o": ["net.c"], "docs": ["README"], "release": ["app", "docs"]}
assert levels(rules) == [["docs", "main.o", "net.o", "util.o"], ["app"], ["release"]]
assert levels({}) == []
---hint
A recursive `level(t)` with a memo dict. `max(..., default=-1)` makes the level 0 when there are no target inputs.
```

## Real-world project: an incremental static-site builder

```project
title: A blog builder that rebuilds only the pages you touched
client: A food blogger with 900 posts whose site generator takes 6 minutes every time they fix a typo
skills: dependency graphs, hashing, caching, file systems
---brief
Build `site.py`: turn a folder of Markdown posts into HTML pages using templates and shared includes (header, footer). Record what each page was built from (its post, its template, the includes the template uses) and a hash of each. On the next run, rebuild only the pages whose inputs changed: fixing a typo in one post rebuilds one page, and editing the footer rebuilds them all. Print what was rebuilt and why, and time it.
---why
Every site generator, bundler and CI system lives or dies by this. Build caches that skip unchanged work save companies millions of compute hours a year.
---milestones
- Build every page from post + template + includes
- Record each page's inputs and their hashes in a JSON file
- Rebuild only pages with a changed input, and say which input changed
- Delete pages whose post was deleted
- Build independent pages in parallel with a thread pool
---stretch
- A `--watch` mode that rebuilds on save
- An index page that depends on every post's title, but not its body
- A shared cache, so two people never build the same page twice
```

```exercise
title: pages_to_rebuild
kind: write
---prompt
Write `pages_to_rebuild(changed, uses)`. `uses` maps each file to the files it uses directly: a page uses its post and a template, a template uses includes. Return the sorted list of **pages** (keys of `uses` whose name ends in `.html`) that use any file in the set `changed`, directly or indirectly.
---starter
def pages_to_rebuild(changed, uses):
    return []
---solution
def pages_to_rebuild(changed, uses):
    def affected(f, seen=()):
        if f in changed:
            return True
        return any(affected(u, seen + (f,)) for u in uses.get(f, []) if u not in seen)
    return sorted(p for p in uses if p.endswith(".html") and affected(p))
---tests
uses = {"pasta.html": ["pasta.md", "post.tpl"], "soup.html": ["soup.md", "post.tpl"], "index.html": ["index.tpl"], "post.tpl": ["footer.inc"], "index.tpl": ["header.inc"]}
assert pages_to_rebuild({"pasta.md"}, uses) == ["pasta.html"]
assert pages_to_rebuild({"footer.inc"}, uses) == ["pasta.html", "soup.html"], "through the template"
assert pages_to_rebuild({"header.inc", "soup.md"}, uses) == ["index.html", "soup.html"]
assert pages_to_rebuild(set(), uses) == []
---hint
A recursive "does this file use anything in `changed`?" check, applied to every page.
```

## Rebuild it and explain it

```exercise
title: make_rebuild
kind: rebuild
---prompt
From memory: write `build(target, rules, mtime, ran)`. `rules` maps a target to `(inputs, command)`; files without a rule are sources. Build the inputs first, then, if the target is missing from `mtime` or older than any input, append its command to the list `ran` and set its time to one more than the largest time in `mtime`.
---starter
def build(target, rules, mtime, ran):
    pass
---solution
def build(target, rules, mtime, ran):
    if target not in rules:
        return
    inputs, command = rules[target]
    for i in inputs:
        build(i, rules, mtime, ran)
    if target not in mtime or any(mtime[i] > mtime[target] for i in inputs):

```

```recall
Q: Explain how make decides what to rebuild after you edit a file, and one weakness of its approach.
A: The build is a graph: each target has inputs and a command that makes it from them, and files with no rule are sources. To build a target, make first builds each of its inputs recursively, so their times are current, and only then compares: if the target is missing or any input has a newer modified time, it runs the command, which gives the target a new time; otherwise it skips it. So editing a header rebuilds every object file that includes it and then relinks the app, while untouched parts are skipped. Checking staleness before building the inputs would miss changes that arrive through an intermediate file. The weakness is that it trusts modified times: a checkout, a copied file or a skewed clock can make unchanged files look new or changed files look old, so tools like Bazel and Cargo compare hashes of the content instead. Targets whose inputs don't depend on each other can be built in parallel, level by level.
```

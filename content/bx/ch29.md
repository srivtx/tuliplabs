## What pytest does for you

You write `def test_total(): assert cart.total() == 3` and run `pytest`. Behind that one word, a framework **finds** every function whose name starts with `test_`, **runs** each one, **catches** whatever goes wrong so the next test still runs, and **reports** what passed and failed. It also hands each test the objects it needs (**fixtures**), fresh every time.

That last part matters more than it looks. Tests that share state can pass or fail depending on the order they run in, which is the worst kind of test: a red result that isn't the code's fault.

## Finding and running tests

A Python module is a namespace: a dict from names to objects (`globals()`, or `vars(module)`). Discovery is just a loop over it.

```exercise
title: run_tests
kind: write
---prompt
Write `run_tests(namespace)`. For every name in the dict `namespace` that starts with `test_` and whose value is callable, call it with no arguments, in sorted name order. Return a dict from test name to `"pass"`, `"fail"` (it raised `AssertionError`) or `"error"` (any other exception). One failing test must not stop the others.
---starter
def run_tests(namespace):
    return {}
---solution
def run_tests(namespace):
    results = {}
    for name in sorted(namespace):
        fn = namespace[name]
        if not name.startswith("test_") or not callable(fn):
            continue
        try:
            fn()
            results[name] = "pass"
        except AssertionError:
            results[name] = "fail"
        except Exception:
            results[name] = "error"
    return results
---tests
def test_ok(): assert 1 + 1 == 2
def test_bad(): assert 1 + 1 == 3
def test_crash(): return {}["missing"]
def helper(): raise RuntimeError("not a test")
ns = {"test_ok": test_ok, "test_bad": test_bad, "test_crash": test_crash, "helper": helper, "test_value": 42}
assert run_tests(ns) == {"test_bad": "fail", "test_crash": "error", "test_ok": "pass"}
---hint
Two `except` clauses: `AssertionError` first, then `Exception`. Skip names that don't start with `test_` and values that aren't callable.
```

```predict
try:
    assert 2 + 2 == 5, "maths is broken"
except AssertionError as e:
    print("fail:", e)
try:
    [1, 2][5]
except AssertionError:
    print("fail")
except Exception as e:
    print("error:", type(e).__name__)
```

A **failure** means the code gave a wrong answer: an `assert` didn't hold. An **error** means the test itself crashed before it could check anything. pytest reports them separately because they need different fixes.

```exercise
title: stop_bug
kind: bug
---prompt
This runner stops at the first failing test, so one broken test hides how many others are broken. Make it run every test and return the list of names that **didn't** pass, in the order they ran.
---starter
def failures(tests):
    bad = []
    for fn in tests:
        fn()
    return bad
---solution
def failures(tests):
    bad = []
    for fn in tests:
        try:
            fn()
        except Exception:
            bad.append(fn.__name__)
    return bad
---tests
def test_a(): assert True
def test_b(): assert False
def test_c(): raise ValueError
def test_d(): assert 3 > 2
assert failures([test_a, test_b, test_c, test_d]) == ["test_b", "test_c"]
---hint
Wrap each call in `try` / `except Exception` and record `fn.__name__` when it raises. (`AssertionError` is an `Exception` too.)
```

## Checking for exceptions

Good tests also check that bad input is *rejected*. pytest writes it as `with pytest.raises(ValueError):`. Under the hood that's a context manager whose `__exit__` looks at the exception that happened inside the block.

```parsons
title: A raises() context manager
---lines
class raises:
    def __init__(self, expected):
        self.expected = expected
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            raise AssertionError(f"did not raise {self.expected.__name__}")
        return issubclass(exc_type, self.expected)
?? return True
?? if exc_type is self.expected:
---tests
with raises(ValueError):
    int("abc")
try:
    with raises(ValueError):
        int("42")
    assert False, "should complain that nothing was raised"
except AssertionError as e:
    assert "did not raise ValueError" in str(e)
try:
    with raises(ValueError):
        {}["k"]
    assert False
except KeyError:
    pass
```

`__exit__` returning `True` swallows the exception (the test goes on, it passed). Returning `False` lets an unexpected exception escape, so the test errors. `issubclass` means `raises(Exception)` also accepts a `ValueError`.

## Fixtures: a fresh start for every test

```quiz
The simulation's tests passed in the written order and failed when shuffled. Where was the bug?
- In the cart's code
* In the tests: they shared one cart, so each depended on what earlier tests left in it
- In the shuffle
- In Python's random number generator
> The cart worked. The tests silently relied on running in one particular order. pytest-randomly shuffles on purpose to catch this; fixtures prevent it.
```

pytest looks at a test's parameter names and, for each one, calls the fixture function with that name to make a fresh object: `def test_total(cart):` gets a new cart every time.

```exercise
title: fixtures
kind: write
---prompt
Write `run_with_fixtures(tests, fixtures)`. `tests` is a list of functions; `fixtures` maps a name to a zero-argument function that builds a fresh object. For each test, read its parameter names with `inspect.signature(fn).parameters`, build a **new** object for each one by calling the fixture with that name, and call the test with them as keyword arguments. Return a dict from test name to `"pass"` or `"fail"` (any exception).
---starter
import inspect

def run_with_fixtures(tests, fixtures):
    return {}
---solution
import inspect

def run_with_fixtures(tests, fixtures):
    results = {}
    for fn in tests:
        args = {name: fixtures[name]() for name in inspect.signature(fn).parameters}
        try:
            fn(**args)
            results[fn.__name__] = "pass"
        except Exception:
            results[fn.__name__] = "fail"
    return results
---tests
fixtures = {"cart": list, "prices": lambda: {"pear": 3, "apple": 2}}
def test_add(cart): cart.append("apple"); assert cart == ["apple"]
def test_empty(cart): assert cart == []
def test_total(cart, prices): cart.append("pear"); assert sum(prices[x] for x in cart) == 3
def test_plain(): assert True
r = run_with_fixtures([test_add, test_empty, test_total, test_plain], fixtures)
assert r == {"test_add": "pass", "test_empty": "pass", "test_total": "pass", "test_plain": "pass"}, r
---hint
`{name: fixtures[name]() for name in inspect.signature(fn).parameters}`: the `()` makes a new object for every test.
```

## One test, many inputs

```exercise
title: parametrize
kind: write
---prompt
Write `parametrize(fn, cases)` that runs `fn(*case)` for each tuple in `cases` and returns a dict from an id like `"test_square[0]"`, `"test_square[1]"`, … (the function's name and the case's index) to `"pass"` or `"fail"` (any exception). That's how pytest reports `@pytest.mark.parametrize`.
---starter
def parametrize(fn, cases):
    return {}
---solution
def parametrize(fn, cases):
    out = {}
    for i, case in enumerate(cases):
        try:
            fn(*case)
            out[f"{fn.__name__}[{i}]"] = "pass"
        except Exception:
            out[f"{fn.__name__}[{i}]"] = "fail"
    return out
---tests
def test_square(x, expected): assert x * x == expected
r = parametrize(test_square, [(2, 4), (3, 9), (4, 15)])
assert r == {"test_square[0]": "pass", "test_square[1]": "pass", "test_square[2]": "fail"}
assert parametrize(test_square, []) == {}
---hint
`enumerate(cases)` gives the index; `fn(*case)` unpacks the tuple into arguments.
```

## Real-world project: an autograder

```project
title: A tiny pytest that grades student homework
client: A secondary-school computing teacher grading 90 Python homework files by hand every week
skills: introspection, exceptions, context managers, timing, reporting
---brief
Build `grade.py HOMEWORK_DIR TESTS.py`: import each student's file, discover the test functions in `TESTS.py`, run every test against every submission with fresh fixtures, and stop any single test after 2 seconds (an infinite loop shouldn't freeze the grader). Report per student: passed, failed (with the assertion message) and errored (with the exception type), plus a score, and write a CSV for the gradebook. Compare floats with a tolerance so `0.1 + 0.2` counts as `0.3`.
---why
Every CI system, autograder and coding interview platform is a test runner underneath. Building one shows exactly what `assert`, fixtures and "flaky test" mean.
---milestones
- Discover and run test functions, separating failures from errors
- Fresh fixtures for every test
- `approx` for floats, and `raises` for expected exceptions
- A per-test time limit
- A summary line and a CSV of scores
---stretch
- Shuffle test order with a printed seed, so a flaky failure can be replayed
- Show the line of the failed assert (look at the traceback)
- Run students in parallel with a process pool
```

```exercise
title: approx
kind: write
---prompt
Floats can't be compared with `==` (`0.1 + 0.2 == 0.3` is `False`). Write `approx(actual, expected, rel=1e-6, abs_=1e-12)` that returns `True` when `|actual - expected|` is at most the larger of `rel * |expected|` and `abs_`. Like pytest's `approx`.
---starter
def approx(actual, expected, rel=1e-6, abs_=1e-12):
    return actual == expected
---solution
def approx(actual, expected, rel=1e-6, abs_=1e-12):
    return abs(actual - expected) <= max(rel * abs(expected), abs_)
---tests
assert approx(0.1 + 0.2, 0.3)
assert not approx(0.31, 0.3)
assert approx(1_000_000.4, 1_000_000.0), "relative: 0.4 in a million is fine"
assert approx(1e-14, 0.0), "near zero, the absolute tolerance applies"
assert not approx(1e-3, 0.0)
---hint
One line: compare the difference with `max(rel * abs(expected), abs_)`.
```

```exercise
title: summary_line
kind: write
---prompt
Write `summary(results, seconds)` that builds pytest's last line from a dict of test name → `"pass"`, `"fail"` or `"error"`: for example `"3 passed, 1 failed, 1 error in 0.42s"`. List only the kinds that occurred, in the order passed, failed, error (the word is `"errors"` when there's more than one). Seconds get 2 decimals. With no tests at all, return `"no tests ran in 0.00s"`.
---starter
def summary(results, seconds):
    return ""
---solution
def summary(results, seconds):
    vals = list(results.values())
    parts = []
    for kind, word in (("pass", "passed"), ("fail", "failed"), ("error", "error")):
        n = vals.count(kind)
        if n:
            parts.append(f"{n} {word}{'s' if kind == 'error' and n > 1 else ''}")
    return f"{', '.join(parts) or 'no tests ran'} in {seconds:.2f}s"
---tests
r = {"a": "pass", "b": "pass", "c": "fail", "d": "pass", "e": "error"}
assert summary(r, 0.4213) == "3 passed, 1 failed, 1 error in 0.42s"
assert summary({"a": "error", "b": "error"}, 1) == "2 errors in 1.00s"
assert summary({"a": "pass"}, 0.05) == "1 passed in 0.05s"
assert summary({}, 0) == "no tests ran in 0.00s"
---hint
Count each kind with `list.count`, skip zeros, and join the parts with `", "`.
```

```recall
Q: Explain what a test framework like pytest does when you run it, and why fixtures matter.
A: It discovers tests by looking through each module's namespace for callables named test_..., then runs each one inside try/except so one failure doesn't stop the rest. An AssertionError is reported as a failure (the code gave a wrong answer); any other exception is an error (the test crashed). It reports every result and a summary line. Helpers like raises() are context managers whose __exit__ checks that the expected exception happened, and approx() compares floats with a tolerance. Fixtures are functions that build fresh objects; the runner reads each test's parameter names and passes a new object for each, so tests don't share state. Without them, tests can pass only because of what earlier tests left behind, and fail when the order changes: a flaky test that isn't the code's fault. Parametrize runs one test over many inputs, each reported separately.
```

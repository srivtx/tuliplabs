## What changed?

Every code review, every `git diff`, every "track changes" in a document answers one question: **given an old version and a new version, what is the smallest set of lines that were added and removed?** The obvious way is to compare line 1 with line 1, line 2 with line 2, and so on. It breaks the moment someone adds a line near the top: everything below shifts by one, and every line looks different.

The real answer is to find the **longest common subsequence** (LCS): the most lines both files share, in the same order. Those lines were kept. Everything else in the old file was removed, and everything else in the new file was added.

## The naive diff

```predict
old = ["a", "b", "c", "d"]
new = ["x", "a", "b", "c", "d"]
changed = 0
for i in range(max(len(old), len(new))):
    if i >= len(old) or i >= len(new) or old[i] != new[i]:
        changed += 1
print(changed)
print(len(set(old) & set(new)))
```

Comparing by position says 5 lines differ, although only one line (`x`) is new. The four shared lines are all still there, in the same order, just shifted down.

## The longest common subsequence

A **subsequence** keeps some items in their original order, with gaps allowed: `a c d` is a subsequence of `a b c d`. The LCS of two files is the longest list of lines that's a subsequence of both.

Build a table where `t[i][j]` is the LCS length of the first `i` old lines and the first `j` new lines. Row 0 and column 0 are all 0 (an empty file shares nothing). Then, for each cell:

- if old line `i` equals new line `j`, the LCS can use it: `t[i][j] = t[i-1][j-1] + 1`
- otherwise drop the last line of one file or the other, whichever keeps more: `t[i][j] = max(t[i-1][j], t[i][j-1])`

That's the height of each cell in the simulation, and the answer sits in the bottom-right corner.

```exercise
title: lcs_length
kind: write
---prompt
Write `lcs_table(a, b)` that builds the table above as a list of `len(a) + 1` lists, each of length `len(b) + 1`, and `lcs_length(a, b)` that returns the bottom-right value. `a` and `b` are lists (or strings: the code is the same).
---starter
def lcs_table(a, b):
    return [[0]]

def lcs_length(a, b):
    return 0
---solution
def lcs_table(a, b):
    t = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i - 1] == b[j - 1]:
                t[i][j] = t[i - 1][j - 1] + 1
            else:
                t[i][j] = max(t[i - 1][j], t[i][j - 1])
    return t

def lcs_length(a, b):
    return lcs_table(a, b)[len(a)][len(b)]
---tests
assert lcs_length(["a", "b", "c", "d"], ["x", "a", "b", "c", "d"]) == 4
assert lcs_length("ABCBDAB", "BDCABA") == 4, "the textbook example: BCBA"
assert lcs_length([], ["a"]) == 0
t = lcs_table("ab", "b")
assert len(t) == 3 and len(t[0]) == 2, "one extra row and column of zeros"
assert t[2][1] == 1
---hint
`[[0] * (len(b) + 1) for _ in range(len(a) + 1)]` makes the table. Remember the lists are 0-based: row `i` talks about `a[i - 1]`.
```

## From the table to a diff

The length alone isn't a diff. To find *which* lines were kept, start at the bottom-right corner and walk back to the top-left:

- if the two current lines are equal, they're **kept**: step diagonally
- otherwise step toward the neighbour with the bigger value: stepping left means the new line was **added**, stepping up means the old line was **removed**

You collect the steps backwards, so reverse them at the end. In the simulation that's the yellow and green path.

```parsons
title: Walk the table back into a diff
---setup
def lcs_table(a, b):
    t = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            t[i][j] = t[i - 1][j - 1] + 1 if a[i - 1] == b[j - 1] else max(t[i - 1][j], t[i][j - 1])
    return t
---lines
def diff(a, b):
    t = lcs_table(a, b)
    i, j, ops = len(a), len(b), []
    while i > 0 or j > 0:
        if i > 0 and j > 0 and a[i - 1] == b[j - 1]:
            ops.append((" ", a[i - 1]))
            i, j = i - 1, j - 1
        elif j > 0 and (i == 0 or t[i][j - 1] >= t[i - 1][j]):
            ops.append(("+", b[j - 1]))
            j -= 1
        else:
            ops.append(("-", a[i - 1]))
            i -= 1
    return ops[::-1]
```

```exercise
title: count_changes
kind: write
---prompt
`diff(a, b)` from the puzzle is ready. Write `summary(a, b)` that returns the string git prints after a commit, like `"1 insertion(+), 2 deletions(-)"`. Count the `"+"` and `"-"` operations.

    return t
def diff(a, b):
    t = lcs_table(a, b)
    i, j, ops = len(a), len(b), []
    while i > 0 or j > 0:
        if i > 0 and j > 0 and a[i - 1] == b[j - 1]:
            ops.append((" ", a[i - 1])); i, j = i - 1, j - 1
        elif j > 0 and (i == 0 or t[i][j - 1] >= t[i - 1][j]):
            ops.append(("+", b[j - 1])); j -= 1
        else:
            ops.append(("-", a[i - 1])); i -= 1
    return ops[::-1]
---starter
def summary(a, b):
    return ""
---solution
def summary(a, b):
    ops = diff(a, b)
    plus = sum(1 for tag, _ in ops if tag == "+")
    minus = sum(1 for tag, _ in ops if tag == "-")
    s = lambda n: "" if n == 1 else "s"
    return f"{plus} insertion{s(plus)}(+), {minus} deletion{s(minus)}(-)"
---tests
assert summary(["a", "b"], ["x", "a", "b"]) == "1 insertion(+), 0 deletions(-)"
assert summary(["a", "b", "c"], ["a"]) == "0 insertions(+), 2 deletions(-)"
assert summary(["a", "b"], ["a", "c"]) == "1 insertion(+), 1 deletion(-)", "a changed line is one of each"
---hint
"insertion" gets an `s` unless the count is exactly 1; same for "deletion".
```

```quiz
Filling the table takes one step per cell. For two files of 10,000 lines each, roughly how many steps is that, and what does git do about it?
- 20,000: it's fast enough
* 100 million: git uses Myers' algorithm, which is quick when the files are mostly the same
- 10,000: one per line
- It's impossible, so git compares by position
> The table has len(a) × len(b) cells. Myers' algorithm finds the same kind of shortest edit, but its work grows with the number of *differences*, which is small for a typical commit.
```

## Hunks: changes with a little context

A real diff doesn't print the whole file. It prints **hunks**: each run of changes plus a few unchanged lines around it (git uses 3), so you can see where the change sits. Hunks that would overlap or touch are merged into one.

```exercise
title: hunks
kind: write
---prompt
Write `hunks(ops, context=1)` that takes a diff (a list of `(tag, line)` with tags `" "`, `"+"`, `"-"`) and returns the hunks as a list of `(start, end)` index ranges into `ops`, `end` exclusive. Each changed op gets up to `context` ops on each side; ranges that overlap or touch merge. No changes means no hunks.
---starter
def hunks(ops, context=1):
    return []
---solution
def hunks(ops, context=1):
    out = []
    for k, (tag, _) in enumerate(ops):
        if tag == " ":
            continue
        s, e = max(0, k - context), min(len(ops), k + context + 1)
        if out and s <= out[-1][1]:
            out[-1] = (out[-1][0], e)
        else:
            out.append((s, e))
    return out
---tests
ops = [(" ", "a"), (" ", "b"), ("+", "x"), (" ", "c"), (" ", "d"), (" ", "e"), (" ", "f"), ("-", "g"), (" ", "h")]
assert hunks(ops, 1) == [(1, 4), (6, 9)]
assert hunks(ops, 2) == [(0, 9)], "with more context the two hunks touch, so they merge"
assert hunks(ops, 0) == [(2, 3), (7, 8)]
assert hunks([(" ", "a")]) == []
---hint
For each changed index `k`, its range is `k - context` to `k + context + 1`, clipped to the list. If it starts at or before the end of the last range, extend that one instead.
```

```exercise
Write `similarity(a, b)`, the score Python's `difflib` calls the ratio: `2 * LCS length / (len(a) + len(b))`, rounded to 2 decimal places. It's 1.0 for identical texts and 0.0 when they share nothing. Two empty texts count as identical. `lcs_length` is ready, and works on strings or lists.

        for j in range(1, len(b) + 1):

    return 0.0
---solution

    if not a and not b:
        return 1.0
    return round(2 * lcs_length(a, b) / (len(a) + len(b)), 2)
```

```exercise
title: apply_patch
kind: write
---prompt
Write `apply_patch(old, ops)` that turns `old` (a list of lines) into the new version using a diff `ops`. Kept (`" "`) and removed (`"-"`) lines must match `old` exactly, in order; if any doesn't, or `ops` doesn't use up all of `old`, the patch doesn't fit this file: raise `ValueError`. Return the list of kept and added lines.
---starter
def apply_patch(old, ops):
    return old
---solution
def apply_patch(old, ops):
    new, k = [], 0
    for tag, line in ops:
        if tag in (" ", "-"):
            if k >= len(old) or old[k] != line:
                raise ValueError(f"patch does not apply at line {k + 1}")
            k += 1
        if tag in (" ", "+"):
            new.append(line)
    if k != len(old):
        raise ValueError("patch does not cover the whole file")
    return new
---tests
ops = [(" ", "Rent is due monthly."), ("-", "Pets are allowed."), ("+", "No pets."), (" ", "Signed.")]
assert apply_patch(["Rent is due monthly.", "Pets are allowed.", "Signed."], ops) == ["Rent is due monthly.", "No pets.", "Signed."]
for bad in (["Rent is due weekly.", "Pets are allowed.", "Signed."], ["Rent is due monthly.", "Pets are allowed.", "Signed.", "Extra."]):
    try:
        apply_patch(bad, ops)
        assert False, "a patch for a different file must be refused"
    except ValueError:
        pass
---hint
Walk `ops` with a pointer `k` into `old`. `" "` and `"-"` both consume an old line (and must match it); `" "` and `"+"` both produce a new line.
```

```recall
Q: Explain how a diff tool finds what changed between two versions of a file, and why it doesn't compare line by line.
A: Comparing line i of the old file with line i of the new one fails as soon as a line is added or removed: everything after it shifts, so unchanged lines look changed. Instead the tool finds the longest common subsequence: the most lines both files share in the same order. A table t[i][j] holds the LCS length of the first i old lines and first j new lines; when the lines are equal it's the diagonal value plus one, otherwise the bigger of the cell above and the cell to the left. Walking back from the bottom-right corner gives the diff: a diagonal step on equal lines keeps a line, a step left adds a new line, a step up removes an old one. The changes are grouped into hunks with a few lines of context. The table costs one step per pair of lines, so git uses Myers' algorithm, whose work grows with the number of differences instead.
```

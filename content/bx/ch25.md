## Memory is fast, databases are not

Reading from memory takes about 100 nanoseconds. Asking a database across the network takes about a millisecond, 10,000 times longer, and the database can only answer so many questions per second. So almost every big website puts a **cache** in front of it: a key → value store in memory (Redis, Memcached) that remembers recent answers. A **hit** is answered from memory; a **miss** goes to the database and the answer is saved for next time.

Two questions decide whether a cache works:

1. **Memory is limited. When it's full, what do you throw away?** The classic answer is the **least recently used** item (LRU): if nobody has asked for it lately, they probably won't soon.
2. **One machine isn't enough. Which machine holds which key?** And what happens when you add a machine?

## An LRU cache

An LRU cache needs two things to be fast: find a key in O(1) (a dict), and find the least recently used key in O(1) (a list ordered by use, where touching a key moves it to the end). Python's `OrderedDict` is both at once: `move_to_end(key)` marks a key as just used, and `popitem(last=False)` removes the oldest.

```exercise
title: LRUCache
kind: write
---prompt
Write a class `LRUCache(capacity)` with:

- `get(key)`: return the value, or `None` on a miss. A hit makes the key the most recently used.
- `put(key, value)`: store it as the most recently used. If that makes the cache hold more than `capacity` items, evict the least recently used one.

Use an `OrderedDict` (imported in the prelude).
---starter
class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity

    def get(self, key):
        return None

    def put(self, key, value):
        pass
---solution
class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return None
        self.data.move_to_end(key)
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)
---tests
c = LRUCache(2)
c.put("a", 1); c.put("b", 2)
assert c.get("a") == 1, "a hit"
c.put("c", 3)
assert c.get("b") is None, "b was least recently used (a was just read)"
assert c.get("a") == 1 and c.get("c") == 3
c.put("a", 10)
c.put("d", 4)
assert c.get("a") == 10 and c.get("c") is None, "updating a counts as using it"
---hint
`get`: `move_to_end(key)` on a hit. `put`: assign, `move_to_end`, then `popitem(last=False)` if it's too big.
```

## How big should it be?

The **hit rate** (hits ÷ requests) is the number that matters: at 90%, the database sees a tenth of the traffic; at 99%, a hundredth. Real traffic is skewed (a few popular items get most of the requests), which is why a small cache can have a high hit rate.

```exercise
title: hit_rate
kind: write
---prompt
Write `hit_rate(requests, capacity)` that replays a list of requested keys through an LRU cache of that capacity (a miss loads the key into the cache) and returns hits ÷ requests. Return `0.0` for no requests.
---starter
def hit_rate(requests, capacity):
    return 0.0
---solution
def hit_rate(requests, capacity):
    if not requests:
        return 0.0
    cache, hits = OrderedDict(), 0
    for k in requests:
        if k in cache:
            hits += 1
            cache.move_to_end(k)
        else:
            cache[k] = True
            if len(cache) > capacity:
                cache.popitem(last=False)
    return hits / len(requests)
---tests
assert hit_rate(["a", "a", "a", "a"], 1) == 0.75, "one miss, then hits"
assert hit_rate(["a", "b", "c"] * 3, 2) == 0.0, "a loop one bigger than the cache: LRU always evicts what's needed next"
assert hit_rate(["a", "b", "c"] * 3, 3) == 6 / 9
assert hit_rate([], 5) == 0.0
---hint
The same replay as the predict block, with a counter for hits.
```

The second test is LRU's famous weak spot: scanning a loop just bigger than the cache gives **zero** hits. Databases guard against it (for example, by keeping pages read once by a big scan out of the main cache).

## Many servers: hash mod N

One machine has maybe 100 GB of memory; big sites cache terabytes. So the keys are split across N servers. The obvious rule is `server = hash(key) % N`. (Use a real hash like MD5 here, not Python's `hash()`, which gives different answers in different processes.)

It works, until N changes. Add a fifth server to four, and a key stays put only if `hash % 4 == hash % 5`, which is true for about 1 key in 5. The other 80% are now looked up on a server that doesn't have them: the cache is effectively empty, and every request lands on the database at once.

```exercise
title: moved_fraction
kind: write
---prompt
Write `moved_fraction(keys, n_old, n_new)` that returns the fraction of `keys` whose server changes when the number of servers goes from `n_old` to `n_new`, using `server = h(key) % n` with `h(key) = int(hashlib.md5(key.encode()).hexdigest(), 16)`.
---starter
def moved_fraction(keys, n_old, n_new):
    return 0.0
---solution
def moved_fraction(keys, n_old, n_new):
    h = lambda k: int(hashlib.md5(k.encode()).hexdigest(), 16)
    moved = sum(h(k) % n_old != h(k) % n_new for k in keys)
    return moved / len(keys)
---tests
keys = [f"user:{i}" for i in range(2000)]
f = moved_fraction(keys, 4, 5)
assert 0.75 < f < 0.85, f"about 80% move, got {f:.2f}"
assert moved_fraction(keys, 4, 4) == 0
assert moved_fraction(keys, 4, 8) < 0.55, "doubling keeps about half"
---hint
A key moves if `h(k) % n_old != h(k) % n_new`; `sum` of booleans counts the `True`s.
```

## Consistent hashing

**Consistent hashing** (1997, the idea behind Akamai, Amazon's Dynamo, Cassandra and many Memcached clients) puts the servers on the same **ring** as the keys: hash each server's name to a point on the ring, and give each key to the **first server clockwise** from it. Add a server, and it takes over only the arc just before it, from one neighbour: about 1/N of the keys move, and everything else stays cached.

With a few servers, the arcs come out uneven by luck, so one server might get twice its share. The fix is **virtual nodes**: put each server on the ring many times (`cache-1#0`, `cache-1#1`, …). Its share becomes the sum of many small arcs, which averages out.

```parsons
title: Find a key's server on the ring
---lines

    i = bisect_left(points, (h, ""))
    if i == len(points):

    return points[i][1]

---setup
def ring_hash(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % 2**32
---tests
points = sorted([(100, "A"), (2**31, "B"), (3 * 2**30, "C")])
def at(h):
    global ring_hash
    old = ring_hash
    ring_hash = lambda s: h
    try:
        return lookup(points, "k")
    finally:
        ring_hash = old
assert at(50) == "A" and at(100) == "A", "up to and including A's point"
assert at(101) == "B" and at(3 * 2**30) == "C"
assert at(2**32 - 1) == "A", "past the last point, wrap around to the first"
```

`points` is a sorted list of `(position, server)`, and `bisect_left` finds the first point at or after the key's position in O(log n).

```exercise
title: HashRing
kind: write
---prompt
Write a class `HashRing(vnodes)` with `add(server)`, `remove(server)` and `lookup(key)`. `add` places the server at the positions `ring_hash(f"{server}#{i}")` for `i` in `range(vnodes)`; keep a sorted list of `(position, server)` pairs. `lookup` returns the server owning the first position at or after `ring_hash(key)`, wrapping around. `ring_hash` is ready for you.
---setup
def ring_hash(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % 2**32
---starter
class HashRing:
    def __init__(self, vnodes):
        self.vnodes = vnodes
        self.points = []

    def add(self, server):
        pass

    def remove(self, server):
        pass

    def lookup(self, key):
        return None
---solution
class HashRing:
    def __init__(self, vnodes):
        self.vnodes = vnodes
        self.points = []

    def add(self, server):
        for i in range(self.vnodes):
            self.points.append((ring_hash(f"{server}#{i}"), server))
        self.points.sort()

    def remove(self, server):
        self.points = [p for p in self.points if p[1] != server]

    def lookup(self, key):
        i = bisect_left(self.points, (ring_hash(key), ""))
        return self.points[i % len(self.points)][1]
---tests
keys = [f"user:{i}" for i in range(3000)]
r = HashRing(100)
for s in ["c0", "c1", "c2", "c3"]: r.add(s)
before = {k: r.lookup(k) for k in keys}
r.add("c4")
after = {k: r.lookup(k) for k in keys}
moved = sum(before[k] != after[k] for k in keys) / len(keys)
assert 0.12 < moved < 0.28, f"about 1/5 should move, got {moved:.2f}"
assert all(after[k] == "c4" for k in keys if before[k] != after[k]), "keys only move to the new server"
loads = [list(after.values()).count(s) for s in ["c0", "c1", "c2", "c3", "c4"]]
assert max(loads) < 1.35 * len(keys) / 5, f"virtual nodes keep the load even: {loads}"
r.remove("c4")
assert all(r.lookup(k) == before[k] for k in keys), "removing it puts every key back"
---hint
`add`: append `vnodes` pairs and sort. `lookup`: `bisect_left` then `% len(self.points)` handles the wrap-around.
```

```quiz
With consistent hashing and 10 servers, one server crashes. Roughly what happens to the cache?
- Every key moves, like hash mod N
* About a tenth of the keys (the crashed server's) move to the servers just after its points; the rest stay cached
- Nothing, because the keys are replicated
- The ring has to be rebuilt from scratch before anything works
> Only that server's arcs change owner. With virtual nodes those arcs are spread around the ring, so its keys are shared among many servers instead of all landing on one neighbour.
```

## Stale data: time to live

A cache holds a **copy**. When the database changes, the copy is wrong until it's replaced. The simplest defence is a **time to live** (TTL): each entry expires a fixed time after it was stored, so nothing stays stale for longer than that. ("There are only two hard things in computer science: cache invalidation and naming things.")


```exercise
title: TTLCache
kind: write
---prompt
Write `TTLCache(ttl)` with `put(key, value, now)` and `get(key, now)`. An entry stored at time `now` is valid while `get`'s `now` is **less than** `stored + ttl`; an expired entry counts as a miss (return `None`) and should be deleted. Times are plain numbers (seconds), passed in so tests don't need to wait.
---starter
class TTLCache:
    def __init__(self, ttl):
        self.ttl = ttl

    def put(self, key, value, now):
        pass

    def get(self, key, now):
        return None
---solution
class TTLCache:
    def __init__(self, ttl):
        self.ttl = ttl
        self.data = {}

    def put(self, key, value, now):
        self.data[key] = (value, now + self.ttl)

    def get(self, key, now):
        if key not in self.data:
            return None
        value, expires = self.data[key]
        if now >= expires:
            del self.data[key]
            return None
        return value
---tests
c = TTLCache(600)
c.put("paris", "14°C", now=0)
assert c.get("paris", now=599) == "14°C"
assert c.get("paris", now=600) is None, "exactly ttl later: expired"
assert "paris" not in c.data, "expired entries are removed"
c.put("oslo", "3°C", now=100)
c.put("oslo", "4°C", now=500)
assert c.get("oslo", now=1000) == "4°C", "storing again restarts the clock"
---hint
Store `(value, now + ttl)`. On `get`, compare `now` with the stored expiry time.
```

```exercise
---prompt
Write `cached_fetch(cache, key, fetch, now)` that returns the cached value if there is one, and otherwise calls `fetch(key)`, stores the result in the cache, and returns it. `cache` is a `TTLCache` like the one above (ready for you). This pattern is called **cache-aside**.

        cache.put(key, value, now)
```

## Rebuild it and explain it

```exercise
title: lru_rebuild
kind: rebuild
---prompt
From memory, using only a plain `dict` (which keeps insertion order in Python): write `lru_access(cache, key, capacity)` that records an access to `key` in the dict `cache` (values can just be `True`) and returns `True` for a hit or `False` for a miss. Evict the least recently used key when it grows past `capacity`.
---starter
def lru_access(cache, key, capacity):
    pass
---solution
def lru_access(cache, key, capacity):
    hit = key in cache
    if hit:
        del cache[key]
    cache[key] = True
    if len(cache) > capacity:
        del cache[next(iter(cache))]
    return hit
---tests
c = {}
assert [lru_access(c, k, 2) for k in ["a", "b", "a", "c", "b", "a"]] == [False, False, True, False, False, False], "c evicts b, then b evicts a"
assert list(c) == ["b", "a"]
---hint
Deleting and re-inserting a key moves it to the end. The first key in iteration order, `next(iter(cache))`, is the oldest.
```

```recall
Q: Explain how a distributed cache decides what to keep and where each key lives, and why consistent hashing matters.
A: Each cache server keeps a bounded key-value store in memory and evicts the least recently used entry when full; with a dict plus a use-ordered list (an OrderedDict), get and put are O(1). Its value is the hit rate, which skewed real traffic makes high even for small caches, though a loop just larger than the cache defeats LRU. Entries also carry a TTL so stale copies expire. To spread keys over N servers, hash mod N is simple but changing N moves almost every key (only about 1/N stay), emptying the cache and flooding the database. Consistent hashing places servers and keys on one hash ring and gives each key to the next server clockwise, so adding or removing a server moves only about 1/N of the keys, to or from its neighbours; many virtual nodes per server even out the arcs and spread a failed server's keys across many others. Clients use cache-aside: read the cache, on a miss fetch from the database and store the result.
```

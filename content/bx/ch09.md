## What happens when you press a key

An editor looks simple: you press `x`, a letter appears. But three questions hide inside:

1. **Storage:** where do the characters live, so that typing in the *middle* of a big file is still instant?
2. **Meaning:** in vim, `x` in NORMAL mode *deletes* a character, while in INSERT mode it *types* an x. How does one key mean two things?
3. **Memory:** how does `u` (undo) know what to put back?

The simulation answers all three. The row of cells is the text in memory; the empty cells are the **gap** (you'll see why soon). The three blocks behind it are the **modes**.

```viz

```

```quiz
You're in NORMAL mode and press `i`, then `x`, then `Esc`, then `x`. What happened to the text?

- Two characters were deleted
* One x was typed, then one character was deleted
- Nothing: `i` cancels the next key
> `i` switches to INSERT mode, where `x` is just a letter. `Esc` goes back to NORMAL, where `x` means "delete the character under the cursor". Same key, different mode, different meaning.
```

## Text as one string

The obvious design: keep the whole file in one string. But Python strings (and Java, JavaScript, Go…) can't be changed in place. To insert one character at position `p`, you build a **new** string: everything before `p`, the new character, everything after. Every character gets copied.

```predict
text = "a" * 10
copied = 0
for _ in range(5):              # type 5 characters at the very start
    copied += len(text)         # the new string copies every old character
    text = "!" + text
print(text)
print(copied)
```

Typing at the start of a 1 MB file would copy a million characters **per keystroke**. At 10 keys a second, that's 10 million copies a second just to keep up. That's why no serious editor stores text as one string.

A first fix: keep a **list of lines**. Typing only rebuilds the one line you're on, and lines are short.

Better, but a very long line (a minified JavaScript file is often one 500 KB line!) is back to the slow case. We want inserts at the cursor to cost the same no matter how long the line is.

## The gap buffer

Here's the trick Emacs has used since the 1980s. Keep the characters in an array with a block of **empty slots** right at the cursor: the **gap**.

```
h e l l o _ _ _ _ w o r l d
          ^gap_start ^gap_end
```

- **Typing** writes into the first empty slot and moves `gap_start` right by one. Nothing else moves. **O(1).**
- **Backspace** just moves `gap_start` left. The character is "deleted" by being inside the gap.
- **Moving the cursor** moves the gap: each step copies *one* character from one side of the gap to the other.

People type in bursts at one spot, then move a bit, then type again. So nearly all the work is the cheap part.

```parsons
title: insert into a gap buffer
---lines
def insert(gb, ch):
    if gb.gap_start == gb.gap_end:
        gb.grow()
    gb.buf[gb.gap_start] = ch
    gb.gap_start += 1
?? gb.buf.insert(gb.gap_start, ch)
?? gb.gap_end += 1
---setup
class GB:
    def __init__(self, text, size):
        self.buf = list(text) + [None] * (size - len(text))
        self.gap_start, self.gap_end = len(text), size
    def grow(self):
        extra = len(self.buf)
        self.buf[self.gap_end:self.gap_end] = [None] * extra
        self.gap_end += extra
    def text(self):
        return "".join(self.buf[:self.gap_start] + self.buf[self.gap_end:])
---tests
g = GB("ab", 3)
insert(g, "c")
assert g.text() == "abc" and g.gap_start == 3, "c fills the last empty slot"
insert(g, "d")
assert g.text() == "abcd", "a full buffer must grow before writing"
assert len(g.buf) == 6, "grow doubles the size, without the list's own slow insert"
```

Moving the cursor is the one place characters move. Moving the gap **left** by one: the character just before the gap jumps to just before `gap_end`.

```exercise

    def __init__(self, text, size):

        self.gap_start, self.gap_end = len(text), size

---starter

    # your code here

---solution
def move_gap(gb, pos):
    moved = 0
    while gb.gap_start > pos:
        gb.gap_start -= 1
        gb.gap_end -= 1
        gb.buf[gb.gap_end] = gb.buf[gb.gap_start]
        gb.buf[gb.gap_start] = None
        moved += 1
    while gb.gap_start < pos:
        gb.buf[gb.gap_start] = gb.buf[gb.gap_end]
        gb.buf[gb.gap_end] = None
        gb.gap_start += 1
        gb.gap_end += 1
        moved += 1
    return moved
---tests

assert move_gap(g, 5) == 5, "moving from the end (10) to 5 moves 5 characters"

assert move_gap(g, 7) == 2 and g.text() == "helloworld", "moving right by 2 moves 2 characters"
assert move_gap(g, 7) == 0, "already there: nothing moves"
---hint
Two loops: one while the gap is too far right (`gap_start > pos`), one while it's too far left.
---hint
Moving left: shrink both ends by one, then copy `buf[gap_start]` to `buf[gap_end]`. Moving right is the mirror image.
```

## Cursor motions

In NORMAL mode, keys move the cursor. Each motion is just a function: **(text, position) → new position**. That makes them easy to test and, as you'll see, easy to combine with operators.

| key | moves to |
|---|---|
| `h` / `l` | one left / right (stops at the ends) |
| `0` / `$` | start / last character of the line |
| `w` | start of the next word |
| `b` | start of this word, or the previous one |
| `j` / `k` | same column, line below / above (clamped if that line is shorter) |

We'll call a **word** a run of non-space characters (vim also splits on punctuation, but the idea is the same).

```exercise
title: word_forward
kind: write
---prompt
Write `word_forward(text, pos)`: skip the rest of the current word (non-spaces), then skip the spaces after it, and return where you land. If there's no next word, return `len(text)`.
---starter
def word_forward(text, pos):
    i = pos
    # your code here
    return i
---solution
def word_forward(text, pos):
    i = pos
    while i < len(text) and text[i] != " ":
        i += 1
    while i < len(text) and text[i] == " ":
        i += 1
    return i
---tests

assert word_forward(t, 0) == 4, f"from 't' of 'the', w lands on 'q' (index 4), got {word_forward(t, 0)}"
assert word_forward(t, 6) == 11, "from inside 'quick', skip the rest and both spaces"
assert word_forward(t, 3) == 4, "from a space, just skip the spaces"
assert word_forward(t, 12) == len(t), "no next word: land at the end"
---hint
Two `while` loops, one after the other, each with `i < len(text)` first so you never index past the end.
```

## Modes are a state machine

Why does vim have modes at all? Because then every letter on the keyboard can be a **command** without holding Ctrl. `dw`, `ciw`, `>>`: one-handed, no chords.

The cost is that the same key means different things, so the editor must always know which mode it's in. That's a **state machine**: a current state, and a table of `(state, key) → next state`. Anything not in the table stays put.

```predict
T = {("NORMAL", "i"): "INSERT", ("NORMAL", "v"): "VISUAL",
     ("INSERT", ESC): "NORMAL", ("VISUAL", ESC): "NORMAL"}
mode = "NORMAL"
for key in ["i", "v", ESC, "v", "x", ESC]:
    mode = T.get((mode, key), mode)
    print(repr(key), mode)
```

Look at the second `v`: in INSERT mode it's just a letter, so the mode stays INSERT. The table is the whole design: to add a mode (vim has REPLACE, COMMAND-LINE and more), you add rows, not `if` statements scattered everywhere.

## Counts and operators

NORMAL-mode commands have a little grammar:

```
[count] operator [count] motion      3dw   d2w   dd
[count] motion                        3j    w     $
```

An **operator** (`d` delete, `c` change, `y` copy) says *what to do*; a **motion** says *over which text*. Learn 5 operators and 10 motions and you know 50 commands. This is why vim users get fast: they compose, they don't memorise.

The text between the cursor and where the motion lands is what the operator acts on. So `dw` = "delete from here to wherever `w` would go".

```exercise
title: parse_command
kind: write
---prompt
Write `parse_command(keys)` returning `(count, operator, motion)`. `count` is the number in front (default 1; a count before **and** after the operator multiply, so `2d3w` is 6). `operator` is `"d"`, `"c"`, `"y"` or `None`. `motion` is the last key. Doubling an operator (`dd`, `yy`) means "whole line": return motion `"line"`.
---starter
def parse_command(keys):
    # your code here
    return 1, None, keys
---solution
def parse_command(keys):
    i, count = 0, 1
    def number():
        nonlocal i
        j = i
        while i < len(keys) and keys[i].isdigit():
            i += 1
        return int(keys[j:i]) if i > j else 1
    count *= number()
    op = None
    if keys[i] in "dcy":
        op = keys[i]
        i += 1
        count *= number()
        if i < len(keys) and keys[i] == op:
            return count, op, "line"
    return count, op, keys[i]
---tests
assert parse_command("w") == (1, None, "w"), "a bare motion: count 1, no operator"
assert parse_command("3j") == (3, None, "j"), f"3j moves down 3 lines, got {parse_command('3j')}"
assert parse_command("dw") == (1, "d", "w"), "dw: delete to the next word"
assert parse_command("12dw") == (12, "d", "w"), "counts can have several digits"
assert parse_command("2d3w") == (6, "d", "w"), "counts before and after the operator multiply"
assert parse_command("dd") == (1, "d", "line"), "dd deletes the whole line"
assert parse_command("3yy") == (3, "y", "line"), "3yy copies 3 lines"
---hint
Read digits (if any) into a number, then check for an operator letter, then read digits again.
---hint
After the operator, if the next key is the **same** operator, it's the line form.
```

## Undo: remember commands, not copies

The simple way to undo: save a **snapshot** (a full copy of the text) before every change. Undo = go back one snapshot. It works, and it's terrible for memory: 1,000 edits to a 1 MB file = 1 GB of snapshots.

The better way: save the **command** and enough to reverse it. "Inserted `abc` at 10" is undone by "delete 3 characters at 10". "Deleted `fox ` at 16" is undone by "insert `fox ` at 16". Each entry is as small as the edit itself.

```predict
text_size = 100_000
edits = [5, 1, 1, 12, 3]           # characters changed by each edit
print("snapshots:", len(edits) * text_size)
print("commands: ", sum(edits))
```

Undo pops the last command, applies its **inverse** and pushes it onto a **redo** stack. Making a fresh edit clears the redo stack: once you've gone a different way, the old future is gone.

```exercise
title: undo_redo
kind: write
---prompt
Write class `Editor` with `self.text`, `insert(pos, s)`, `delete(pos, n)`, `undo()` and `redo()`. Store commands as tuples `("insert", pos, s)` or `("delete", pos, removed_text)` on `self.undo_stack`; never store a copy of the whole text. A new insert/delete clears the redo stack. Undo/redo with an empty stack does nothing.
---starter
class Editor:
    def __init__(self, text=""):
        self.text = text
        self.undo_stack = []
        self.redo_stack = []

    def insert(self, pos, s):
        self.text = self.text[:pos] + s + self.text[pos:]

    def delete(self, pos, n):
        self.text = self.text[:pos] + self.text[pos + n:]

    def undo(self):
        pass

    def redo(self):
        pass
---solution
class Editor:
    def __init__(self, text=""):
        self.text = text
        self.undo_stack = []
        self.redo_stack = []

    def _apply(self, cmd):
        kind, pos, s = cmd
        if kind == "insert":
            self.text = self.text[:pos] + s + self.text[pos:]
        else:
            self.text = self.text[:pos] + self.text[pos + len(s):]

    @staticmethod
    def _inverse(cmd):
        kind, pos, s = cmd
        return ("delete" if kind == "insert" else "insert", pos, s)

    def insert(self, pos, s):
        self._do(("insert", pos, s))

    def delete(self, pos, n):
        self._do(("delete", pos, self.text[pos:pos + n]))

    def _do(self, cmd):
        self._apply(cmd)
        self.undo_stack.append(cmd)
        self.redo_stack.clear()

    def undo(self):
        if self.undo_stack:
            cmd = self.undo_stack.pop()
            self._apply(self._inverse(cmd))
            self.redo_stack.append(cmd)

    def redo(self):
        if self.redo_stack:
            cmd = self.redo_stack.pop()
            self._apply(cmd)
            self.undo_stack.append(cmd)
---tests
e = Editor("the fox")
e.insert(4, "quick ")
assert e.text == "the quick fox", "insert works"
e.delete(0, 4)
assert e.text == "quick fox", "delete works"
assert e.undo_stack[-1] == ("delete", 0, "the "), f"the delete command must remember the removed text, got {e.undo_stack[-1:]}"
e.undo()
assert e.text == "the quick fox", "undo puts 'the ' back"
e.undo()
assert e.text == "the fox", "a second undo removes 'quick '"
e.redo()
assert e.text == "the quick fox", "redo re-applies the insert"
e.insert(0, "see ")
e.redo()
assert e.text == "see the quick fox", "a new edit clears the redo stack, so redo does nothing"
e.undo(); e.undo(); e.undo(); e.undo()
assert e.text == "the fox", "extra undos on an empty stack are harmless"
assert all(len(c[2]) < 10 for c in e.redo_stack), "commands store only the changed text, not snapshots"
---hint
Write one private `_apply(cmd)` that performs either kind of command. The inverse of `("insert", p, s)` is `("delete", p, s)` and vice versa.
---hint
A delete must read the text it's about to remove **before** removing it, and store that in the command.
```

Vim groups a whole INSERT session (from `i` to `Esc`) into **one** undo step, so `u` takes back the whole word you typed, not one letter at a time.

## Search

`/fox` jumps to the next `fox` after the cursor. If there isn't one, vim **wraps around** to the top. That's two searches: from the cursor to the end, then from the start.

```predict
def search(text, pattern, pos):
    hit = text.find(pattern, pos + 1)
    if hit == -1:
        hit = text.find(pattern)        # wrap around
    return hit

t = "fox one fox two fox"
p = 0
for _ in range(4):
    p = search(t, "fox", p)
    print(p)
```

Notice `pos + 1`: without it, searching again from a match would find the same match forever.

## Real-world project: a modal note-taking app

Terminal apps like vim, less, htop, tig and lazygit, and "vim mode" in VS Code, Obsidian and Jupyter, all have this core: a buffer, a mode, and a loop that turns each keystroke into a command.

```project
title: A modal note editor for the terminal
client: A writer who wants distraction-free notes and keeps reaching for vim keys
skills: state machines, string slicing, parsing, undo stacks
---brief
Build the engine of a tiny vim-style notes editor. It reads keystrokes one at a time (exactly what a terminal sends: `\x1b` for Esc) and updates the text and cursor. It needs INSERT mode for typing, NORMAL mode for moving and deleting, counts like `2dw`, and `u` to undo.
---why
Every interactive program is a loop over input events plus a state machine: terminal UIs, game controllers, form wizards, network protocol parsers. Command-based undo is what Google Docs, Figma and Photoshop's history panel use, because snapshots of big documents don't fit in memory.
---milestones
- A loop over keys with a `mode` variable: `i`/`a` enter INSERT, `\x1b` returns to NORMAL
- Motions `h l 0 $ w` move a cursor in NORMAL mode; `x` deletes under the cursor
- `d` + motion deletes the range the motion covers; counts multiply (`2dw`)
- Every edit pushes an undo command; `u` pops and reverses it, one INSERT session at a time
- Wrap it in a real terminal loop with `curses` (stretch)
---stretch
- Add VISUAL mode: `v`, move, then `d` deletes the selection
- Store the text in your gap buffer instead of a string
- Add `/` search with wrap-around and `n` for "next match"
```

```exercise
title: run_keys
kind: write
---prompt

---setup

---solution
def run_keys(text, keys):
    pos, mode, count, op = 0, "NORMAL", "", None
    undo, start = [], 0
    for k in keys:
        if mode == "INSERT":
            if k == ESC:
                mode = "NORMAL"
                if pos > start:
                    undo.append(("insert", start, text[start:pos]))
                pos = max(0, pos - 1)
            else:
                text = text[:pos] + k + text[pos:]
                pos += 1
            continue
        if k.isdigit() and (count or k != "0"):
            count += k
            continue
        n = int(count or "1")
        count = ""
        if op:
            n *= op_n
            op = None
            if k == "w":
                end = pos
                for _ in range(n):
                    end = word_forward(text, end)
                undo.append(("delete", pos, text[pos:end]))
                text = text[:pos] + text[end:]
            pos = min(pos, max(0, len(text) - 1))
            continue
        if k == "d":
            op, op_n = "d", n
        elif k in "ia":
            if k == "a" and text:
                pos += 1
            mode, start = "INSERT", pos
        elif k == "h":
            pos = max(0, pos - n)
        elif k == "l":
            pos = min(max(0, len(text) - 1), pos + n)
        elif k == "0":
            pos = 0
        elif k == "$":
            pos = max(0, len(text) - 1)
        elif k == "w":
            for _ in range(n):
                pos = word_forward(text, pos)
            pos = min(pos, max(0, len(text) - 1))
        elif k == "x" and text:
            gone = text[pos:pos + n]
            undo.append(("delete", pos, gone))
            text = text[:pos] + text[pos + n:]
            pos = min(pos, max(0, len(text) - 1))
        elif k == "u" and undo:
            kind, p, s = undo.pop()
            if kind == "insert":
                text = text[:p] + text[p + len(s):]
            else:
                text = text[:p] + s + text[p:]
            pos = min(p, max(0, len(text) - 1))
    return text

Handle INSERT mode first and `continue`: there, every key except ESC is just typed. Remember where the INSERT session started so ESC can push one undo entry for all of it.
---hint
For counts, collect digits into a string (but a `0` with no digits before it is the `0` motion). When you see `d`, remember the count and wait for the next key, the motion.
```

## Rebuild it and explain it

```exercise
title: GapBuffer
kind: rebuild
---prompt
From memory, write class `GapBuffer(text, size)` with `buf`, `gap_start`, `gap_end`, and methods `text()`, `move_to(pos)`, `insert(ch)` (grow by doubling when the gap is empty) and `backspace()`.
---starter
class GapBuffer:
    def __init__(self, text, size=8):
        pass
---solution
class GapBuffer:
    def __init__(self, text, size=8):
        size = max(size, len(text) + 1)
        self.buf = list(text) + [None] * (size - len(text))
        self.gap_start, self.gap_end = len(text), size

    def text(self):
        return "".join(self.buf[:self.gap_start] + self.buf[self.gap_end:])

    def move_to(self, pos):
        while self.gap_start > pos:
            self.gap_start -= 1
            self.gap_end -= 1
            self.buf[self.gap_end] = self.buf[self.gap_start]
            self.buf[self.gap_start] = None
        while self.gap_start < pos:
            self.buf[self.gap_start] = self.buf[self.gap_end]
            self.buf[self.gap_end] = None
            self.gap_start += 1
            self.gap_end += 1

    def insert(self, ch):
        if self.gap_start == self.gap_end:
            extra = len(self.buf)
            self.buf[self.gap_end:self.gap_end] = [None] * extra
            self.gap_end += extra
        self.buf[self.gap_start] = ch
        self.gap_start += 1

    def backspace(self):
        if self.gap_start > 0:
            self.gap_start -= 1
            self.buf[self.gap_start] = None
---tests
g = GapBuffer("helo", 6)
g.move_to(3)
g.insert("l")
assert g.text() == "hello", f"insert in the middle, got {g.text()!r}"
for c in " world":
    g.move_to(len(g.text()))
    g.insert(c)
assert g.text() == "hello world", "the buffer grows when it runs out of gap"
g.move_to(5)
g.backspace()
assert g.text() == "hell world", "backspace removes the character before the cursor"
assert g.gap_start == 4, "the cursor moved back by one"
---hint
Text = everything before the gap + everything after it. Every method only touches `gap_start`, `gap_end` and the slots right next to the gap.
```

```recall
Q: Why does a gap buffer make typing fast, why does vim need modes, and why does undo store commands instead of copies?
A: A gap buffer keeps empty slots at the cursor, so typing just fills the next slot (O(1)); only moving the cursor shifts characters, one per step, and people type in bursts in one place. Modes let plain letters be commands in NORMAL mode and text in INSERT mode; a state machine (mode + key → action/next mode) keeps that straight. Undo stores each edit and how to reverse it (inserted X at p ↔ delete X at p), which costs as much memory as the edit itself, while a snapshot costs the whole document every time.
```

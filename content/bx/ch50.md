## The program on the other end

You open a coffee app, tap **Latte**, then **Order**. Your phone doesn't make the latte. It sends a short message to a program running on a computer somewhere, and that program writes your order down and answers. That program is a **backend**, and this part of the course is about building the ones companies actually run.

Every exchange has the same shape. The app sends a **request**: a **method** (`GET` to read, `POST` to create), a **path** (`/menu`, `/orders`) and sometimes a **body**. The server sends back a **response**: a **status code** (`201 Created`, `404 Not Found`) and a body. Everything in the next eight chapters, from logins to chatbots to payments, is built from exchanges like this one.

## A server with nothing but Node

Node comes with an `http` module. `createServer` takes one function, and Node calls it once for every request that arrives, with the request (`req`) and a response to fill in (`res`). `listen(3000)` starts waiting on port 3000.

The code on these pages runs in a small Node inside your browser. `fetch` talks to the servers your code starts, as if it were another program on the same machine. On your own computer you'd run the file with `node main.js` and send the request from another terminal with `curl localhost:3000`. The pages also let you write `await` at the top of the file, as you can in a modern Node module.

```run
title: A server, and a request to it
const http = require("http");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from the coffee shop\n");
});
server.listen(3000);

const reply = await fetch("http://localhost:3000/");
console.log(reply.status, reply.statusText);
console.log(await reply.text());
```

That server answers every request the same way, whatever was asked. `req.method` and `req.url` say what was asked. What does this print?

```predict
const http = require("http");

http.createServer((req, res) => {
  res.end(`You asked for ${req.method} ${req.url}`);
}).listen(3000);

for (const path of ["/", "/menu", "/orders?drink=latte"]) {
  const reply = await fetch("http://localhost:3000" + path);
  console.log(await reply.text());
}
```

The query string, `?drink=latte`, is part of `req.url`. Node hands you the raw text and nothing more: picking it apart is your job, or your framework's.

## Routes by hand

A **route** is a method and a path together, and the code that answers them. `GET /menu` and `POST /menu` are different routes. Two more things a good API always does: it says what kind of body it sent, in the `Content-Type` header, and it answers errors as JSON too, so the app can show them.

## Express: the same server, with routing done for you

Every backend needs routes, JSON bodies and error handling, so nobody writes them by hand twice. **Express** is the framework most Node companies start with. `app.get(path, handler)` adds a route, and `res.json(value)` sends JSON with the right header. A route you didn't add gets a 404 without you writing anything.

```run
title: The menu, in Express
const express = require("express");

const MENU = [
  { id: 1, name: "Espresso", price: 250 },
  { id: 2, name: "Latte", price: 400 },
  { id: 3, name: "Mocha", price: 450 },
];

const app = express();
app.get("/menu", (req, res) => {
  res.json(MENU);
});
app.listen(3000);

const menu = await fetch("http://localhost:3000/menu");
console.log(menu.status, menu.headers.get("content-type"));
console.log(await menu.json());

const cake = await fetch("http://localhost:3000/cake");
console.log(cake.status, cake.headers.get("content-type"));
```

Express's own 404 is a small web page, meant for a browser. An API usually replaces it with JSON, and you'll do that in the project.

## Status codes: the answer before the answer

The first line of every response is a number, and it's the first thing the app's code reads. `res.ok` is true for anything from 200 to 299, so most app code is `if (res.ok) { show it } else { show the error }`. The numbers you'll use most:

| Code | Means | A coffee shop example |
|---|---|---|
| 200 OK | here's what you asked for | the menu |
| 201 Created | I made a new thing; here it is | your new order, with its id |
| 400 Bad Request | what you sent makes no sense | an order for a drink that isn't on the menu |
| 404 Not Found | there's no such thing | order 9999 |
| 500 Internal Server Error | the server broke | a bug in the handler |

The 4xx codes mean "the client should change something". The 5xx codes mean "the server broke, and the same request might work later". Retry libraries, browsers and monitoring all read that difference, so a wrong code misleads every one of them. You saw that in the simulation: an error sent with **200** made the app announce an order that didn't exist.

## Path parameters and query strings

## Taking orders: POST and a JSON body

To create something, the app sends `POST` with a **body**, usually JSON: `{"drinkId": 2, "size": "L"}`. The body arrives as raw text, in pieces. `app.use(express.json())` adds **middleware**: a function that runs before your routes, reads the whole body, parses it and puts the result in `req.body`.

A good create endpoint answers **201 Created** with the new thing, including the id the server gave it. It also sends a `Location` header saying where the thing now lives, `/orders/1`, so the app can ask about it later. `res.status(201)` sets the status, `res.location(path)` sets the header, and both return `res`, so you can chain them.

```exercise

- A new order is `{id, drink, size, price, status: "queued"}`, with ids 1, 2, 3… and the drink's name in `drink`. Answer it with 201 and `Location: /orders/<id>`.

const express = require("express");

const MENU = [
  { id: 1, name: "Espresso", price: 250 },
  { id: 2, name: "Latte", price: 400 },
  { id: 3, name: "Mocha", price: 450 },
];
const EXTRA = { S: -50, M: 0, L: 50 };
const orders = [];

const app = express();
app.use(express.json());

app.post("/orders", (req, res) => {
  const drink = MENU.find((d) => d.id === req.body.drinkId);
  if (!drink) return res.status(400).json({ error: "Unknown drink" });
  const size = req.body.size ?? "M";
  if (!(size in EXTRA)) return res.status(400).json({ error: "size must be S, M or L" });
  const order = { id: orders.length + 1, drink: drink.name, size, price: drink.price + EXTRA[size], status: "queued" };
  orders.push(order);
  res.status(201).location(`/orders/${order.id}`).json(order);
});

app.get("/orders/:id", (req, res) => {
  const order = orders.find((o) => o.id === Number(req.params.id));
  if (!order) return res.status(404).json({ error: `No order ${req.params.id}` });
  res.json(order);
});

app.listen(3000);

const got = await request("GET /orders/1");
assert(got.status === 200 && got.json.drink === "Latte", "GET /orders/1 answers the latte");
const lost = await request("GET /orders/7");
assert(lost.status === 404 && lost.json.error === "No order 7", "GET /orders/7 is a 404: No order 7");
---hint

---hint
```

## Quick-fire: lock it in

```quiz
Someone posts an order for `{"drinkId": 9}`, and there's no drink 9. Which status fits best?
- 200, with `{"error": "Unknown drink"}` in the body
* 400 Bad Request
- 404 Not Found
- 500 Internal Server Error
> The route `/orders` exists, so it's not a 404: what's wrong is what the client sent. (Some APIs use 422 for "the JSON parsed, but the values are wrong". Either way it's a 4xx: the client must change something.) A 200 would make every app announce a drink that will never come.
```

```quiz
In `app.get("/menu/:id", …)`, what is `req.params.id` for `GET /menu/2`?
- The number 2
* The string "2"
- `{ id: 2 }`
- `undefined`, until you parse it
> Everything in a URL is text. Convert it yourself with `Number(…)`, and check the result.
```

```quiz
Why is a latte's price stored as `400` and not `4.00`?
- It's shorter to type
* Money in cents is a whole number, so adding prices never drifts (`0.1 + 0.2` is `0.30000000000000004`)
- JSON can't hold decimals
- Express only sends integers
> Payment systems such as Stripe take amounts in the smallest unit (cents, pence, paise) for exactly this reason.
```

## Real-world project: the order API for a coffee cart chain

```project
title: brew, the order backend for a chain of coffee carts
client: A company with 12 coffee carts in train stations. Customers order on an app and collect at the cart; baristas see the queue on a tablet.
skills: Express routing, status codes, path and query parameters, JSON bodies, an order lifecycle
---brief
Build `brew`, the API both apps talk to. The customer app reads `GET /menu` (filtered with `?max=`), places orders with `POST /orders`, and checks `GET /orders/:id` until the drink is ready. The barista tablet lists `GET /orders?status=queued` and moves each order along with `PATCH /orders/:id`: `queued` → `making` → `ready` → `collected`. A move that skips a step, or goes back, is refused with 409 Conflict, so two baristas tapping at once can't hand out the same drink twice. Every error is JSON, including the 404 for a route that doesn't exist.
---why
This is the shape of nearly every company backend: a list of things, ways to create them, and a lifecycle each thing moves through, with the rules enforced on the server, because the server is the only place two apps' views of the world meet.
---milestones
- `GET /menu` with `?max=`, and `GET /menu/:id`
- `POST /orders` with drink and size checks, 201 and a Location header
- `GET /orders/:id`, and `GET /orders?status=` for the barista tablet
- `PATCH /orders/:id` with the four statuses, 409 for a move out of order
- A JSON 404 for every route that doesn't exist
---stretch
- `DELETE /orders/:id` while the order is still `queued` (a customer cancels), and 409 once it's `making`
- Wait times: each order's place in the queue, and the minutes until it's ready
```

```exercise
const express = require("express");

const MENU = [{ id: 2, name: "Latte", price: 400 }];

const NEXT = { queued: "making", making: "ready", ready: "collected" };
const orders = [];

const app = express();
app.use(express.json());

app.post("/orders", (req, res) => {
  const drink = MENU.find((d) => d.id === req.body.drinkId);
  if (!drink) return res.status(400).json({ error: "Unknown drink" });

  const known = [...Object.keys(NEXT), ...Object.values(NEXT)];
  if (!known.includes(to)) return res.status(400).json({ error: "Unknown status" });
  if (NEXT[order.status] !== to) return res.status(409).json({ error: `Can't go from ${order.status} to ${to}` });
  order.status = to;
  res.json(order);
});

app.use((req, res) => {
  res.status(404).json({ error: "Not found" });
});

app.listen(3000);
---tests

const making = await request("PATCH /orders/1", { status: "making" });
assert(making.status === 200 && making.json.status === "making", "queued → making is allowed, and answers the order");
const skip = await request("PATCH /orders/1", { status: "collected" });
assert(skip.status === 409, "making → collected skips ready: 409 Conflict");
assert(skip.json.error === "Can't go from making to collected", "the 409 says which move was refused");
const back = await request("PATCH /orders/1", { status: "queued" });
assert(back.status === 409, "going back to queued is a 409 too");
const odd = await request("PATCH /orders/1", { status: "spilled" });
assert(odd.status === 400 && odd.json.error === "Unknown status", '"spilled" is a 400: Unknown status');

assert(ghost.status === 404 && ghost.json.error === "No order 9", "order 9 is a 404");

const done = await request("PATCH /orders/1", { status: "collected" });
assert(done.json.status === "collected", "ready → collected finishes the order");
const nowhere = await request("GET /coupons");
assert(nowhere.status === 404 && nowhere.type === "application/json" && nowhere.json.error === "Not found", "a route that doesn't exist answers JSON, not a web page");
---hint
`NEXT[order.status]` is the one status allowed next; anything else that's still a real status is a 409.
---hint
Express tries routes in the order you added them, so a catch-all `app.use(...)` must come after all of them.
```

```recall
Q: Explain what a backend does with one request, from the bytes arriving to the app showing the result: methods and paths, routes, parameters and bodies, and why the status code matters.
A: A backend is a program listening on a port. A request arrives as text: a method (GET reads, POST creates, PATCH changes), a path, headers, and sometimes a body. The server matches the method and path together against its routes and runs exactly one handler; if nothing matches it answers 404. The handler finds what it needs in the path (path parameters like /orders/:id, for naming one thing), the query string (?max=400, for options on a list) and the body (JSON, read and parsed by middleware such as express.json()). All of these arrive as text, so numbers must be converted and checked. The handler answers a status code and a body, usually JSON with a Content-Type header. The status is the answer before the answer: clients read it first (res.ok means 200–299), so 201 means created, 400 means the client sent something wrong, 404 means no such thing, 409 means the move conflicts with the current state, and 5xx means the server broke. A wrong status, like 200 with an error in the body, misleads every client at once.
```

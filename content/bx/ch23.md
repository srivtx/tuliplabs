## The most popular programming language

More people program in spreadsheets than in every other language combined: every `=B2*C2` is a little program. Behind the grid sits an engine with one job. When you change a cell, **work out which other cells depend on it, and recompute them in an order where every cell comes after the cells it reads.** Get the order wrong and the sheet shows wrong numbers; recompute everything and a big sheet gets slow.

That problem, "update what depends on a change, in the right order", is everywhere: build tools (make, Bazel) rebuild only the files affected by an edit, React re-renders only components whose inputs changed, and package managers install dependencies before the packages that need them. You'll build it here with a 3 × 3 sheet.

## Which cells does a formula read?

```exercise
title: refs
kind: write
---prompt
Write `refs(formula)` that returns the cell names a formula reads, in the order they first appear, without repeats, in upper case. A cell name is one or more letters followed by one or more digits. Formulas start with `=`; anything else is a plain value that reads nothing.
---starter
def refs(formula):
    return []
---solution
def refs(formula):
    if not formula.startswith("="):
        return []
    out = []
    for name in re.findall(r"[A-Za-z]+[0-9]+", formula):
        name = name.upper()
        if name not in out:
            out.append(name)
    return out
---tests
assert refs("=A1+B2*2") == ["A1", "B2"]
assert refs("=a1*A1+c10") == ["A1", "C10"], "case-insensitive, no repeats"
assert refs("=AB12/2") == ["AB12"], "column AB"
assert refs("42") == [], "a plain number"
assert refs("=3*4") == []
---hint
`re.findall(r"[A-Za-z]+[0-9]+", formula)` finds every name; then upper-case and skip ones already in the list.
```

---solution
def evaluate(formula, values):
    if not formula.startswith("="):
        return float(formula)
    expr = re.sub(r"[A-Za-z]+[0-9]+", lambda m: repr(values[m.group().upper()]), formula[1:])
    return eval(expr, {"__builtins__": {}})
---tests

assert evaluate("=A1*2+b1", {"A1": 10.0, "B1": 1.0}) == 21.0
assert evaluate("=(A1+A2)/2", {"A1": 3.0, "A2": 4.0}) == 3.5

---hint

## The order matters

```predict
formulas = {"B1": lambda v: v["C1"] + 1, "C1": lambda v: v["A1"] * 10}
v = {"A1": 1, "B1": 0, "C1": 0}
for cell in ["B1", "C1"]:
    v[cell] = formulas[cell](v)
print(v["B1"], v["C1"])
for cell in ["C1", "B1"]:
    v[cell] = formulas[cell](v)
print(v["B1"], v["C1"])
```

Reading order (left to right, top to bottom) is the obvious order, and it's wrong whenever a formula reads a cell that comes later. The fix is to treat the sheet as a **graph**: an arrow from each cell to every formula that reads it. You need an order where every arrow points forwards: a **topological order**.

```parsons
title: A topological order by depth-first search
---lines
def topo_order(deps):
    order, done = [], set()
    def visit(cell):
        if cell in done:
            return
        done.add(cell)
        for d in deps.get(cell, []):
            visit(d)
        order.append(cell)
    for cell in deps:
        visit(cell)
    return order
?? order.insert(0, cell)
?? for cell in sorted(deps, reverse=True):
---tests
deps = {"C1": ["B3", "B1"], "B1": ["A1"], "B3": ["A2"], "A2": ["B2"], "B2": ["A1"], "A1": []}
o = topo_order(deps)
assert all(o.index(d) < o.index(c) for c in deps for d in deps[c]), "every cell after the cells it reads"
assert sorted(o) == sorted(deps)
```

`deps` maps each cell to the cells it **reads**. Visiting what a cell reads before appending the cell itself puts every cell after its inputs.

## Only what changed

Recomputing every cell is correct but slow on a sheet with a million cells, when you changed one. The engine keeps the reverse graph too: for each cell, the formulas that read it. After an edit it collects every cell **downstream** of the change, and recomputes only those, in topological order.

```exercise
title: dependents
kind: write
---prompt
Write `dependents(deps, cell)` that returns the set of every cell that reads `cell` directly **or indirectly** (not including `cell` itself, unless it's on a cycle). `deps` maps each cell to the list of cells it reads.
---starter
def dependents(deps, cell):
    return set()
---solution
def dependents(deps, cell):
    readers = {}
    for c, ins in deps.items():
        for i in ins:
            readers.setdefault(i, []).append(c)
    out, todo = set(), [cell]
    while todo:
        x = todo.pop()
        for r in readers.get(x, []):
            if r not in out:
                out.add(r)
                todo.append(r)
    return out
---tests
deps = {"A1": [], "B1": ["A1"], "C1": ["B1", "B3"], "A2": ["B2"], "B2": ["A1"], "A3": [], "B3": ["A2", "A3"]}
assert dependents(deps, "A1") == {"B1", "C1", "B2", "A2", "B3"}
assert dependents(deps, "A3") == {"B3", "C1"}
assert dependents(deps, "C1") == set(), "nothing reads C1"
---hint
First invert the graph: for each cell, who reads it. Then walk from `cell` with a to-do list, adding each new reader.
```

## Circular references

If B3 reads C3 and C3 (through a chain) reads B3, there is no topological order: some cell would have to be computed before itself. A spreadsheet must spot this and show an error (`#CYCLE`, or Excel's *circular reference* warning) instead of recursing forever.

```exercise
title: find_cycle
kind: write
---prompt
Write `has_cycle(deps)` that returns `True` if the dependency graph contains a cycle. Use depth-first search with three states per cell: not visited, **on the current path**, and finished. Reaching a cell that's on the current path means you've gone round a loop. Cells that appear only in someone's list have no dependencies of their own.
---starter
def has_cycle(deps):
    return False
---solution
def has_cycle(deps):
    state = {}
    def visit(c):
        if state.get(c) == "path":
            return True
        if state.get(c) == "done":
            return False
        state[c] = "path"
        for d in deps.get(c, []):
            if visit(d):
                return True
        state[c] = "done"
        return False
    return any(visit(c) for c in list(deps))
---tests
assert not has_cycle({"B1": ["A1"], "C1": ["A1", "B1"]}), "a diamond is not a cycle"
assert has_cycle({"A1": ["A1"]}), "a cell reading itself"
assert has_cycle({"B3": ["C3"], "C3": ["C2"], "C2": ["C1"], "C1": ["B3"]})
assert not has_cycle({}), "an empty sheet"
---hint
A cell you finished earlier (`"done"`) is safe to meet again: that's a diamond, not a loop. Only `"path"` means a cycle.
```

```quiz
Why does the engine need the three states ("on the path" vs "finished") rather than just "visited"?
- To make it faster
* Because meeting a finished cell again is normal (two formulas can read the same cell), while meeting a cell on the current path means a loop
- Because cells can have three values
- It doesn't: "visited" is enough
> With only "visited", the diamond B1 → A1, C1 → A1 and B1 would look like a cycle when C1's search reaches A1 a second time. A cycle is only a cell that's still waiting for its own inputs.
```

```exercise
title: recalc
kind: write
---prompt
Put it together. Write `recalc(formulas, values, changed)`: `values` holds the current value of every cell, and the cell `changed` has just been edited in `formulas`. Recompute `changed` and every cell downstream of it, each after the cells it reads, and return `(values, count)` where `count` is how many cells you recomputed. `refs`, `evaluate`, `topo_order` and `dependents` are ready.
---setup
def refs(f):
    out = []
    for n in re.findall(r"[A-Z]+[0-9]+", f):
        if n not in out:
            out.append(n)
    return out if f.startswith("=") else []
def evaluate(f, v):
    if not f.startswith("="):
        return float(f)
    return eval(re.sub(r"[A-Z]+[0-9]+", lambda m: repr(v[m.group()]), f[1:]), {"__builtins__": {}})
def topo_order(deps):
    order, done = [], set()
    def visit(c):
        if c in done:
            return
        done.add(c)
        for d in deps.get(c, []):
            visit(d)
        order.append(c)
    for c in deps:
        visit(c)
    return order
def dependents(deps, cell):
    out, todo = set(), [cell]
    while todo:
        x = todo.pop()
        for c, ins in deps.items():
            if x in ins and c not in out:
                out.add(c); todo.append(c)
    return out
---starter
def recalc(formulas, values, changed):
    return values, 0
---solution
def recalc(formulas, values, changed):
    deps = {c: refs(f) for c, f in formulas.items()}
    todo = dependents(deps, changed) | {changed}
    count = 0
    for c in topo_order(deps):
        if c in todo:
            values[c] = evaluate(formulas[c], values)
            count += 1
    return values, count
---tests
f = {"A1": "10", "B1": "=A1*2", "C1": "=B3+B1", "A2": "=B2+1", "B2": "=A1+5", "A3": "3", "B3": "=A2*A3", "C3": "=A3+1"}

f["A1"] = "0"

assert n == 6 and v["C3"] == 4, "A3 and C3 don't depend on A1: leave them alone"
---hint
The cells to redo are `dependents(...) | {changed}`. Walk `topo_order(deps)` and recompute only those.
```

```exercise
title: expand_range
kind: write
---prompt
Write `expand_range(r)` that turns a range like `"A1:B3"` into the list of cells it covers, column by column: `["A1", "A2", "A3", "B1", "B2", "B3"]`. Columns are single letters `A`–`Z`. The corners may be given in either order (`"B3:A1"` covers the same cells).
---starter
def expand_range(r):
    return []
---solution
def expand_range(r):
    a, b = r.upper().split(":")
    c1, c2 = sorted([a[0], b[0]])
    r1, r2 = sorted([int(a[1:]), int(b[1:])])
    return [chr(c) + str(row) for c in range(ord(c1), ord(c2) + 1) for row in range(r1, r2 + 1)]
---tests
assert expand_range("A1:B3") == ["A1", "A2", "A3", "B1", "B2", "B3"]
assert expand_range("B3:A1") == expand_range("A1:B3"), "corners in either order"
assert expand_range("C5:C5") == ["C5"]
assert expand_range("a1:a2") == ["A1", "A2"]
---hint
Split on `:`, take the letter and the number of each corner, sort each pair, then two nested ranges.
```

```recall
Q: Explain how a spreadsheet engine updates the sheet after you edit one cell.
A: Each formula's cell references are parsed out, giving a dependency graph: an edge from each cell to every formula that reads it. After an edit, the engine collects every cell downstream of the changed one (walking the reverse edges), then recomputes those cells in a topological order, so every cell is computed after all the cells it reads; cells not downstream keep their values. Computing in plain reading order would use stale values whenever a formula reads a later cell, and recomputing everything is correct but wastes time on big sheets. If the graph has a cycle there is no topological order, so a depth-first search with "on the current path" and "finished" states detects it and the cells involved show an error instead of looping. Ranges like A1:B3 expand to lists of cells, which become ordinary dependencies of functions like SUM.
```

## Assume the table leaks

Every product a company sells starts with the same screen: an email, a password, **Create account**. Behind it is the backend you'll build in this chapter, **Doormat**: it takes the sign-up, checks it, stores the account, and later lets that person back in.

Two things make this harder than the order API. First, anyone can send anything: the sign-up form is only one way to reach `POST /signup`. Second, the users table will leak one day. That has happened to companies far bigger than yours, through a stolen backup, a bug or a misplaced laptop. So the question isn't only "is it locked?", it's "when someone has a copy, what can they read?"

## Never trust the body

A sign-up form can check that the email looks like an email before it sends anything, and it should, because it's friendlier. But the form runs on the user's computer. Anyone can skip it and send their own request with `curl`, a script or the browser's developer tools. The server is the only place a check can't be skipped.

Here is a sign-up route that trusts its body. It's fine for the body the form sends, and breaks on the first one it doesn't.

```run
title: A route that trusts what it's sent
const express = require("express");

const app = express();
app.use(express.json());
app.post("/signup", (req, res) => {
  const email = req.body.email.trim().toLowerCase();
  res.status(201).json({ email });
});
app.listen(3000);

for (const body of [{ email: " Ana@Example.com " }, { email: 42 }, {}]) {
  const r = await fetch("http://localhost:3000/signup", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });
  console.log(JSON.stringify(body), "→", r.status, r.headers.get("content-type"));
}
```

The `TypeError` lines are Express logging each crash, as it would in your terminal. `42` has no `.trim()`, and `{}` has no email at all, so both are 500s: Express's HTML error page, sent to an app that expected JSON. A 500 says "the server broke", but the server was fine. The client sent something wrong, and that's a 400 with a message saying what.

## Zod: say what a valid body looks like, once

Checking each field by hand (is it there, is it a string, is it long enough) is how holes get left. **Zod** turns "what a valid sign-up looks like" into one declaration, a **schema**, and checks a value against it. `safeParse` never throws: it answers `{success: true, data}` or `{success: false, error}`.

```run
title: A schema, a good body and a bad one
const { z } = require("zod");

const SignUp = z.object({
  email: z.string().trim().toLowerCase().email(),
  password: z.string().min(8),
});

const good = SignUp.safeParse({ email: " Ana@Example.COM ", password: "correct-horse" });
console.log(good.success, JSON.stringify(good.data));

const bad = SignUp.safeParse({ email: 42, password: "short" });
console.log(bad.success);
for (const issue of bad.error.issues) console.log(issue.path.join("."), "→", issue.message);
```

Look at `good.data`: the email came back trimmed and lowercased. A schema doesn't only check, it also **cleans**, and `data` is the cleaned value. So from here on, the handler uses `data` and never touches `req.body` again.

Three more things a schema does. What does this print?

```predict
const { z } = require("zod");

const Team = z.object({
  name: z.string().trim().min(1),
  plan: z.enum(["free", "team"]).default("free"),
  seats: z.coerce.number().int().min(1),
});

for (const body of [
  { name: " Ana ", seats: "3" },
  { name: "Ben", plan: "team", seats: 2, admin: true },
  { name: "   ", seats: 0 },
]) {
  const r = Team.safeParse(body);
  console.log(r.success ? JSON.stringify(r.data) : "invalid: " + r.error.issues.map((i) => i.path.join(".")).join(", "));

```

`.default("free")` fills in a missing field. `z.coerce.number()` turns the text `"3"` into the number 3, which is what you want for form fields and query strings. And `admin: true` simply vanished: an object schema keeps only the keys it names. Hold on to that one, it's about to matter.

## Errors a form can show

A form shows each error under its own box: "Invalid email address" under the email, "Too short" under the password. So the 400 should say which field each message belongs to. `z.flattenError(error)` groups the issues that way: `fieldErrors` holds one list of messages per field.

```run
title: Issues, grouped by field
const { z } = require("zod");

const SignUp = z.object({
  email: z.string().trim().toLowerCase().email(),
  password: z.string().min(8),
});

const r = SignUp.safeParse({ email: "ana", password: "short" });
const { fieldErrors } = z.flattenError(r.error);
for (const [field, messages] of Object.entries(fieldErrors)) console.log(field, "→", messages.join("; "));
```

## The field nobody asked for

Users have a `role`: `"member"` for everyone who signs up, `"admin"` for the company's own staff. The sign-up form has no role box. But the body is whatever the client sends, and nothing stops it from sending `"role": "admin"`.

This is called **mass assignment**: copying the request body into a record wholesale, so the client gets to set fields it was never meant to touch. It has given real attackers admin rights on real sites.

The rule that fixes this whole class of bug: **after `safeParse`, never read `req.body` again.** Everything the handler needs is in `r.data`, checked, cleaned and holding only the fields you named.

## Storing the password

You saw in the simulation what each way of storing a password costs an attacker who has the table:

| Stored as | When the table leaks |
|---|---|
| plain text | every account is open, and on every other site where the person reused the password |
| a fast hash (SHA-256) | the attacker hashes a list of common passwords once and looks every row up; equal passwords have equal hashes |
| a fast hash + a salt | the list must be hashed again for every account, but fast hashes are cheap |
| a slow hash + a salt | every guess costs the attacker the full slow hash, for every account |

A **salt** is a random value made for each account and stored next to its hash. A **slow hash** repeats the work many times on purpose. Node's `crypto.pbkdf2Sync(password, salt, rounds, 32, "sha256")` does both: it mixes the salt in and hashes `rounds` times. Signing in costs your server one slow hash, which nobody notices; it costs an attacker one slow hash per guess.

```run
title: Same password, different salts
const crypto = require("crypto");

const sha = (s) => crypto.createHash("sha256").update(s).digest("hex");
console.log("SHA-256, ben:  ", sha("sunshine1").slice(0, 16));
console.log("SHA-256, chloe:", sha("sunshine1").slice(0, 16));

const slow = (password) => {
  const salt = crypto.randomBytes(16).toString("hex");
  return salt + ":" + crypto.pbkdf2Sync(password, salt, 10000, 32, "sha256").toString("hex");
};
const ben = slow("sunshine1"), chloe = slow("sunshine1");
console.log("salted and slow, the same?", ben === chloe);
console.log("one stored value is", ben.length, "characters: 32 of salt, a colon, 64 of hash");
```

On these pages the hash runs 10,000 rounds, so the checks stay quick. A real server should use far more: OWASP, the security community's reference, advises 600,000 for PBKDF2 with SHA-256. Alternatives built to be slow on purpose, bcrypt, scrypt and Argon2, are just as good choices.

To check a password at sign-in, read the salt back from the stored value, hash what was typed with it, and compare. Compare with `crypto.timingSafeEqual`, not `===`: `===` stops at the first byte that differs, so how long it takes leaks how many bytes were right. `timingSafeEqual` always looks at every byte.

```exercise
const crypto = require("crypto");

const ROUNDS = 10000; // a real server: 600,000 or more

function hashPassword(password) {
  const salt = crypto.randomBytes(16).toString("hex");
  const hash = crypto.pbkdf2Sync(password, salt, ROUNDS, 32, "sha256").toString("hex");
  return `${salt}:${hash}`;
}

function checkPassword(password, stored) {
  const [salt, hash] = stored.split(":");
  const again = crypto.pbkdf2Sync(password, salt, ROUNDS, 32, "sha256");
  return crypto.timingSafeEqual(again, Buffer.from(hash, "hex"));
}

module.exports = { hashPassword, checkPassword };
---tests

assert(/^[0-9a-f]{32}:[0-9a-f]{64}$/.test(a), "it's 32 hex characters of salt, a colon, and 64 of hash");
const b = mod.hashPassword("sunshine1");
assert(a !== b, "the same password, stored twice, looks different: each has its own salt");
assert(mod.checkPassword("sunshine1", a) === true, "the right password checks out");
assert(mod.checkPassword("sunshine2", a) === false, "a wrong one doesn't");
assert(mod.checkPassword("hunter22", "a1b2c3d4e5f60718293a4b5c6d7e8f90:53902e964739a63d31093c6f3b725da79df23752510099069b15f50c22e6733e") === true, "it's PBKDF2-SHA256 with 10,000 rounds: it checks a value made by another program");
---hint
`stored.split(":")` gives `[salt, hash]`. Hash the typed password with the same salt and rounds, and you get a Buffer.
---hint
`timingSafeEqual` takes two Buffers of the same length: the one you just made, and `Buffer.from(hash, "hex")`.
```

## Signing in, and staying signed in

Signing in checks the email and password, and answers a **session token**: a long random string the app keeps and sends with every later request, in the header `Authorization: Bearer <token>`. The server keeps a map from token to user. 32 random bytes is 256 bits: nobody will ever guess one. (A website usually keeps the token in a cookie instead of a header. The idea is the same.)

One rule looks odd until you think like an attacker. A wrong email and a wrong password get **the same answer**: `401` with "Email or password is wrong". If the server said "no account with that email", anyone could test a list of emails and learn who uses your product, a useful list for anyone planning a phishing email.

## Quick-fire: lock it in

```quiz
The sign-up form already checks the email before sending it. Why check it again on the server?
- The browser's check is sometimes wrong
* Anyone can send a request without the form, with curl or a script, so only the server's check can't be skipped
- Zod is faster than the browser
- The server's check is only for logging
> Check in the form to be friendly (instant feedback), and on the server to be safe. Only the second one counts.
```

```quiz
Two users chose the same password. With a salt, their stored values are…
- The same, because the password is the same
* Different, because each account's salt is different
- Different only if their emails differ
- Empty, because salts hide the password
> That's why one cracked account doesn't give away the other, and why the attacker can't hash the list once for everyone.
```

```quiz
Why does a slow hash help, if signing in has to compute it too?
- It doesn't: it only slows down your own server
- It makes the stored value longer
* The server computes it once per sign-in; an attacker computes it once per guess, for millions of guesses per account
- Slow hashes can't be computed on graphics cards
> A sign-in that takes 0.2 s more is invisible to a person. The same 0.2 s on every guess turns a list of a million words into more than two days of work, for one account.
```

## Real-world project: Doormat

```project
title: Doormat, accounts for a SaaS app
client: A start-up selling a project-planning tool to small teams. Their launch is in a month and they need sign-up, email verification and sign-in done properly before anyone else's data goes in.
skills: Zod schemas and error shapes, mass assignment, salted slow password hashing, session tokens, email verification
---brief
Build Doormat, the accounts service. `POST /signup` checks the body with Zod, refuses an email that already has an account (409), stores the password salted and slow, and "sends" a verification email (the start-up's mail service isn't wired in yet, so it goes in an `outbox` list). `GET /verify?token=` marks the account verified. `POST /login` refuses wrong details with one 401 message, and an unverified account with 403. `GET /me` answers the signed-in user, and `POST /logout` ends the session.
---why
Every product has these five routes, and they're where most security incidents begin: leaked tables, admin rights handed out through mass assignment, accounts made with someone else's email. Getting them right once means every feature built later stands on solid ground.
---milestones
- `POST /signup` with the Zod schema, a 400 with `fields`, and 201
- Passwords stored as `salt:hash` with PBKDF2, never sent back
- One account per email (after lowercasing), else 409
- A verification token in the outbox, and `GET /verify?token=`
- `POST /login` (401 for wrong details, 403 until verified), `GET /me`, `POST /logout`
---stretch
- Refuse the 1,000 most common passwords at sign-up, with a message under the password box
- Password reset: a token that expires after 30 minutes and works only once
- Lock sign-in for an email for 15 minutes after 10 wrong passwords in a row
```

```exercise
  const token = crypto.randomBytes(16).toString("hex");
  verifyTokens.set(token, user.id);
  outbox.push({ to: user.email, link: `/verify?token=${token}` });

});

app.get("/verify", (req, res) => {
  const id = verifyTokens.get(req.query.token);
  if (id === undefined) return res.status(400).json({ error: "That link isn't valid" });
  verifyTokens.delete(req.query.token);
  users.find((u) => u.id === id).verified = true;
  res.json({ verified: true });
});

app.post("/login", (req, res) => {
  const r = Login.safeParse(req.body);
  const user = r.success && users.find((u) => u.email === r.data.email);
  if (!user || !checkPassword(r.data.password, user.passwordHash)) return res.status(401).json({ error: "Email or password is wrong" });
  if (!user.verified) return res.status(403).json({ error: "Check your email to verify your account first" });
  const token = crypto.randomBytes(32).toString("hex");
  sessions.set(token, user.id);
  res.json({ token });
});
```

```recall
Q: Explain how a sign-up and sign-in backend keeps accounts safe: what you check, what you store, and what you answer.
A: The server checks every body itself, because the form can be skipped: a Zod schema declares the valid shape (an email, trimmed and lowercased; a password of at least 8 characters), safeParse answers success with cleaned data or the issues, and a failure is a 400 with the messages grouped by field (z.flattenError) so a form can show them. After safeParse the handler uses only the parsed data, never req.body, so a client can't set fields like role or verified (mass assignment). Emails are unique after lowercasing (409 otherwise). The password is never stored: the server stores a random per-account salt and a deliberately slow hash of salt and password (PBKDF2 with many rounds, or bcrypt, scrypt, Argon2). The salt makes equal passwords look different and forces an attacker to attack each account separately; the slowness makes every guess expensive, since an attacker with a leaked table tries millions. Weak and common passwords are refused at sign-up, because no hash saves a password that's first on every list. Sign-in hashes the typed password with the stored salt and compares with timingSafeEqual; a wrong email and a wrong password get the same 401, so the API doesn't reveal who has an account. Success answers a random session token (32 random bytes) that the app sends back as Authorization: Bearer, and the server maps it to the user. The answer never includes the password or its hash.
```

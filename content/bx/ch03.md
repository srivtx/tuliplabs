## What a math engine does

In chapter 2 every leaf of the tree was a number. Let one leaf be the letter **x** and you have a math engine: the thing inside Wolfram Alpha, SymPy, and the autograd of every deep-learning library.

The big surprise: **differentiation is just another tree walk.** Each rule (sum, product, chain) only looks at the *top* node of a tree and says what to build. Recursion handles everything below. The catch is that the rules produce a lot of junk like `1*cos(x)` and `0*x`, and if nobody cleans it up, the tree grows out of control.

```quiz
The derivative rules produce `("*", 1.0, ("cos", "x"))`. Why bother simplifying it to `("cos", "x")`, if both give the same numbers?
- It's only for looks; the computer doesn't care
* Every extra node gets copied and differentiated again next time, so junk multiplies with each derivative
- Python can't evaluate a tree that contains 1.0
- The product rule only works on simplified trees
> Both trees give the same value, but the second derivative of the unsimplified one has to differentiate the `1.0` and the `*` too, producing even more junk. Simplifying keeps the tree small, which keeps everything after it fast.
```

## Variables need an environment

Our trees use the same shapes as the calculator: a number is a `float`, an operation is a tuple like `("+", a, b)`. Two new things:

- a **variable** is a string leaf, like `"x"`;
- a **function** is a tuple with one child, like `("sin", "x")`.

To evaluate a tree with variables you need to know what each variable is worth right now. That lookup table is called an **environment**: a dict like `{"x": 2.0}`. Every interpreter has one; in Python, it's what `globals()` returns.

```predict
def evaluate(t, env):
    if isinstance(t, float):
        return t
    if isinstance(t, str):
        return env[t]
    op, a, b = t
    x, y = evaluate(a, env), evaluate(b, env)
    return x + y if op == "+" else x * y

tree = ("+", ("*", "x", "x"), 1.0)
print(evaluate(tree, {"x": 3.0}))
print(evaluate(tree, {"x": -2.0}))
```

## Each rule only looks at the top

Here is every rule you need, written as "what to build". `d(u)` means "the derivative of u", which is a recursive call.

| The tree is… | Its derivative is… | Name |
|---|---|---|
| a number `c` | `0` | constant |
| `x` | `1` (and any other variable gives `0`) | |
| `u + v` | `d(u) + d(v)` | sum |
| `u * v` | `d(u)*v + u*d(v)` | product |
| `u ^ n` (n a number) | `n * u^(n-1) * d(u)` | power + chain |
| `sin(u)` | `cos(u) * d(u)` | chain |

Notice the `* d(u)` at the end of the last two. That's the **chain rule**: whatever is inside the function changes too, and its rate of change multiplies in. Forgetting it is the most common calculus mistake there is, and the recursion makes it impossible to forget.

## Why the tree explodes

Let's count nodes. Each derivative copies the original subtrees and adds new ones, so sizes grow fast, and the junk (`*1.0`, `+0.0`) gets differentiated again next time.

```run
title: Derivatives of derivatives, unsimplified
def deriv(t, v="x"):
    if isinstance(t, (int, float)): return 0.0
    if isinstance(t, str): return 1.0 if t == v else 0.0
    op = t[0]
    if op == "sin": return ("*", ("cos", t[1]), deriv(t[1], v))
    if op == "cos": return ("*", ("*", -1.0, ("sin", t[1])), deriv(t[1], v))
    a, b = t[1], t[2]
    if op == "+": return ("+", deriv(a, v), deriv(b, v))
    if op == "*": return ("+", ("*", deriv(a, v), b), ("*", a, deriv(b, v)))
    if op == "^": return ("*", ("*", b, ("^", a, b - 1)), deriv(a, v))

def size(t):
    return 1 if not isinstance(t, tuple) else 1 + sum(size(c) for c in t[1:])

f = ("*", "x", ("sin", "x"))
for k in range(5):
    print(f"derivative {k}: {size(f):5d} nodes")
    f = deriv(f)
```

A simplifier walks the tree **bottom-up** (simplify the children first, then look at the node) and applies safe rewrites:

- both children are numbers → compute it now (**constant folding**);
- `u*0` or `0*u` → `0`;  `u*1` or `1*u` → `u`;
- `u+0` or `0+u` → `u`;  `u-0` → `u`;
- `u^1` → `u`;  `u^0` → `1`.

## Trust, but check with numbers

How do you know your rules are right? Ask the definition of a derivative directly: nudge x a tiny bit and see how much f moves. The **central difference** `(f(x+h) - f(x-h)) / 2h` is a numeric slope that needs no rules at all. If your symbolic derivative disagrees with it, a rule is wrong. Every autodiff library tests itself exactly this way ("gradient checking").

```predict
f = lambda x: x ** 3
h = 1e-3
slope = (f(2 + h) - f(2 - h)) / (2 * h)
print(round(slope, 4))
print(round(3 * 2 ** 2, 4))
```

## Real-world project: a pricing optimizer

You can now take derivatives of anything you can type. That's the core of every **optimizer**: the best point of a smooth curve is where its slope is zero, and the derivative tells you which way is uphill.

```project
title: Best price for a coffee cart
client: A coffee cart owner who wants the price that makes the most profit
skills: expression trees, symbolic derivatives, Newton's method, environments
---brief
At price `p` the cart sells `100 - 10*p` cups a day, and each cup costs 2 to make, so profit is `(p - 2) * (100 - 10*p)`. Too cheap and you earn nothing per cup; too expensive and nobody buys. Find the peak **without** trying every price: build the profit tree, take its derivative with your engine, and solve `profit'(p) = 0` with **Newton's method**, which needs the derivative of *that*, the second derivative. Your engine gives you both for free.
---why
Newton's method and its cousins sit inside every solver you've used: square roots on your calculator, the "Goal Seek" button in spreadsheets, physics engines resolving contacts, and the optimizers that fit statistical models. Symbolic derivatives are how tools like SymPy, Mathematica and JAX's `grad` hand those solvers exact slopes instead of guesses.
---milestones
- Write the profit formula as a tree with the variable `"p"`
- Get `profit'` and `profit''` from your `deriv` (with `v="p"`) and simplify both
- Write `newton(g, dg, x0)`: repeat `x = x - g(x)/dg(x)` until it stops moving
- Find the best price, then double-check it with a finite difference
- Try a messier demand curve, like `120 * exp(-0.3*p)`, where you couldn't solve it by hand
---stretch
- Add a second variable (a discount `d`) and use partial derivatives
- Plot profit against price and mark the point Newton found
- Count Newton steps vs a brute-force search over 1,000 prices
```

def newton(t, x0, v="x", steps=30):

    x = x0
    for _ in range(steps):
        step = evaluate(t, {v: x}) / evaluate(d, {v: x})
        x -= step
        if abs(step) < 1e-12:
            break
    return x

        return ("*", ("cos", t[1]), d(t[1]))
    op, a, b = t

---setup
def ev(t, x):
    if isinstance(t, float): return t
    if t == "x": return x
    if t[0] == "sin": return math.sin(ev(t[1], x))
    if t[0] == "cos": return math.cos(ev(t[1], x))
    a, b = ev(t[1], x), ev(t[2], x)
    return a + b if t[0] == "+" else a * b

Four cases: number, x, sin (with the chain rule), and the two binary operators.

```recall
Q: Explain to a friend why a computer can differentiate *any* formula with just a handful of rules, and why it then has to simplify.
A: Every formula is a tree, and each rule only needs to know the top node (a sum, a product, a sin) plus the derivatives of the children, which it gets by calling itself. Recursion walks the whole tree, so a few rules cover everything. But the rules are mechanical: they produce `*1`, `+0` and repeated copies of subtrees. Without simplification those leftovers are carried and differentiated again, so the tree (and the time to evaluate it) grows explosively.
```

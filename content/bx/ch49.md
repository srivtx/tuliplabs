## Look closely at this sentence

You've read thousands of words in this course, and every letter looked smooth. None of them are. Your screen is a grid of tiny squares that can't draw a curve. What's happening is a magic trick, performed thousands of times on every page, and this is the last piece of the waves story: **a smooth world, forced through a grid.**

A font file doesn't hold pictures of letters. It holds recipes, outlines made of curves, so that one file works at any size. The curves came from the car industry. Around 1960, two French engineers needed a way to describe car bodies to machines: Paul de Casteljau at Citroën, and Pierre Bézier at Renault. Citroën kept its work secret, so the curves carry Bézier's name. Decades later, the curves that shaped those car doors became the letters on your screen.

The whole construction is one operation.

```exercise
title: lerp
kind: write
---prompt
Write `lerp(a, b, t)`, for two points `(x, y)`. Return the point that's `t` of the way from `a` to `b`, as a tuple.
---starter

---solution
def lerp(a, b, t):
    return (a[0] + (b[0] - a[0]) * t, a[1] + (b[1] - a[1]) * t)
---tests
assert lerp((0, 0), (10, 20), 0.5) == (5, 10)
assert lerp((0, 0), (10, 20), 0) == (0, 0)

Start at `a`, and add `t` times the distance to `b`, for each coordinate.
```

Now use it on a list of points. Going part of the way along each neighbouring pair gives you a shorter list. Do that again and again until one point is left, and that point is on the curve. This is **de Casteljau's algorithm**, and it works for any number of points.

```exercise
title: curve_point
kind: write
---prompt
Write `curve_point(points, t)`. While there's more than one point, replace the list with `lerp` of each neighbouring pair. Return the last point left. (`lerp` is given in the starter.)
---starter
def lerp(a, b, t):
    return (a[0] + (b[0] - a[0]) * t, a[1] + (b[1] - a[1]) * t)

def curve_point(points, t):
    return points[0]
---solution
def lerp(a, b, t):
    return (a[0] + (b[0] - a[0]) * t, a[1] + (b[1] - a[1]) * t)

def curve_point(points, t):
    while len(points) > 1:
        points = [lerp(a, b, t) for a, b in zip(points, points[1:])]
    return points[0]
---tests
line = [(0, 0), (10, 0)]
assert curve_point(line, 0.3) == (3, 0), "two points is just a line"
arch = [(0, 0), (5, 10), (10, 0)]
assert curve_point(arch, 0.5) == (5, 5), "the curve goes towards the handle, but doesn't reach it"
assert curve_point(arch, 0) == (0, 0) and curve_point(arch, 1) == (10, 0), "it starts and ends on the end points"
s = [(0, 0), (0, 10), (10, 10), (10, 0)]
assert curve_point(s, 0.5) == (5, 7.5)
---hint
`zip(points, points[1:])` gives each neighbouring pair.
```

## A screen can't draw that

Graphics hardware works with straight edges, so a curve is cut into short lines first. How many?

Use **Size on screen** in the simulation. A small curve needs far fewer lines, because the screen can't show the difference. A fixed count is wasted on small text and looks faceted on a poster, so engines cut a curve in half until each piece is straight enough.

```exercise
title: flatten
kind: write
---prompt
Write `flatten(a, b, c, tol)` for a curve with three points, where `b` is the handle. Work out the curve's middle point `m` at `t = 0.5`. Its distance from the midpoint of the straight line `a` to `c` measures how bent the curve is. If that's `tol` or less, return `[a, c]`. Otherwise split the curve: the first half has points `a, lerp(a, b, 0.5), m` and the second has `m, lerp(b, c, 0.5), c`. Flatten both, and join the lists without repeating `m`.
---starter
def lerp(a, b, t):
    return (a[0] + (b[0] - a[0]) * t, a[1] + (b[1] - a[1]) * t)

def flatten(a, b, c, tol):
    return [a, c]
---solution
from math import dist

def lerp(a, b, t):
    return (a[0] + (b[0] - a[0]) * t, a[1] + (b[1] - a[1]) * t)

def flatten(a, b, c, tol):
    ab = lerp(a, b, 0.5)
    bc = lerp(b, c, 0.5)
    m = lerp(ab, bc, 0.5)
    if dist(m, lerp(a, c, 0.5)) <= tol:
        return [a, c]
    return flatten(a, ab, m, tol) + flatten(m, bc, c, tol)[1:]
---tests
assert flatten((0, 0), (5, 0), (10, 0), 0.1) == [(0, 0), (10, 0)], "already straight"
arch = flatten((0, 0), (5, 10), (10, 0), 1)
assert arch[0] == (0, 0) and arch[-1] == (10, 0)
assert (5, 5) in arch, "the middle of the curve is a cut"
assert len(flatten((0, 0), (5, 10), (10, 0), 0.1)) > len(arch), "tighter limit, more lines"
big = flatten((0, 0), (50, 100), (100, 0), 1)
assert len(big) > len(arch), "the same shape drawn bigger needs more lines"
---hint
It's recursive. Stop when bent little enough, and otherwise do both halves. The `[1:]` removes the repeated `m`.
```

There's a nice law hiding in here. A short piece of curve strays from its straight line by an amount that shrinks with the **square** of its length.

```predict
for lines in [4, 8, 16]:
    print(lines, 100 / lines ** 2)
```

So doubling the lines makes the error four times smaller. Four times the accuracy costs only twice the work, and that's why a modest number of lines looks perfectly smooth.

You might expect that splitting curves where they bend would always beat even steps. Measure it on a single smooth curve like the ones in a font, and the two come out about level, with halving sometimes costing more. The real saving is against a fixed count.

## What's inside a letter?

Now we have an outline made of straight lines, and need to know which points are inside. Here's the trick: from a point, look along a line to the right, and count the crossings. It's the same idea for any shape, however twisted.

The catch is the hole in a letter like **R** or **o**. Fonts solve it by giving outlines a direction. The outer edge runs one way and the hole runs the other. Count +1 for an edge going down and −1 for an edge going up. Inside the hole, the two cancel, and you get 0. That count is the **winding number**.

```exercise
title: winding
kind: write
---prompt
Write `winding(point, polygon)`. `polygon` is a list of `(x, y)` corners, and it's closed, so the last corner joins the first. For each edge `a` to `b`: if the edge crosses the height of the point, meaning `(a_y <= y) != (b_y <= y)`, work out the `x` where it crosses. If that's to the right of the point, add `1` when `b_y > a_y`, and `-1` otherwise. Return the total.
---starter
def winding(point, polygon):
    return 1
---solution
def winding(point, polygon):
    x, y = point
    total = 0
    for i, a in enumerate(polygon):
        b = polygon[(i + 1) % len(polygon)]
        if (a[1] <= y) != (b[1] <= y):
            cx = a[0] + (y - a[1]) / (b[1] - a[1]) * (b[0] - a[0])
            if cx > x:
                total += 1 if b[1] > a[1] else -1
    return total
---tests
square = [(0, 0), (10, 0), (10, 10), (0, 10)]
assert winding((5, 5), square) == 1, "inside"
assert winding((15, 5), square) == 0, "outside"
assert winding((-5, 5), square) == 0, "outside to the left: the crossings cancel"
assert winding((5, 5), square[::-1]) == -1, "the opposite direction"
hole = [(3, 3), (3, 7), (7, 7), (7, 3)]
assert winding((5, 5), square) + winding((5, 5), hole) == 0, "inside the hole"
assert winding((1, 5), square) + winding((1, 5), hole) == 1, "in the solid part"
---hint
The `!=` test is true only when one end is at or above the point's height, and the other is below it.
```

## Grey is a trick for position

Time to meet the grid.

```viz
name: bx-raster
title: A letter meets the grid
goal: At **12 pixels tall or fewer**, look at **Test the centre**, then **Measure coverage**, then turn on **Snap to pixels**.
height: 430
The red line is the exact outline. The box shows the result at one screen dot per pixel.
```

Testing the centre of each pixel gives you stairs. This is aliasing again, the same thing that made a fast sound fold down to a slow one in chapter 46. A sharp edge has frequencies higher than the grid can hold.

The fix is lovely. Instead of asking "is this pixel inside?", ask "**how much** of it is inside?" If an edge covers 30% of a pixel, paint it 30% grey. The eye blurs neighbouring pixels together, so it sees an edge sitting between pixels, at a position your screen can't really draw. **Grey buys you position.**

```exercise
title: coverage
kind: write
---prompt
Write `coverage(inside, px, py, n)`. `inside(x, y)` says whether a point is in the shape. Test an `n × n` grid of points in the pixel with its corner at `(px, py)`, where the points sit at `px + (i + 0.5) / n` and `py + (j + 0.5) / n`. Return the share of points that are inside, from 0 to 1.
---starter
def coverage(inside, px, py, n):
    return 1 if inside(px + 0.5, py + 0.5) else 0
---solution
def coverage(inside, px, py, n):
    hits = 0
    for j in range(n):
        for i in range(n):
            if inside(px + (i + 0.5) / n, py + (j + 0.5) / n):
                hits += 1
    return hits / (n * n)
---tests
left = lambda x, y: x < 0.25
assert coverage(left, 0, 0, 4) == 0.25, "a quarter of the pixel"
assert coverage(lambda x, y: True, 3, 3, 4) == 1
assert coverage(lambda x, y: False, 3, 3, 4) == 0
assert coverage(lambda x, y: x < 5.5, 5, 0, 2) == 0.5
assert coverage(lambda x, y: x + y < 1, 0, 0, 4) == 0.375
---hint
Two loops over the sample points. Count the hits and divide by the number of samples.
```

## Bending the truth

Now the honest problem. With coverage at 12 pixels tall, the stem of the R might land across two pixels, and it turns into two grey columns: soft, and pale. Slide the letter sideways by a fraction of a pixel and it changes again, so the same letter looks different at different places on the line.

The answer is **hinting**: nudge the outline so that the important edges land on whole pixels. The stem gets a bit wider or narrower than the design says, on purpose. For years, specialists hand-wrote these instructions for each letter at each size. It's an odd job when you think about it: making letters slightly wrong so that they look right.

```exercise
title: hint_stem
kind: write
---prompt
Write `snap_stem(left, width)`, the position of a stem in pixels. Round `width` to the nearest whole pixel, but never below 1. Round `left` to the nearest whole pixel. Return `(left, width)`.
---starter
def snap_stem(left, width):
    return left, width
---solution
def snap_stem(left, width):
    return round(left), max(1, round(width))
---tests
assert snap_stem(3.4, 1.8) == (3, 2)
assert snap_stem(7.6, 2.2) == (8, 2)
assert snap_stem(1.2, 0.3) == (1, 1), "a stem can never vanish"
assert snap_stem(0, 4) == (0, 4)
---hint
Two calls to `round`, and a `max`.
```

**Coloured stripes** is another clever cheat. Each pixel on many screens is really three thin lights, red, green and blue. Light them one at a time and you get three times the detail across. Magnified it looks like a mess of colour, but at real size your eye merges it. Microsoft shipped this as ClearType around 2000.

Then screens changed the rules. On a modern phone a pixel is so small that a letter is dozens of pixels tall, so the grid hardly matters and hinting has faded. In a way, the problem was solved by making the grid finer, though the mathematics never went away.

## What Part 14 was really about

Four chapters, one idea. A synthesizer stacks waves into sound. A kernel filters a picture the way your retina does. JPEG rewrites blocks as waves and throws away what you can't see. A font squeezes a perfect curve through a grid and hides the damage with grey.

Each time, reality is continuous and the machine is sampling it. Each time, the craft is knowing what a human will notice. Most of what you experience as a smooth, solid, complete world, on a screen and in your own head, is sampling, filtering and filling in.

```exercise
title: text_width
kind: write
---prompt
Write `text_width(text, advance, kern)`. `advance` maps each letter to its width. `kern` maps a two-letter string to an adjustment, for pairs that need moving closer or further apart, and pairs not listed are 0. Return the total width.
---starter
def text_width(text, advance, kern):
    return sum(advance[c] for c in text)
---solution
def text_width(text, advance, kern):
    total = sum(advance[c] for c in text)
    for a, b in zip(text, text[1:]):
        total += kern.get(a + b, 0)
    return total
---tests
```

```exercise
title: fit_label
kind: write
---prompt
Write `fit_size(width_at, max_width, biggest, smallest)`. `width_at(size)` gives the text's width at a whole-number size, and it grows with size. ---starter

---solution

    for size in range(biggest, smallest - 1, -1):
        if width_at(size) <= max_width:
            return size
    return None

assert fit_size(w, 60, 14, 6) == 6, "the smallest size is allowed"
---hint
`range(biggest, smallest - 1, -1)` counts down and includes `smallest`.
```

```recall
Q: Explain how a font's curve becomes pixels on a screen: how the curve is built, how it's cut into lines, how the program knows what's inside the letter, why edges look smooth, and why small text gets altered on purpose.
A: A font stores outlines made of Bézier curves. A point on one is found with de Casteljau's algorithm: go t of the way along each pair of neighbouring control points, and repeat until one point is left. Hardware deals with straight edges, so the curve is cut in half until each piece is straight enough, which means small text uses few lines, and doubling the lines cuts the error by four. To fill the shape, the winding number counts signed crossings to the right of a point. The outer outline and the hole run in opposite directions, so the count is non-zero in solid parts and 0 in the hole. Testing only pixel centres gives jagged stairs, which is aliasing. Measuring how much of each pixel is covered and painting that shade of grey lets the eye place an edge between pixels. At small sizes a stem can smear across two pixels and go soft, so hinting nudges the outline onto whole pixels, trading accuracy for readability. Subpixel rendering uses a pixel's red, green and blue stripes to get about three times the sideways detail.
```

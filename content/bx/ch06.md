## What a key-value database really does

A **key-value store** is the simplest database there is: `set(key, value)`, `get(key)`, `delete(key)`. That's the whole interface. Redis, Memcached, DynamoDB, RocksDB and the storage engine under many bigger databases all start from it.

The interface is easy. The hard part is the promise behind it: **after `set` returns, the value survives a crash**, and reads and writes stay fast even after millions of them. The design you'll build is called **Bitcask** (it powered the Riak database): a log on disk that only ever grows at the end, plus a small map in memory that remembers where each key's latest record is.

## A dict forgets everything

The obvious first try: a Python `dict`. Reads and writes are instant. But a dict lives in the process's memory. When the process crashes, or the machine loses power, it's gone.

So write it to a file. The obvious way is to save the **whole** dict every time something changes (like pressing Ctrl+S in an editor). It's correct, but count the bytes: every `set` rewrites *everything*, so the cost grows with the size of the database, not the size of the change.

In this chapter the "disk" is a `bytearray`: it behaves like a file you can append to and read slices of, and it runs anywhere.

```predict
import json
db = {}
written = 0
for i in range(4):
    db[f"user{i}"] = "x" * 10
    data = json.dumps(db).encode()
    written += len(data)
    print(i, len(data), written)
```

Look at the last column. Writing four 10-byte values cost hundreds of bytes, and it gets worse every time: n writes cost roughly n²/2 record-sizes. A database with a million keys would rewrite gigabytes to change one value.

## Append, don't rewrite

The fix: never touch old data. Every `set` **appends** one small record to the end of the log, like writing a new line in a diary. We'll use one line per record: `key<TAB>value<NEWLINE>`, as bytes.

Writes are now as cheap as they can be: you write exactly the new record. The cost moved to reads: to `get` a key you scan the **whole** log and keep the last record for that key (later records win, because they are newer).

## A hash index of byte offsets

Scanning is fine for ten records and hopeless for ten million. But notice: when we append a record, we **know exactly where it starts**: the length of the disk just before the append. Keep a dict in memory, `index[key] = (offset, length)`, and a read becomes: look up the offset, read that one slice, done.

That's the Bitcask idea. Memory holds only the keys and two numbers each; the values stay on disk. Writes are still pure appends, and reads now touch exactly one record. The dict in memory is not the database any more; it's a *map of the database*, and (as you'll see) it can always be rebuilt from the log.

## Deletes and compaction

Two problems are left, and both come from "never touch old data".

**Deletes.** You can't erase a record from the middle of the log. Instead you append a **tombstone**: a record that says "this key is gone". We'll write it as just `key\n` (no tab). Reading the log later, a tombstone wins over older values just like a newer value would.

**The log grows forever.** Set the same key a thousand times and you have 999 dead records. So Bitcask splits the log into **segments** (files of a fixed size). When one is full it's closed and never written again, and a new one starts. Closed segments can be **compacted** in the background: copy only the *live* records (the newest per key, minus deleted keys) into a fresh segment, then throw the old ones away. Nothing reading the database notices, because the index is just switched to point at the new copies.

```run
title: How much of the log is dead?
import random
random.seed(1)
disk = bytearray()
latest = {}
for i in range(1000):
    key = f"user{random.randint(1, 50)}"
    rec = f"{key}\t{random.randint(0, 9999)}\n".encode()
    latest[key] = rec
    disk += rec
live = sum(len(r) for r in latest.values())
print(f"log size {len(disk)} bytes, live data {live} bytes")
print(f"{100 * (1 - live / len(disk)):.0f}% of the log is old versions nobody can read")
```

```exercise
---solution
def compact(disk):
    latest = {}
    for line in bytes(disk).decode().split("\n"):
        if not line:
            continue
        if "\t" in line:
            k, v = line.split("\t", 1)
            latest[k] = v
        else:
            latest[line] = None
    new_disk, index = bytearray(), {}
    for k, v in latest.items():
        if v is None:
            continue
        rec = f"{k}\t{v}\n".encode()
        index[k] = (len(new_disk), len(rec))
        new_disk += rec
    return new_disk, index
```

## Crash recovery and torn writes

Now pull the plug. Memory is wiped, so the **index is gone**. But the log is on disk, and the log is the truth: replay it from the start, and for every record set `index[key] = (offset, length)` (or remove the key for a tombstone). Afterwards the index is exactly what it was. That's **crash recovery by replaying the log**, and it's why "append only" is such a strong idea: there is never a half-updated structure on disk to repair.

Almost never. If the power dies *while* a record is being written, the end of the log holds a **torn write**: half a record. Worse, a disk can return garbage for a damaged block. So every record carries a **checksum**: a number computed from its bytes. On replay, recompute it; if it doesn't match, the record is broken, and so is everything after it, so stop there and cut the log off. The format becomes `crc<TAB>key<TAB>value<NEWLINE>`, where `crc` is `zlib.crc32` of `key\tvalue` in 8 hex digits.

```predict
import zlib
good = zlib.crc32(b"cat\tmeow")
print(f"{good:08x}")
damaged = zlib.crc32(b"cat\tmeom")
print(f"{damaged:08x}")
print(zlib.crc32(b"cat\tmeow") == good)
```

One wrong letter gives a completely different checksum. That's what makes it a good detector: random damage almost never produces a matching number.

## Real-world project: a URL shortener backend

```project
title: tinylink: a URL shortener on your own storage engine
client: A school newsletter that prints links on paper

Long links don't fit on a printed page. `tinylink` turns `https://example.org/very/long/path?with=params` into `t.ly/3f` and redirects anyone who visits it. ---why
URL shorteners (bit.ly), session stores (a login cookie → user id), shopping carts and feature flags are all key-value workloads: tiny records, lots of reads, a "latest value wins" rule. Bitcask itself was built for Riak; the same log + index + compaction pattern is inside Kafka, RocksDB's write-ahead log, PostgreSQL's WAL and every database that promises not to lose a committed write.

- Wrap your KV store in a `Shortener` with `shorten(url)` and `resolve(code)`

- Restore the counter after a restart by replaying the log, not by trusting memory
- Return the existing code if the same URL is shortened twice (a second index: url → code)
- Run compaction when more than half the log is dead records
---stretch
- Count visits per code without making the log explode (hint: batch the counters)
```

```exercise
def base62(n):

    while n:
```

## Rebuild it and explain it

```exercise

---solution
class Store:
    def __init__(self, disk=None):
        self.disk = disk if disk is not None else bytearray()
        self.index = {}
        offset = 0
        for line in bytes(self.disk).split(b"\n")[:-1]:
            text = line.decode()
            if "\t" in text:
                self.index[text.split("\t", 1)[0]] = (offset, len(line) + 1)
            else:
                self.index.pop(text, None)
            offset += len(line) + 1
    def set(self, key, value):
        rec = f"{key}\t{value}\n".encode()
        self.index[key] = (len(self.disk), len(rec))
        self.disk += rec
    def get(self, key):
        if key not in self.index:
            return None
        o, n = self.index[key]
        return bytes(self.disk[o:o + n]).decode().rstrip("\n").split("\t", 1)[1]
    def delete(self, key):
        self.disk += f"{key}\n".encode()
        self.index.pop(key, None)
```

```recall
Q: In a Bitcask-style store, what is on disk, what is in memory, and why can you lose the memory part safely?
A: On disk: an append-only log of records (newest version wins, tombstones for deletes), split into segments that compaction rewrites to drop dead records. In memory: a hash index from each key to the byte offset (and length) of its newest record, so a read is one lookup plus one small disk read. The index is only a cache of where things are: after a crash you rebuild it by replaying the log from the start, and checksums let you detect and cut off a torn final write.
```

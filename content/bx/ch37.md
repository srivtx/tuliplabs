## Three questions every scheduler answers

**When?** Recurring jobs are written as **cron** expressions: five fields, `minute hour day-of-month month day-of-week`. `*/15 9-17 * * 1-5` means "every 15 minutes, 9 to 5, Monday to Friday". `0 3 * * *` is "3 a.m. every day".

**In what order?** Jobs that are due wait in a **queue**. A delayed or prioritised queue is a heap of `(run_at, priority, seq, job)`: the earliest first, the most important first among equals, first-come among those.

**What if it fails?** Networks blip and services go down. A good scheduler **retries**, but not straight away: hammering a service that's struggling keeps it down. **Exponential backoff** waits 1 s, 2 s, 4 s, 8 s… (with a cap), and **jitter** adds a random part so a thousand failed jobs don't all retry in the same instant. After too many tries, the job goes to a **dead-letter queue** for a human to look at.

```viz

title: Six jobs, one flaky service
goal: Run **retry every second** to the end, then run **exponential backoff + jitter** and compare.

```

Retries mean a job can run **more than once** (it may have half-worked before failing, or succeeded but the reply was lost). So jobs must be **idempotent**: running twice has the same effect as once. Charge a card with a unique payment key, not "charge £10".

```exercise
title: cron_field
kind: write
---prompt
Write `field_values(spec, lo, hi)`: all the numbers from lo to hi that a single cron field allows, as a sorted list. A field is a comma-separated list of parts, and each part is `*`, a number `n`, a range `a-b`, or any of those followed by `/step` (`*/15`, `10-30/5`). `*` means lo to hi.
---starter
def field_values(spec, lo, hi):
    if spec == "*":
        return list(range(lo, hi + 1))
    return [int(spec)]
---solution
def field_values(spec, lo, hi):
    out = set()
    for part in spec.split(","):
        rng, _, step = part.partition("/")
        step = int(step) if step else 1
        if rng == "*":
            a, b = lo, hi
        elif "-" in rng:
            a, b = map(int, rng.split("-"))
        else:
            a = b = int(rng)
            if step > 1:
                b = hi
        out.update(range(a, b + 1, step))
    return sorted(v for v in out if lo <= v <= hi)
---tests
assert field_values("*", 0, 5) == [0, 1, 2, 3, 4, 5]
assert field_values("*/15", 0, 59) == [0, 15, 30, 45]
assert field_values("9-17", 0, 23) == list(range(9, 18))
assert field_values("1,15,30", 1, 31) == [1, 15, 30]
assert field_values("10-30/10,59", 0, 59) == [10, 20, 30, 59]
assert field_values("1-5", 0, 6) == [1, 2, 3, 4, 5]
---hint
The starter handles `*` and a single number. Split on commas first, then split each part on `/`, then handle `*`, `a-b` or `n`.
---hint
`part.partition("/")` gives the range and the step in one go (step is `""` when there's none).
```

```exercise
from datetime import datetime, timedelta

def field_values(spec, lo, hi):
    out = set()
    for part in spec.split(","):
        rng, _, step = part.partition("/")
        step = int(step) if step else 1
        if rng == "*":
            a, b = lo, hi
        elif "-" in rng:
            a, b = map(int, rng.split("-"))
        else:
            a = b = int(rng)
            if step > 1:
                b = hi
        out.update(range(a, b + 1, step))
    return sorted(v for v in out if lo <= v <= hi)

def next_run(expr, after):
    m, h, d, mo, wd = expr.split()
    M, H, D = set(field_values(m, 0, 59)), set(field_values(h, 0, 23)), set(field_values(d, 1, 31))
    MO, WD = set(field_values(mo, 1, 12)), set(field_values(wd, 0, 6))
    t = after.replace(second=0, microsecond=0) + timedelta(minutes=1)
    for _ in range(366 * 24 * 60 * 5):
        if t.month not in MO or t.day not in D or t.weekday() not in WD:
            t = (t + timedelta(days=1)).replace(hour=0, minute=0)
            continue
        if t.hour in H and t.minute in M:
            return t
        t += timedelta(minutes=1)
    return None
---tests

assert next_run("0 3 * * *", now) == datetime(2026, 11, 4, 3, 0)
assert next_run("30 9 * * 0", now) == datetime(2026, 11, 9, 9, 30), "next Monday"
assert next_run("0 0 1 1 *", now) == datetime(2027, 1, 1, 0, 0)
assert next_run("7 10 * * *", now) == datetime(2026, 11, 4, 10, 7), "strictly after, so not right now"

---hint
The starter just adds a minute. Parse the five fields into sets, then walk forward from one minute after `after`.
---hint
If the day, month or weekday doesn't match, jump to midnight of the next day. Otherwise check hour and minute and step one minute.
```

## Queues and retries

```exercise
title: delayed_queue
kind: write
---prompt
Write `Scheduler` with `add(name, run_at, priority=0)` and `due(now)`: remove and return the names of every job with `run_at <= now`, ordered by run time, then **higher** priority first, then the order they were added.
---starter
class Scheduler:
    def __init__(self):
        self.jobs = []

    def add(self, name, run_at, priority=0):
        self.jobs.append((run_at, name))

    def due(self, now):
        out = [n for t, n in self.jobs if t <= now]
        self.jobs = [(t, n) for t, n in self.jobs if t > now]
        return out
---solution
import heapq

class Scheduler:
    def __init__(self):
        self.heap, self.seq = [], 0

    def add(self, name, run_at, priority=0):
        heapq.heappush(self.heap, (run_at, -priority, self.seq, name))
        self.seq += 1

    def due(self, now):
        out = []
        while self.heap and self.heap[0][0] <= now:
            out.append(heapq.heappop(self.heap)[3])
        return out
---tests
s = Scheduler()
s.add("report", 10); s.add("email", 5); s.add("backup", 5, priority=2); s.add("cleanup", 5)
assert s.due(4) == []
assert s.due(5) == ["backup", "email", "cleanup"]
s.add("late", 7)
assert s.due(100) == ["late", "report"]
assert s.due(100) == []
---hint
The starter returns jobs in the order they were added, ignoring time and priority. Use a heap of `(run_at, -priority, seq, name)`.
```

```exercise
title: backoff
kind: write
---prompt
Write `backoff(attempt, base, cap, rand)`: the wait before retry number `attempt` (1, 2, 3, …). The ceiling is `min(cap, base * 2 ** (attempt - 1))`; with "full jitter" the wait is `rand * ceiling`, where `rand` is a number in [0, 1) supplied by the caller (so tests are repeatable). Then write `retry_times(fail_until, base, cap, rands)`: a job first runs at time 0 and fails every time it runs before `fail_until`; return the list of times it runs (the last one succeeds). Use `rands[k]` for the k-th retry. If it runs out of `rands`, it gives up: return the times so far.
---starter
def backoff(attempt, base, cap, rand):
    return base

def retry_times(fail_until, base, cap, rands):
    return [0]
---solution
def backoff(attempt, base, cap, rand):
    return rand * min(cap, base * 2 ** (attempt - 1))

def retry_times(fail_until, base, cap, rands):
    times, t = [0], 0
    for k, r in enumerate(rands, 1):
        if t >= fail_until:
            break
        t += backoff(k, base, cap, r)
        times.append(t)
    return times
---tests
assert backoff(1, 1, 60, 0.5) == 0.5
assert backoff(4, 1, 60, 1.0) == 8
assert backoff(10, 1, 60, 1.0) == 60, "capped"
assert backoff(3, 2, 60, 0.25) == 2
assert retry_times(10, 1, 60, [1, 1, 1, 1, 1]) == [0, 1, 3, 7, 15]
assert retry_times(0, 1, 60, [1, 1]) == [0], "succeeds first time"
assert retry_times(5, 2, 4, [1, 1, 1, 1]) == [0, 2, 6], "the third wait is capped at 4"
assert retry_times(1000, 1, 60, [1, 1]) == [0, 1, 3], "gives up when it runs out of retries"
---hint
The ceiling doubles each attempt until it hits the cap; jitter scales it by `rand`.
---hint
In `retry_times`, keep the current time. Stop as soon as the time reaches `fail_until` (that run succeeded) or you run out of retries.
```

```quiz

- Retrying faster

- A longer timeout
- Running it at night
> At-least-once delivery plus idempotent jobs gives exactly-once effects.
```

```exercise
title: idempotent_jobs
kind: write
---prompt
Write `Payments` with `charge(key, amount)`: the first call with a given idempotency key records the charge and returns `"charged"`; any later call with the same key changes nothing and returns `"duplicate"`. A call reusing a key with a **different** amount raises `ValueError` (that's a bug in the caller). `total()` returns the sum actually charged.
---starter
class Payments:
    def __init__(self):
        self.amounts = []

    def charge(self, key, amount):
        self.amounts.append(amount)
        return "charged"

    def total(self):
        return sum(self.amounts)
---solution
class Payments:
    def __init__(self):
        self.seen = {}

    def charge(self, key, amount):
        if key in self.seen:
            if self.seen[key] != amount:
                raise ValueError("same key, different amount")
            return "duplicate"
        self.seen[key] = amount
        return "charged"

    def total(self):
        return sum(self.seen.values())
---tests
p = Payments()
assert p.charge("inv-1", 1000) == "charged"
assert p.charge("inv-1", 1000) == "duplicate"
assert p.charge("inv-2", 250) == "charged"
for _ in range(5):
    p.charge("inv-2", 250)
assert p.total() == 1250
try:
    p.charge("inv-1", 9999)
    assert False, "reusing a key with a new amount is an error"
except ValueError:
    pass
---hint
The starter charges every call. Remember each key and the amount it was used with.
```

```recall
Q: Explain how a job scheduler works: cron expressions and finding the next run, a delayed priority queue, retries with exponential backoff and jitter, dead-letter queues, and why jobs must be idempotent.
A: Recurring jobs are cron expressions with five fields (minute, hour, day of month, month, day of week), each allowing *, numbers, lists, ranges and /steps. The next run is found by walking forward from just after now, skipping whole days whose day, month or weekday can't match, and returning the first minute whose hour and minute match. Due and delayed jobs sit in a heap keyed by (run time, minus priority, sequence), so the earliest, most important, oldest job is popped first. When a job fails it's retried after a wait that doubles each time (exponential backoff) up to a cap, multiplied by a random factor (jitter) so jobs that failed together don't retry together and overload a recovering service. After a maximum number of tries the job moves to a dead-letter queue for a person to inspect. Because a job may run more than once (it can fail after doing part of its work, or its success reply can be lost), jobs must be idempotent: they carry a unique key, and the receiving side ignores repeats, so at-least-once delivery has exactly-once effects.
```

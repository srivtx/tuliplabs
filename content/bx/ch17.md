## Why files shrink

A text file stores every character in 8 bits, whether it's the common `e` or the rare `z`. That's wasteful in two ways, and the two main ideas in compression fix one each:

1. **Some symbols are more common than others.** Give them shorter codes (Huffman coding).
2. **Whole chunks repeat.** Store "copy the 12 characters from 40 back" instead of the chunk itself (LZ77).

ZIP, gzip and PNG all use exactly these two ideas together, in a format called DEFLATE.

## The simplest compressor: run-length encoding

If the data has long runs, like `aaaaabbbcc`, store each run once with its length: `a5b3c2`. Old fax machines and simple image formats such as BMP's RLE mode do this.

That last test shows the catch: on text without runs, RLE **doubles** the size. Every compressor makes some inputs bigger; good ones choose which inputs win.

## Short codes for common symbols

Morse code already knew this: `E` is a single dot, `Q` is `--.-`. But Morse needs pauses between letters, otherwise `..` could be `I` or `EE`. The fix is a **prefix-free** code: no code is the beginning of another, so a decoder always knows where one symbol ends.

Huffman's algorithm builds the best possible prefix-free code:

1. Make one tree per symbol, weighted by its count.
2. Take the two lightest trees and join them under a new parent whose weight is their sum.
3. Repeat until one tree is left. Left edges are 0, right edges are 1; each symbol's code is its path.

```quiz
Why are Huffman codes always prefix-free?
- Because the algorithm checks every pair of codes
* Because every symbol is a leaf, and a path to one leaf can't pass through another leaf
- Because the codes are sorted by length
- They aren't; a decoder needs separators
> Symbols only live at leaves. A code that's a prefix of another would mean one symbol sits on the path to another, which would make it an internal node. So the tree shape guarantees it.
```

```parsons
title: Build the tree with a heap
---lines
def huffman_tree(text):
    heap = [(w, i, ch) for i, (ch, w) in enumerate(Counter(text).items())]
    heapq.heapify(heap)
    i = len(heap)
    while len(heap) > 1:
        w1, _, a = heapq.heappop(heap)
        w2, _, b = heapq.heappop(heap)
        heapq.heappush(heap, (w1 + w2, i, (a, b)))
        i += 1
    return heap[0][2]
?? heapq.heappush(heap, (w1 * w2, i, (a, b)))
---tests
tree = huffman_tree("aaab")
assert tree in (("b", "a"), ("a", "b")), tree
tree = huffman_tree("aaaabbc")
assert isinstance(tree, tuple) and "a" in tree, "the commonest letter hangs right under the root"
```

The middle number `i` in each heap entry is a tie-breaker: when two weights are equal, Python would otherwise try to compare a letter with a tuple and crash.

        w2, _, b = heapq.heappop(heap)
        heapq.heappush(heap, (w1 + w2, i, (a, b)))
        i += 1

---starter

---solution
def huffman_codes(text):
    tree = huffman_tree(text)
    if isinstance(tree, str):
        return {tree: "0"}
    codes = {}
    def walk(node, path):
        if isinstance(node, str):
            codes[node] = path
        else:
            walk(node[0], path + "0")
            walk(node[1], path + "1")
    walk(tree, "")
    return codes
---tests
text = "abracadabra alakazam"
c = huffman_codes(text)

codes = list(c.values())
assert all(not b.startswith(a) for a in codes for b in codes if a != b), "prefix-free"
assert sum(len(c[ch]) for ch in text) == 55, f"optimal total is 55 bits, got {sum(len(c[ch]) for ch in text)}"
assert len(c["a"]) == min(map(len, codes)), "the commonest letter has the shortest code"

---hint
Recursive walk: at a string, record the path so far; at a tuple, go left adding `"0"` and right adding `"1"`.

---solution
def encode(text, codes):
    return "".join(codes[ch] for ch in text)

def decode(bits, codes):
    back = {code: ch for ch, code in codes.items()}
    out, cur = [], ""
    for b in bits:
        cur += b
        if cur in back:
            out.append(back[cur])
            cur = ""
    return "".join(out)
---tests

## How small can it get? Entropy

Claude Shannon showed in 1948 that if symbols appear with probabilities p₁, p₂, …, no lossless code can average fewer than

    H = −Σ p · log₂ p     bits per symbol

That's the **entropy**: a measure of how unpredictable the data is. Huffman gets within 1 bit per symbol of it, and usually much closer.

```exercise
title: entropy
kind: write
---prompt
Write `entropy(text)` returning the entropy in bits per symbol, using the character frequencies in `text`.
---starter
def entropy(text):
    return 0.0
---solution
def entropy(text):
    n = len(text)
    return -sum(c / n * math.log2(c / n) for c in Counter(text).values())
---tests
assert entropy("aaaa") == 0, "no surprise at all"
assert abs(entropy("abab") - 1) < 1e-9, "two equally likely symbols: 1 bit"
assert abs(entropy("abcdefgh") - 3) < 1e-9, "eight equally likely: 3 bits"
assert abs(entropy("abracadabra alakazam") - 2.6955) < 1e-3, entropy("abracadabra alakazam")
---hint
Count each character, turn counts into probabilities `c / n`, and sum `-p * log2(p)`.
```

```quiz
Why can't any compressor shrink every file?
- Because computers store files in fixed blocks
* There are fewer short files than long ones, so if some files get shorter, others must get longer
- Because of entropy in the CPU
- It's possible, but too slow
> The pigeonhole principle: there are 2ⁿ files of n bits but fewer than 2ⁿ files shorter than n bits. A compressor can't map them all to shorter files and still decode uniquely. That's why zipping a ZIP (or random data) doesn't help.
```

## Repeated chunks: LZ77

Huffman squeezes single symbols. LZ77 (the "Z" in ZIP's family tree) squeezes **repetition**: when text repeats something earlier, write a back-reference `(distance, length)`: go back `distance` characters and copy `length` of them.

    "blah blah blah!"  →  b l a h ␣ (5, 9) !

The copy can **overlap itself**: `(5, 9)` copies 9 characters starting 5 back, so it re-reads characters it has just written. That's how a short token produces a long run.

```exercise
title: lz_decode
kind: write
---prompt
Write `lz_decode(tokens)` where each token is either a one-character string (a literal) or a tuple `(distance, length)` meaning "copy `length` characters, starting `distance` back from the current end". Copy one character at a time, so overlapping copies work.
---starter
def lz_decode(tokens):
    return ""
---solution
def lz_decode(tokens):
    out = []
    for t in tokens:
        if isinstance(t, str):
            out.append(t)
        else:
            dist, length = t
            for _ in range(length):
                out.append(out[-dist])
    return "".join(out)
---tests
assert lz_decode(["a", "b", "c", (3, 3)]) == "abcabc", "a plain copy"
assert lz_decode(list("blah ") + [(5, 9), "!"]) == "blah blah blah!", "an overlapping copy"
assert lz_decode(["a", (1, 7)]) == "aaaaaaaa", "run-length encoding falls out for free"
---hint
Keep the output as a list. For a copy, append `out[-dist]` one character at a time: each append makes the just-copied character available for the next step.
```

## Rebuild it and explain it

```exercise
title: rle_rebuild
kind: rebuild
---prompt
From memory: write `rle_encode(s)` returning a string like `"a5b3c2"` and `rle_decode(t)` that reverses it. Counts can have several digits (`"x12"`); characters are never digits.
---starter
def rle_encode(s):
    pass

def rle_decode(t):
    pass
---solution
def rle_encode(s):
    out, i = [], 0
    while i < len(s):
        j = i
        while j < len(s) and s[j] == s[i]:
            j += 1
        out.append(f"{s[i]}{j - i}")
        i = j
    return "".join(out)

def rle_decode(t):
    out, i = [], 0
    while i < len(t):
        ch, j = t[i], i + 1
        while j < len(t) and t[j].isdigit():
            j += 1
        out.append(ch * int(t[i + 1:j]))
        i = j
    return "".join(out)
---tests
assert rle_encode("aaaaabbbcc") == "a5b3c2"
assert rle_decode("a5b3c2") == "aaaaabbbcc"
assert rle_decode(rle_encode("x" * 12 + "y")) == "x" * 12 + "y" and rle_encode("x" * 12) == "x12", "multi-digit counts"
assert rle_encode("") == "" and rle_decode("") == "", "empty"
---hint
Encode: find each run's end with an inner loop. Decode: read one character, then all the digits after it.
```

```recall
Q: Explain how lossless compression works, using Huffman coding and LZ77, and what limits it.
A: Compression removes predictability. Huffman coding gives short codes to common symbols and long codes to rare ones: start with one tree per symbol weighted by its count, repeatedly merge the two lightest, and read each code as the left/right path from the root. Because symbols sit only at leaves, the codes are prefix-free, so the bit stream decodes without separators. LZ77 handles repetition: it replaces a repeated chunk with a back-reference saying how far back to look and how much to copy, and copies may overlap to produce runs. DEFLATE (ZIP, gzip, PNG) runs LZ77 then Huffman. Shannon's entropy, minus the sum of p log2 p, is the lower bound on average bits per symbol for a source, and the pigeonhole principle means no compressor can shrink every input: some must grow, which is why random or already-compressed data doesn't compress.
```

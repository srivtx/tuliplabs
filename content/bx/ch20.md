## One copy is one crash away from gone

A database on one server loses everything when that disk dies, and is down whenever that server is. So real systems keep **copies** on several servers. But copies create a new problem: two clients write at the same moment to different servers, a network cable is cut, a server reboots halfway through. Now the copies disagree. Which one is right?

The servers need to agree on **one** sequence of writes, even while some of them are crashed or unreachable. That's **consensus**, and the algorithm most systems use for it today (etcd, which runs Kubernetes; Consul; CockroachDB; TiDB) is **Raft**. It was designed in 2014 to be *understandable*, and you'll build its core in this chapter.

The whole design rests on one fact: **any two majorities of the same group share at least one member.** If 3 of 5 servers agreed on something, any later group of 3 includes at least one that remembers it.

## Terms and elections

Raft splits time into numbered **terms**. Each term starts with an election and has at most one leader. Every message carries its sender's term, and a server that sees a higher term than its own updates its term and becomes a follower at once: that's how a stale leader finds out it's been replaced.

Each server votes at most once per term, first come, first served, with one more condition: it only votes for a candidate whose log is **at least as up to date** as its own. Compare the **term of the last entry** first (the later term wins); if those are equal, the longer log wins.

```exercise
title: up_to_date_bug
kind: bug
---prompt
`up_to_date(my_log, last_idx, last_term)` should say whether a candidate's log (its length `last_idx` and the term of its last entry `last_term`) is at least as up to date as `my_log` (a list of terms, one per entry). It gives the wrong answer whenever the last terms differ. Fix it.
---starter
def up_to_date(my_log, last_idx, last_term):
    my_last = my_log[-1] if my_log else 0
    if last_term != my_last:
        return last_term < my_last
    return last_idx >= len(my_log)
---solution
def up_to_date(my_log, last_idx, last_term):
    my_last = my_log[-1] if my_log else 0
    if last_term != my_last:
        return last_term > my_last
    return last_idx >= len(my_log)
---tests
assert up_to_date([1, 1, 1], 2, 2), "shorter, but its last entry is from a later term"
assert not up_to_date([1, 2], 5, 1), "longer, but stuck in an older term"
assert up_to_date([1, 2], 2, 2), "identical"
assert not up_to_date([1, 2], 1, 2), "same last term, but shorter"
assert up_to_date([], 0, 0), "two empty logs"
---hint
When the last terms differ, the candidate is up to date only if its last term is the *later* one.
```

```exercise
title: grant_vote
kind: write
---prompt
Write `grant_vote(state, term, candidate, last_idx, last_term)`. `state` is a dict `{"term", "voted_for", "log"}` (the log is a list of terms). Follow Raft's rules, updating `state` in place:

1. A request from an older term (`term < state["term"]`) is refused.
2. A request from a newer term moves this server to that term, with no vote cast yet (`voted_for = None`).
3. Grant the vote (and record it) if this server hasn't voted this term, or already voted for this same candidate, **and** the candidate's log is up to date (use the rule from the last exercise).

Return `True` if the vote is granted.
---starter
def grant_vote(state, term, candidate, last_idx, last_term):
    return False
---solution
def grant_vote(state, term, candidate, last_idx, last_term):
    if term < state["term"]:
        return False
    if term > state["term"]:
        state["term"], state["voted_for"] = term, None
    log = state["log"]
    my_last = log[-1] if log else 0
    ok_log = last_term > my_last or (last_term == my_last and last_idx >= len(log))
    if state["voted_for"] in (None, candidate) and ok_log:
        state["voted_for"] = candidate
        return True
    return False
---tests
s = {"term": 1, "voted_for": None, "log": [1, 1]}
assert grant_vote(s, 2, "A", 2, 1) and s["term"] == 2 and s["voted_for"] == "A", "a new term, a fine log: yes"
assert not grant_vote(s, 2, "B", 5, 1), "already voted for A this term"
assert grant_vote(s, 2, "A", 2, 1), "A asking again (a retried request) is fine"
s2 = {"term": 3, "voted_for": None, "log": [1, 3]}
assert not grant_vote(s2, 4, "C", 5, 2) and s2["term"] == 4, "older last term: refused, but the term still moves up"
assert grant_vote(s2, 4, "D", 2, 3), "D's log is as good as ours"
assert not grant_vote(s2, 3, "E", 9, 9), "a stale term is always refused"
---hint
Check the term first, then the vote, then the log. `state["voted_for"] in (None, candidate)` covers both "not voted" and "voted for you already".
```

Why do elections usually end in one round? Each follower waits a **random** timeout (say 150–300 ms) without hearing a leader before it stands. One server nearly always wakes up first and collects its votes before anyone else even starts.

```quiz
What goes wrong if every server uses exactly the same election timeout?
- Nothing: the timeout only matters for heartbeats
* They all become candidates together, each votes for itself, nobody gets a majority, and this can repeat forever
- Two leaders get elected in the same term
- The log entries get out of order
> A split vote just means a new term and another try, so safety is fine, but the cluster could stay leaderless indefinitely. Randomness breaks the symmetry.
```

## Replicating the log

Once elected, the leader handles every write: it appends the write to its own log, then sends it to every follower in an **AppendEntries** message. Each message also says where the new entries go: the index and term of the entry just **before** them. The follower accepts only if its log has a matching entry there. If not, it says no, and the leader retries one entry earlier, until they find the point where their logs agree.

That one check gives Raft its **log matching property**: if two logs have an entry with the same index and term, everything up to that point is identical.

```exercise
title: append_entries
kind: write
---prompt
Write `append_entries(log, prev_idx, prev_term, entries)` for a follower. `log` and `entries` are lists of `(term, command)`; indexes count from 1, and `prev_idx = 0` means "from the start". Return `(ok, new_log)`:

- If the consistency check fails, return `(False, log)` unchanged.
- Otherwise place each new entry at index `prev_idx + 1`, `prev_idx + 2`, …: if an entry already there has a **different term**, delete it and everything after it; if it's the same, keep it; append entries the log doesn't have yet.

Don't simply cut the log at `prev_idx`: a delayed, duplicated message would then delete entries the leader already counted as stored here.
---starter
def append_entries(log, prev_idx, prev_term, entries):
    return False, log
---solution
def append_entries(log, prev_idx, prev_term, entries):
    if prev_idx > len(log) or (prev_idx > 0 and log[prev_idx - 1][0] != prev_term):
        return False, log
    new = list(log)
    for i, e in enumerate(entries):
        k = prev_idx + i
        if k < len(new) and new[k][0] != e[0]:
            new = new[:k]
        if k >= len(new):
            new.append(e)
    return True, new
---tests
log = [(1, "a"), (1, "b")]
assert append_entries(log, 2, 1, [(2, "c")]) == (True, [(1, "a"), (1, "b"), (2, "c")]), "a plain append"
assert append_entries(log, 3, 2, [(2, "d")]) == (False, log), "we don't have entry 3 yet: the leader must step back"
assert append_entries([(1, "a"), (1, "b"), (1, "x"), (1, "y")], 2, 1, [(2, "c")]) == (True, [(1, "a"), (1, "b"), (2, "c")]), "a conflict at entry 3 deletes it and everything after"
full = [(1, "a"), (1, "b"), (1, "c")]
assert append_entries(full, 1, 1, [(1, "b")]) == (True, full), "an old duplicate message deletes nothing"
assert append_entries(log, 0, 0, []) == (True, log), "a heartbeat"
---hint
First the check from the parsons puzzle. Then walk the new entries with their position `k = prev_idx + i` (0-based in the Python list): truncate on a term conflict, append when `k` is past the end.
```

## When is a write safe?

An entry is **committed** once the leader has stored it on a majority. From then on it's permanent: any future leader needs votes from a majority, that majority includes a server with the entry, and the up-to-date rule means a server missing it can't win. Only committed entries are applied to the database and reported to clients as done.

There's one subtle extra rule: a leader only commits entries **from its own term** by counting copies. Older entries become committed along with them. (The Raft paper's Figure 8 shows how counting old-term copies can commit an entry that a later leader then overwrites.)

```exercise
title: commit_index
kind: write
---prompt
Write `commit_index(match, log_terms, term)`. `match` has one number per server, **including the leader**: how many entries of the leader's log that server is known to store. `log_terms` is the term of each entry in the leader's log, and `term` is the leader's current term. Return the largest `k` such that more than half the servers have at least `k` entries **and** entry `k` is from the current term, or `0` if there is none.
---starter
def commit_index(match, log_terms, term):
    return 0
---solution
def commit_index(match, log_terms, term):
    n = len(match)
    for k in range(len(log_terms), 0, -1):
        if sum(m >= k for m in match) > n // 2 and log_terms[k - 1] == term:
            return k
    return 0
---tests
assert commit_index([5, 5, 3, 2, 1], [1, 1, 2, 2, 2], 2) == 3, "3 of 5 servers have entries 1 to 3"
assert commit_index([5, 5, 3, 2, 1], [1, 1, 2, 2, 3], 3) == 0, "entry 3 is on a majority, but it's from an older term"
assert commit_index([5, 5, 5, 1, 1], [1, 1, 2, 2, 3], 3) == 5, "entry 5 is from this term, which commits 1 to 4 too"
assert commit_index([2, 2, 2], [1, 1], 1) == 2
assert commit_index([1], [], 1) == 0, "an empty log"
---hint
Try each `k` from the end of the log down to 1, count how many servers have `m >= k`, and stop at the first `k` that passes both checks.
```

```exercise
title: apply_committed
kind: write
---prompt
The log only stores commands; the **state machine** is what they build. Write `apply(log, commit)` that runs the first `commit` entries of `log` (a list of `(term, command)`) against an empty dict and returns it. Commands are `"set KEY VALUE"` and `"del KEY"` (deleting a missing key does nothing). Uncommitted entries must not be applied.
---starter
def apply(log, commit):
    return {}
---solution
def apply(log, commit):
    db = {}
    for term, cmd in log[:commit]:
        parts = cmd.split()
        if parts[0] == "set":
            db[parts[1]] = parts[2]
        elif parts[0] == "del":
            db.pop(parts[1], None)
    return db
---tests
log = [(1, "set x 1"), (1, "set y 2"), (2, "del x"), (2, "set y 3")]
assert apply(log, 4) == {"y": "3"}
assert apply(log, 2) == {"x": "1", "y": "2"}, "only the committed prefix"
assert apply(log, 0) == {}
assert apply([(1, "del z")], 1) == {}, "deleting a missing key is harmless"
---hint
`cmd.split()` gives `["set", "x", "1"]`. `dict.pop(key, None)` removes a key if it's there.
```

Because every server applies the **same** committed entries in the **same** order, every server ends up with the same database. That's the trick behind every replicated database: agree on the log, and the data follows.

## Rebuild it and explain it

```exercise
title: commit_rebuild
kind: rebuild
---prompt
From memory: write `majority_index(match)` that returns the largest `k` stored on more than half the servers, where `match[i]` is how many log entries server `i` has (ignore the current-term rule this time). Do it by sorting.
---starter
def majority_index(match):
    pass
---solution
def majority_index(match):
    s = sorted(match, reverse=True)
    return s[len(s) // 2]
---tests
assert majority_index([5, 5, 3, 2, 1]) == 3
assert majority_index([1, 1, 1]) == 1
assert majority_index([7, 0, 0]) == 0, "only the leader has anything"
assert majority_index([4, 4, 2, 1]) == 2, "with 4 servers, 3 of them must have it"
---hint
Sort from most to fewest. The value at position `len // 2` is held by that server and every server before it: `len // 2 + 1` servers, a majority.
```

```recall
Q: Explain how Raft keeps five servers agreeing on one log while servers crash and come back.
A: Time is split into terms, each with at most one leader. Followers that hear nothing from a leader for a random timeout become candidates, start a new term and ask for votes; a server votes once per term, and only for a candidate whose log is at least as up to date (later last term, or same last term and at least as long). A majority of votes makes a leader, and any higher term seen in a message makes a server step down. The leader appends client writes to its log and sends them in AppendEntries, which also carry the index and term of the preceding entry; a follower rejects a mismatch, and the leader backs up until the logs agree, then the follower's log is overwritten to match. An entry from the leader's current term stored on a majority is committed, and everything before it with it; committed entries are applied to the state machine in order on every server. Because any two majorities overlap and the vote rule refuses out-of-date candidates, every future leader already has every committed entry. With a majority down, nothing can be elected or committed: Raft stays unavailable rather than letting servers diverge.
```

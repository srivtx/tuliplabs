## Where did 90% of the photo go?

A 12-megapixel photo has 36 million colour numbers, which is 36 MB. Your phone stores it in about 3 MB, and you can't see the difference. Over 90% of the numbers have gone. How can you throw away nine-tenths of something and lose nothing you care about?

The lossless tricks from chapter 17 can't do that. They rely on repeats, and a photo has almost none, because no two pixels of sky are quite the same. JPEG, published in 1992, takes a different path. It throws things away on purpose, and picks what to throw using a model of the human eye. That makes it a piece of biology, written in arithmetic.

It starts with an idea you've already met. On the synthesizer, one wiggly line turned out to be a stack of sine waves. A block of pixels is the same thing in two dimensions.

```viz
name: bx-dct
title: One block, 64 waves
goal: Slide down to the **fewest waves** that keep a 97% match on the smooth sky, then switch to **Keep pixels** at that same count.
height: 340
The middle grid shows the 64 fixed patterns. A lit tile is one that's being used.
```

That transform is the **discrete cosine transform**, published by Nasir Ahmed, T. Natarajan and K. R. Rao in 1974. It's why almost every image and video you've seen on the internet was possible to send.

The transform alone saves nothing: 64 numbers go in and 64 come out, and you can get the block back exactly. What it does is **concentrate** the picture. Raw pixels share the load evenly. After the transform, a smooth block keeps nearly everything in a few numbers, and the rest are close to zero.

```exercise
title: dct
kind: write
---prompt
Write `dct(row)`, the one-dimensional version. For a list `x` of length `n`, output `X[u]` for `u` from 0 to `n - 1`: the sum over every sample `i` of `x[i] × cos((2i + 1) × u × π / (2n))`, multiplied by `sqrt(1 / n)` when `u` is 0, and `sqrt(2 / n)` otherwise.
---starter
def dct(row):
    return list(row)
---solution
from math import cos, pi, sqrt

def dct(row):
    n = len(row)
    out = []
    for u in range(n):
        s = sum(x * cos((2 * i + 1) * u * pi / (2 * n)) for i, x in enumerate(row))
        out.append(s * sqrt((1 if u == 0 else 2) / n))
    return out
---tests
from math import sqrt
flat = dct([5, 5, 5, 5])
assert abs(flat[0] - 10) < 1e-9, "the first number holds the average, scaled by sqrt(n)"
assert all(abs(v) < 1e-9 for v in flat[1:]), "a flat row needs no waves at all"
ramp = dct([1, 2, 3, 4, 5, 6, 7, 8])
assert abs(ramp[2]) < 1e-9 and abs(ramp[1]) > abs(ramp[3]) > abs(ramp[5]), "a smooth ramp lives in the slow waves"
x = [3, 1, 4, 1, 5, 9, 2, 6]
assert abs(sum(v * v for v in x) - sum(v * v for v in dct(x))) < 1e-6, "no energy is created or lost"
---hint
The formula has one `cos` per sample. Add them up for each `u`, then scale.
```

The last test says something worth noticing: total energy doesn't change. The transform only moves it around. A 2D block is the same thing run across the rows and then down the columns, which is the same two-pass trick as the blur in chapter 47.

## What your eye doesn't care about

Now the biology. You need to throw numbers away, so which ones? Ask the eye.

```viz
name: bx-jpeg
title: A real JPEG, running live
goal: Try **both blurs**, then choose **Shrink the colour** and get the file to **8% or less**, with the error at 14 or lower.
height: 400
Everything on the picture is worked out live: the waves, the rounding, and the size of the coded symbols.
```

The two blurs were the same operation, and the results were nothing alike. Your eye reads shape from brightness and has much less resolution for colour.

Did you catch the error numbers? The brightness blur scored **better**, even though it looks far worse. Plain error treats every number the same, but your eye doesn't. That gap is why engineers test image quality on real people, and why they've built measures that try to behave more like vision.

So step one is to stop storing red, green and blue, and to store brightness and two colour-difference channels instead. Colour television worked this way in the 1950s, because it needed a colour signal that could fit into a narrow channel alongside the black-and-white picture.

```exercise

---prompt

---starter
def to_ycbcr(r, g, b):

---solution
def to_ycbcr(r, g, b):
    y = 0.299 * r + 0.587 * g + 0.114 * b
    cb = 128 + 0.564 * (b - y)
    cr = 128 + 0.713 * (r - y)
    return round(y), round(cb), round(cr)
---tests

assert to_ycbcr(255, 255, 255) == (255, 128, 128), "white has no colour"
assert to_ycbcr(100, 100, 100) == (100, 128, 128), "any grey has no colour"

```

Look at the numbers in that brightness formula. Green counts for nearly 60%, and blue only for about 11%. They come from measurements of human vision, so this line of code has your retina in it.

Step two stores each colour channel at a quarter of the pixels, by averaging each 2×2 square. Half of all the numbers disappear before any maths happens.

```exercise

---solution
def shrink(plane):
    out = []
    for y in range(0, len(plane), 2):
        row = []
        for x in range(0, len(plane[0]), 2):
            row.append((plane[y][x] + plane[y][x + 1] + plane[y + 1][x] + plane[y + 1][x + 1]) / 4)
        out.append(row)
    return out

assert shrink([[0, 0, 8, 8], [0, 0, 8, 8]]) == [[0, 8]]
big = shrink([[1] * 6 for _ in range(4)])

---hint

```

## Rounding is the only lie

Here's the single step where information is really lost. Each wave's strength is divided by a number from a table, and rounded to a whole number. Slow waves get small divisors, so they stay accurate. Fast waves get big divisors, so most of them round to **zero**. Your eye is poor at seeing fine ripples, and the table was tuned by testing what people could see.

```exercise
title: quantize
kind: write
---prompt
Write `quantize(block, table)`. Both are lists of equal length. Return `round(block[i] / table[i])` for each item. Then write `restore(q, table)`, which multiplies them back.
---starter
def quantize(block, table):
    return list(block)

def restore(q, table):
    return list(q)
---solution
def quantize(block, table):
    return [round(b / t) for b, t in zip(block, table)]

def restore(q, table):
    return [v * t for v, t in zip(q, table)]
---tests
assert quantize([100, 7, -3], [10, 20, 40]) == [10, 0, 0], "small fast waves round to nothing"
assert quantize([-96, 33], [16, 11]) == [-6, 3]
assert restore([10, 0, 0], [10, 20, 40]) == [100, 0, 0]
assert restore(quantize([103], [10]), [10]) == [100], "close, but the 3 is gone for good"
---hint
`zip` the two lists together. Each function is one line.
```

That last test is the whole of lossy compression: `103` went in, and `100` came out, for ever.

Now the block is mostly zeros, in the bottom right where the fast waves live. Reading it row by row would scatter those zeros, so JPEG reads along diagonals in a zigzag, from slow waves to fast ones, which pushes all the zeros to the end.

```exercise
title: zigzag
kind: write
---prompt
Write `zigzag(n)`, which returns the `(row, col)` positions of an `n × n` block in zigzag order. Go through the diagonals `s = row + col` from 0 up. Within a diagonal, go with `row` increasing when `s` is odd, and with `row` decreasing when `s` is even. The order starts `(0, 0), (0, 1), (1, 0), (2, 0), (1, 1), (0, 2)`.
---starter
def zigzag(n):
    return [(r, c) for r in range(n) for c in range(n)]
---solution
def zigzag(n):
    out = []
    for s in range(2 * n - 1):
        cells = [(r, s - r) for r in range(n) if 0 <= s - r < n]
        if s % 2 == 0:
            cells.reverse()
        out += cells
    return out
---tests
assert zigzag(3)[:6] == [(0, 0), (0, 1), (1, 0), (2, 0), (1, 1), (0, 2)]
assert zigzag(2) == [(0, 0), (0, 1), (1, 0), (1, 1)]
z = zigzag(8)
assert len(set(z)) == 64 and z[-1] == (7, 7), "visits every cell once"
assert z[:3] == [(0, 0), (0, 1), (1, 0)]
---hint
For each diagonal, collect the cells with `r` going up, and reverse the list when `s` is even.
```

```exercise
title: runs
kind: write
---prompt
Write `runs(values)`. Turn a list into `(zeros_before, value)` pairs, one for each non-zero value, where `zeros_before` is how many zeros came just before it. If the list ends in zeros, finish with the single item `"end"`, whatever their number.
---starter
def runs(values):
    return list(values)
---solution
def runs(values):
    out = []
    zeros = 0
    for v in values:
        if v == 0:
            zeros += 1
        else:
            out.append((zeros, v))
            zeros = 0
    if zeros:
        out.append("end")
    return out
---tests
assert runs([5, 0, 0, 3, 0, 0, 0, 0]) == [(0, 5), (2, 3), "end"]
assert runs([1, 2]) == [(0, 1), (0, 2)], "no trailing zeros, no end"
assert runs([0, 0, 0]) == ["end"]
assert runs([0, 7]) == [(1, 7)]
---hint
Keep a count of zeros, and reset it each time you hit a value.
```

Fifty-odd zeros become the single word `end`. Then Huffman coding from chapter 17 packs these pairs into bits. That's the entire format.

Go back to the JPEG, set the quality to 5, and look at the zoom. You can see the machinery: each 8×8 block has fallen back on a few waves, and the seams between them show. Around the letters you can see ripples, the same overshoot as the corners of the square wave.

## Your brain does this too

MP3 works the same way: a loud sound hides quieter sounds near it in pitch, so those can be thrown out. Video adds another trick by only storing what changed since the last frame. Every one of these is a list of things humans don't notice.

The same is true of your own head. Each eye has a blind spot where the optic nerve leaves, and you've never seen the hole, because your brain fills it in. You only see sharp detail in a spot about the width of your thumb held at arm's length, and the rest is filled in from a few quick glances. What you experience as a crisp, complete world is a heavily compressed reconstruction.

## Why you can't shrink everything

There's a limit to all of this, and it's simple counting.

```predict
n = 10
files = 2 ** n
shorter = sum(2 ** k for k in range(n))
print(files, shorter)
```

There are 1,024 possible 10-bit files, and only 1,023 strings shorter than that. Each compressed file has to turn back into exactly one original, so at least one file can't shrink. **No compressor can make every file smaller.** It can only make some smaller, by making others larger.

So compression is a bet about which files are likely. Claude Shannon worked out the exact limit in 1948: it's the **entropy** of the source, the average surprise in each symbol.

```exercise
title: entropy
kind: write
---prompt
Write `entropy(symbols)`. For each distinct symbol with share `p` of the list, add `-p × log2(p)`. Return the total, in bits per symbol, rounded to 3 decimal places.
---starter
def entropy(symbols):
    return float(len(set(symbols)))
---solution
from math import log2
from collections import Counter

def entropy(symbols):
    n = len(symbols)
    total = 0
    for c in Counter(symbols).values():
        p = c / n
        total -= p * log2(p)
    return round(total, 3)
---tests
assert entropy("aaaa") == 0, "no surprise at all"
assert entropy("abab") == 1, "a coin flip is one bit"
assert entropy("abcd") == 2
assert entropy("aaab") == 0.811, "lopsided means less surprise"
---hint
`collections.Counter` counts each symbol. Add up `-p * log2(p)`.
```

Noise has the highest entropy, which is why it wouldn't shrink on the block viewer. A pattern is just something predictable, and only what's predictable can be left out. So a better compressor **has** to be a better predictor. If you could perfectly predict the next pixel, you wouldn't need to store it at all.

That idea now runs far beyond images. A language model predicting the next word is a compressor of human writing, and it can be used as one directly. Understanding something and compressing it may be the same activity: a scientific law is a very short file that replaces a huge table of measurements.

```exercise
title: pick_quality
kind: write
---prompt
Write `pick_quality(score, target)`. `score(q)` gives the measured quality for a setting `q` from 1 to 100, and it never falls as `q` rises. Return the **lowest** `q` where `score(q) >= target`, or `None` if even 100 falls short. Use binary search, so that you don't call `score` 100 times.

def pick_quality(score, target):
    if score(100) < target:
        return None
    lo, hi = 1, 100
    while lo < hi:
        mid = (lo + hi) // 2
        if score(mid) >= target:
            hi = mid
        else:
            lo = mid + 1
    return lo
---tests

assert pick_quality(lambda q: q, 100) == 100
assert pick_quality(lambda q: q, 101) is None
---hint
```

## Rebuild it and explain it

```exercise
title: dct_rebuild
kind: rebuild
---prompt
From memory: `dct(row)`, with the `sqrt(1 / n)` and `sqrt(2 / n)` scaling.
---starter
def dct(row):
    pass
---solution
from math import cos, pi, sqrt

def dct(row):
    n = len(row)
    out = []
    for u in range(n):
        s = sum(x * cos((2 * i + 1) * u * pi / (2 * n)) for i, x in enumerate(row))
        out.append(s * sqrt((1 if u == 0 else 2) / n))
    return out
---tests
d = dct([4, 4, 4, 4])
assert abs(d[0] - 8) < 1e-9 and abs(d[1]) < 1e-9
assert abs(dct([1, -1])[1] - 2 ** 0.5) < 1e-9
---hint
One sum per output, and a different scale for the first one.
```

```recall
Q: Explain how JPEG throws away most of a photo without you noticing, which step really loses information, why no compressor can shrink every file, and what compression has to do with prediction.
A: JPEG splits colour into brightness and two colour channels and stores colour at a quarter of the pixels, because human vision has far less resolution for colour. It cuts the picture into 8 by 8 blocks and applies the discrete cosine transform, which rewrites each block as 64 wave strengths. That loses nothing, but it concentrates a smooth block into a few numbers. Each strength is then divided by a table entry and rounded, with big divisors for fast waves that the eye barely sees. That rounding is where information is really lost, and most fast waves become zero. A zigzag read pushes the zeros to the end, they collapse into run lengths, and Huffman coding packs the rest. No compressor can shrink every file, because there are fewer short strings than long ones and each output has to map back to one input. So compression is a bet on which data is likely, and Shannon's entropy gives the limit. Only what's predictable can be left out, so better compression needs better prediction, which is why noise can't be compressed and why a language model is a kind of compressor.
```

## What a graphics engine does

Every 3D game, CAD program and phone map does the same thing millions of times a second: take **triangles** in 3D, figure out where they land on a flat screen, colour the pixels they cover, and make sure **near things hide far things**. That last part is harder than it sounds.

```quiz
The painter's algorithm sorts triangles from far to near and draws them in that order, like a painter covering the background first. When does it fail?
- When there are more than 100 triangles
- When the light is behind the camera
* When two triangles cross through each other, so neither is entirely in front
- Never; it's what modern GPUs use
> Sorting needs one "depth" per triangle, but two crossing triangles are each in front over part of their area. No order can be right. The z-buffer decides per **pixel** instead, so crossing is no problem.
```

## Vectors: dot and cross

Two operations do almost all the geometry in graphics:

- The **dot product** `a·b = ax·bx + ay·by + az·bz` measures how much two directions agree: positive when they point the same way, zero at right angles, negative when opposite. For unit vectors it's the cosine of the angle between them.
- The **cross product** `a×b` gives a vector **perpendicular** to both. Take two edges of a triangle, cross them, and you get the direction the triangle *faces*: its **normal**.

```predict
a = np.array([1.0, 0.0, 0.0])
b = np.array([0.0, 1.0, 0.0])
print(np.dot(a, b), np.dot(a, a), np.dot(a, -a))
print(np.cross(a, b))
```

## Turning things: rotation matrices

To spin a model, multiply every point by a **rotation matrix**. Turning by angle θ around the vertical (y) axis:

    [ cos θ   0   sin θ ]
    [   0     1     0   ]
    [ -sin θ  0   cos θ ]

Why a matrix and not a formula per point? Because matrices **compose**: "rotate, then tilt, then move" becomes one matrix you multiply every vertex by, and that's exactly what a GPU is built to do fast. With numpy, `points @ R.T` rotates thousands of points in one line.

```exercise
title: rotate_y
kind: fill
---prompt
Fill in the rotation matrix around the y axis, then apply it to an `(n, 3)` array of points.
---starter
def rotate_y(points, theta):
    c, s = np.cos(theta), np.sin(theta)
    R = np.array(____)

---solution
def rotate_y(points, theta):
    c, s = np.cos(theta), np.sin(theta)
    R = np.array([[c, 0, s], [0, 1, 0], [-s, 0, c]])
    return points @ R.T
---tests
p = np.array([[1.0, 2.0, 0.0]])

assert np.allclose(q, [[0, 2, -1]]), f"a quarter turn takes +x to -z and leaves y alone; got {q.round(3)}"
assert np.allclose(rotate_y(p, 2 * np.pi), p), "a full turn changes nothing"
pts = np.random.default_rng(0).normal(size=(50, 3))
assert np.allclose(np.linalg.norm(rotate_y(pts, 0.7), axis=1), np.linalg.norm(pts, axis=1)), "rotation never changes a point's distance from the origin"
---hint
Copy the matrix above row by row: `[[c, 0, s], [0, 1, 0], [-s, 0, c]]`.
```

## Perspective: divide by depth

Why do far things look small? Picture rays from your eye through a window to the world. A point twice as far away needs to be twice as far sideways to hit the same spot on the window. So the screen position is the sideways position **divided by the depth**:

    x_screen = f · x / z,    y_screen = f · y / z

`f` is the focal length (zoom). That one division *is* perspective. Then we map screen coordinates (−1 … 1) to pixel columns and rows; rows count **down** from the top.

```predict
f = 1.0
for z in [2.0, 4.0, 8.0]:
    x, y = 1.0, 1.0
    print(z, f * x / z, f * y / z)
```

```exercise
title: project
kind: write
---prompt
Write `project(p, f, w, h)`: the camera sits at the origin looking down **+z**. Return the pixel coordinates `(px, py)` of 3D point `p` as floats: first `sx = f*x/z`, `sy = f*y/z`, then `px = (sx + 1) * w / 2` and `py = (1 - sy) * h / 2` (so +y is up on screen).
---starter

---solution

    x, y, z = p
    sx, sy = f * x / z, f * y / z

---tests

a, b = project((1, 0, 2), 1, 100, 100), project((1, 0, 4), 1, 100, 100)
assert a[0] > b[0] > 50, "the same sideways offset looks smaller when it's further away"
---hint
Divide by `z` first; then map −1…1 onto 0…w for columns and flip the rows with `1 - sy`.
```

## Filling a triangle: edge functions

Given a triangle's three corners in pixels, which pixels does it cover? For each edge `a → b`, the **edge function**

    E(a, b, p) = (b.x − a.x)(p.y − a.y) − (b.y − a.y)(p.x − a.x)

is positive on one side of the line and negative on the other. A pixel is **inside** when all three edges give the same sign. GPUs do this test for millions of pixels in parallel, because each pixel's test is independent.

```parsons
title: Inside or outside?
---lines
def inside(a, b, c, p):
    e0 = edge(a, b, p)
    e1 = edge(b, c, p)
    e2 = edge(c, a, p)
    return (e0 >= 0 and e1 >= 0 and e2 >= 0) or (e0 <= 0 and e1 <= 0 and e2 <= 0)
?? e2 = edge(a, c, p)
---setup
def edge(a, b, p):
    return (b[0] - a[0]) * (p[1] - a[1]) - (b[1] - a[1]) * (p[0] - a[0])
---tests
assert inside((0, 0), (10, 0), (0, 10), (2, 2)), "(2,2) is inside"
assert not inside((0, 0), (10, 0), (0, 10), (8, 8)), "(8,8) is beyond the long edge"
assert inside((0, 0), (0, 10), (10, 0), (2, 2)), "works for either winding"
```

```exercise
title: rasterize
kind: write
---prompt
Write `rasterize(a, b, c, w, h)`: return a `(h, w)` boolean numpy array that is True for every pixel whose **centre** `(col + 0.5, row + 0.5)` is inside the triangle (either winding). `edge` is defined. Use numpy so it's fast: build arrays of all pixel centres with `np.meshgrid`.
---setup
def edge(a, b, p):
    return (b[0] - a[0]) * (p[1] - a[1]) - (b[1] - a[1]) * (p[0] - a[0])
---starter
def rasterize(a, b, c, w, h):
    return np.zeros((h, w), dtype=bool)
---solution
def rasterize(a, b, c, w, h):
    xs, ys = np.meshgrid(np.arange(w) + 0.5, np.arange(h) + 0.5)
    p = (xs, ys)
    e0, e1, e2 = edge(a, b, p), edge(b, c, p), edge(c, a, p)
    return ((e0 >= 0) & (e1 >= 0) & (e2 >= 0)) | ((e0 <= 0) & (e1 <= 0) & (e2 <= 0))
---tests
m = rasterize((0, 0), (20, 0), (0, 20), 20, 20)

assert 190 <= m.sum() <= 210, f"half of a 20x20 square is about 200 pixels; got {m.sum()}"
assert m[1, 1] and not m[18, 18], "the corner near (0,0) is in, the far corner is out"
assert rasterize((0, 0), (0, 20), (20, 0), 20, 20).sum() == m.sum(), "winding doesn't matter"
---hint
`edge` works on arrays too: pass `p = (xs, ys)` where `xs, ys = np.meshgrid(np.arange(w) + 0.5, np.arange(h) + 0.5)`.
```

## The z-buffer

Keep a second image the same size as the screen, the **depth buffer**, filled with infinity. When a triangle wants to colour a pixel, compare its depth there with what's stored. **Nearer wins**: write the colour *and* the new depth. Otherwise, skip it. Triangles can now be drawn in any order and crossing surfaces come out right, at the cost of one number per pixel.

```exercise
title: zbuffer_bug
kind: bug
---prompt
This `plot(img, zbuf, row, col, z, color)` should draw a pixel only if it's **nearer** than what's there. But far triangles keep painting over near ones. Fix it.
---starter
def plot(img, zbuf, row, col, z, color):
    if z > zbuf[row, col]:
        zbuf[row, col] = z
        img[row, col] = color
---solution
def plot(img, zbuf, row, col, z, color):
    if z < zbuf[row, col]:
        zbuf[row, col] = z
        img[row, col] = color
---tests
img, zb = np.zeros((1, 1)), np.full((1, 1), np.inf)
plot(img, zb, 0, 0, 5.0, 1)
plot(img, zb, 0, 0, 9.0, 2)
assert img[0, 0] == 1, "a far pixel (z=9) must not cover a near one (z=5)"
plot(img, zb, 0, 0, 2.0, 3)
assert img[0, 0] == 3 and zb[0, 0] == 2.0, "a nearer pixel (z=2) wins and updates the depth"
---hint
The camera looks down +z, so a **smaller** z is closer to the eye. And the buffer starts at infinity: with `>`, nothing would ever be drawn.
```

## Light: Lambert's cosine law

A surface facing the light head-on is bright; tilted away, the same light spreads over more area, so it's dimmer; facing away, it's dark. The brightness is the **dot product** of the unit normal and the unit direction toward the light, clipped at zero:

    brightness = max(0, n · l)

```predict
l = np.array([0.0, 0.0, 1.0])
for n in [np.array([0.0, 0.0, 1.0]), np.array([0.0, 0.6, 0.8]), np.array([0.0, 0.0, -1.0])]:
    print(round(max(0.0, float(np.dot(n, l))), 2))
```

## Real-world project: a 3D product viewer

```project

client: A furniture start-up that wants customers to spin a table before they buy it

---why
```

```exercise
title: render
kind: write
---prompt
Write `render(tris, w, h)`. Each item in `tris` is `(pts, value)`: `pts` is three `(x, y, z)` tuples **already in pixel coordinates** (x = column, y = row, z = depth), and `value` is the colour number to paint. Return an `(h, w)` float image (background 0) with a z-buffer so the **nearest** triangle wins at every pixel. Interpolate z inside a triangle with barycentric weights: `wa = edge(b, c, p) / area` etc., where `area = edge(a, b, c)`. `edge` is defined and works on arrays.
---setup
def edge(a, b, p):
    return (b[0] - a[0]) * (p[1] - a[1]) - (b[1] - a[1]) * (p[0] - a[0])
---starter
def render(tris, w, h):
    img = np.zeros((h, w))
    return img
---solution
def render(tris, w, h):
    img = np.zeros((h, w))
    zbuf = np.full((h, w), np.inf)
    xs, ys = np.meshgrid(np.arange(w) + 0.5, np.arange(h) + 0.5)
    p = (xs, ys)
    for (a, b, c), value in tris:
        area = edge(a, b, c)
        if area == 0:
            continue
        wa, wb, wc = edge(b, c, p) / area, edge(c, a, p) / area, edge(a, b, p) / area
        inside = (wa >= 0) & (wb >= 0) & (wc >= 0)
        z = wa * a[2] + wb * b[2] + wc * c[2]
        win = inside & (z < zbuf)
        zbuf[win] = z[win]
        img[win] = value
    return img
---tests
near = ((0, 0, 1.0), (30, 0, 1.0), (0, 30, 1.0)), 1.0
far = ((0, 0, 5.0), (30, 0, 5.0), (0, 30, 5.0)), 2.0
assert render([far, near], 30, 30)[5, 5] == 1.0, "the near triangle wins even when it's drawn second"
assert render([near, far], 30, 30)[5, 5] == 1.0, "...and when it's drawn first: order doesn't matter any more"
tilted = ((0, 0, 0.0), (30, 0, 10.0), (0, 30, 0.0)), 3.0
flat = ((0, 0, 5.0), (30, 0, 5.0), (0, 30, 5.0)), 4.0
img = render([tilted, flat], 30, 30)
assert img[5, 2] == 3.0 and img[2, 26] == 4.0, "crossing triangles: each wins on its own side of the crossing line, per pixel"
assert render([], 10, 10).sum() == 0, "no triangles, empty picture"
---hint
Barycentric weights `wa, wb, wc` are all ≥ 0 exactly inside the triangle (for either winding, once you divide by the signed area), and they blend the three corner depths.
---show
cube_v = np.array([[x, y, z] for x in (-1, 1) for y in (-1, 1) for z in (-1, 1)], dtype=float)
faces = [(0, 1, 3, 2), (4, 6, 7, 5), (0, 4, 5, 1), (2, 3, 7, 6), (0, 2, 6, 4), (1, 5, 7, 3)]
light = np.array([0.4, 0.6, -0.7]); light /= np.linalg.norm(light)
frames = []
for k in range(36):
    t = k * np.pi / 18
    c, s = np.cos(t), np.sin(t)
    R = np.array([[c, 0, s], [0, 1, 0], [-s, 0, c]]) @ np.array([[1, 0, 0], [0, np.cos(0.5), -np.sin(0.5)], [0, np.sin(0.5), np.cos(0.5)]])
    v = cube_v @ R.T + [0, 0, 5]
    tris = []
    for f in faces:
        q = v[list(f)]
        n = np.cross(q[1] - q[0], q[2] - q[0]); n /= np.linalg.norm(n)
        shade = 0.15 + 0.85 * max(0.0, float(-np.dot(n, light)))
        pix = [((x / z + 1) * 40, (1 - y / z) * 40, z) for x, y, z in q]
        tris += [((pix[0], pix[1], pix[2]), shade), ((pix[0], pix[2], pix[3]), shade)]
    frames.append(render(tris, 80, 80))
print("A shaded cube, rendered by YOUR z-buffer:")
flipbook(frames, cmap="gray", vmin=0, vmax=1, fps=12)
```

## Rebuild it and explain it

```exercise
title: draw_triangle
kind: rebuild
---prompt
From memory: write `draw_triangle(img, zbuf, a, b, c, value)` that paints one triangle (corners in pixel coordinates with depth, either winding) into `img` with z-buffering, interpolating depth with barycentric weights. Modify `img` and `zbuf` in place.
---starter
def draw_triangle(img, zbuf, a, b, c, value):
    pass
---solution
def draw_triangle(img, zbuf, a, b, c, value):
    def edge(a, b, p):
        return (b[0] - a[0]) * (p[1] - a[1]) - (b[1] - a[1]) * (p[0] - a[0])
    h, w = img.shape
    xs, ys = np.meshgrid(np.arange(w) + 0.5, np.arange(h) + 0.5)
    area = edge(a, b, c)
    if area == 0:
        return
    wa, wb, wc = edge(b, c, (xs, ys)) / area, edge(c, a, (xs, ys)) / area, edge(a, b, (xs, ys)) / area
    z = wa * a[2] + wb * b[2] + wc * c[2]
    win = (wa >= 0) & (wb >= 0) & (wc >= 0) & (z < zbuf)
    img[win] = value
    zbuf[win] = z[win]
---tests
img, zb = np.zeros((20, 20)), np.full((20, 20), np.inf)
draw_triangle(img, zb, (0, 0, 3.0), (20, 0, 3.0), (0, 20, 3.0), 1.0)
draw_triangle(img, zb, (0, 0, 9.0), (0, 20, 9.0), (20, 0, 9.0), 2.0)
assert img[3, 3] == 1.0, "the farther triangle (z=9) doesn't cover the nearer one"
assert 150 < (img == 1).sum() < 250, "about half the square is painted"
assert zb[3, 3] == 3.0, "the depth buffer remembers the nearest depth"
---hint
Edge functions → barycentric weights → interpolated z → one boolean mask `inside & nearer`.
```

```recall
Q: Walk through how a 3D triangle becomes coloured pixels, and say why the z-buffer beats sorting triangles.
A: Rotate and move the triangle's corners with matrices, then divide x and y by depth to project them onto the screen (perspective). For every pixel, edge functions say whether its centre is inside; barycentric weights interpolate the depth there. A z-buffer stores the nearest depth seen so far at each pixel, and a triangle only paints a pixel when it's nearer. Sorting whole triangles needs one depth per triangle, which is impossible when triangles cross or overlap cyclically; the z-buffer decides each pixel separately, so order never matters.
```

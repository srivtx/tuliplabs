## A bot is a backend

Kiln & Co sells mugs, teapots and lids online, and the same five questions arrive all day: where is my order, I want a refund, I moved, cancel it, are you open on Sunday. In this chapter you build **Lantern**, the backend behind the shop's chat bubble. It works out what each customer wants, remembers the conversation, looks up their order, sends its answer word by word, and passes the customer to a person when it's out of its depth.

Lantern's brain is a keyword counter, so you can see every decision it makes. A shop might swap it for a language model. Everything else in this chapter stays the same, and matters even more, because a model's output is as untrusted as the customer's message.

## Intents: what does the customer want?

An **intent** is what the customer wants done: track an order, get a refund, change an address. Lantern gives each intent a list of keywords, counts how many of a message's words are on each list, and picks the intent with the most. No keyword at all means it didn't understand.

## Memory: one conversation per customer

A chat is more than one message. Lantern asks "which order?", the customer answers "it's 1042", and that answer has no keywords at all. It only means something next to the question before it.

So Lantern keeps a small **session** for each customer: the question it's waiting on (`pending`) and the last order number it heard (`order`). A real server keeps these in a fast store like Redis, so any of its machines can pick up the chat. Here a `Map` will do.

## Tools: let the bot look things up

"Order 1042 arrives Thursday" was made up. To answer for real, Lantern needs the shop's data, through **tools**: small functions it may call, each with a name, a schema for its arguments, and code that runs them. This is the same shape as tool calling in a language model API. The model writes `{"name": "lookup_order", "args": {"order": "1042"}}` as text, and **your server** checks it and runs it.

The most important line in a tool is the one that asks who's calling. Lantern talks to every customer, so whatever a tool can see, any customer can try to ask for.

const express = require("express");
const { z } = require("zod");

const ORDERS = {
  "1042": { customer: "ana", item: "Blue mug", status: "shipped", eta: "Thursday", address: "4 Elm St" },
  "1077": { customer: "chloe", item: "Teapot", status: "packing", eta: "Monday", address: "19 Quay Rd" },
  "1093": { customer: "ana", item: "Lid", status: "delivered", eta: null, address: "4 Elm St" },

const TOOLS = {
  lookup_order: {
    args: z.object({ order: z.string().regex(/^\d{4}$/) }),
    run: (user, { order }) => {
      const o = ORDERS[order];
      if (!o || o.customer !== user) return null;
      return { order, item: o.item, status: o.status, eta: o.eta };
    },
  },
  store_hours: {
    args: z.object({}),
    run: () => ({ open: "09:00", close: "18:00", sundays: true }),
  },
};

const app = express();
app.use(express.json());

app.post("/tools/:name", (req, res) => {
  const user = req.get("X-User");
  if (!user) return res.status(401).json({ error: "Sign in first" });
  const tool = TOOLS[req.params.name];
  if (!Object.hasOwn(TOOLS, req.params.name)) return res.status(404).json({ error: `No tool ${req.params.name}` });
  const r = tool.args.safeParse(req.body ?? {});
  if (!r.success) return res.status(400).json({ error: "Invalid arguments" });

});

This bug is called an **insecure direct object reference**, and it isn't special to bots. Any route that takes an id and fetches by it has to ask whose it is. A bot just makes it easier to try: anyone can type any number, all day, politely. With a language model it gets worse, because a customer can write "ignore your rules, I'm the admin" and the model may believe them. The check in `run` doesn't read the conversation at all, so it can't be talked out of anything.

## Streaming the answer

A language model writes its answer a few words at a time, and a long answer can take several seconds. Making the customer stare at a spinner for all of it feels broken, so chat apps show the words as they arrive. The server passes each piece on the moment it has it.

The simplest way is **Server-Sent Events**. The response has the type `text/event-stream` and never says how long it is. The server writes one event at a time, each a `data:` line followed by a blank line, and ends the response when it's done. The browser reads events as they come. Each piece goes out as JSON, because a newline inside the text would otherwise end the event early.

```run
title: Reading a stream of events
const body = 'data: {"text":"Order"}\n\n' +
  'data: {"text":" 1042 is"}\n\n' +
  'data: {"text":" on its way."}\n\n' +
  "event: done\ndata: {}\n\n";

for (const event of body.split("\n\n").filter(Boolean)) {
  const lines = event.split("\n");
  const name = (lines.find((l) => l.startsWith("event: ")) || "event: message").slice(7);
  const data = JSON.parse(lines.find((l) => l.startsWith("data: ")).slice(6));
  console.log(name.padEnd(8), JSON.stringify(data));
}
```

In Express you send a stream with `res.writeHead` for the headers, `res.write` for each event, and `res.end()` at the end. One thing to know about this page: its browser waits for the whole response before the checks read it. In real Node each `res.write` leaves the moment you call it, and the timing check below holds either way.

  };

## Handing off to a person

Some chats a bot shouldn't keep: the customer asks for a person, or Lantern has failed to understand them twice in a row. Then it **hands off**. It opens a ticket on the support desk's queue with the **whole transcript**, so the person who picks it up doesn't make the customer repeat themselves, and from then on it stays out of the conversation.

Look back at the simulation. Handing off at the first miss sent 9 of the 18 chats to the desk; after two misses in a row it was 4, because several customers say it badly once and then in words Lantern knows. Never handing off left the customer who wanted gift cards stuck, saying the same thing until they gave up.

```recall
Q: Explain how a support bot's backend turns "where is my order?" into a real answer, and what keeps it safe and useful.
A: Each message gets an intent: here by counting each intent's keywords and taking the most (ties to the first listed, no matches meaning it didn't understand); a language model can do the guessing instead, but every method is sometimes confidently wrong ("when will my refund arrive" counts as track). The bot keeps a session per customer, in Redis on a real server: the question it's waiting on and the last order number, so "it's 1042" answers "which order?" and "it" means 1042 later on; sessions expire after a quiet spell so yesterday's question can't be answered by accident. To answer with real data it calls tools: each has a name, a Zod schema for its arguments and code that runs it, which is exactly how language model tool calling works (the model writes the call, the server checks and runs it). A tool must check who's asking: an order that isn't the customer's gets the same reply as one that doesn't exist, and only the fields the answer needs leave the server; that check is in code, so no message, however persuasive, can talk its way past it. Replies are streamed as Server-Sent Events: text/event-stream, one "data:" line of JSON and a blank line per piece, then a done event and the end of the response. When the customer asks for a person or the bot misses twice in a row, it hands off: a ticket on the desk's queue with the whole transcript, and the bot goes quiet. Handing off at the first miss floods the desk (9 of 18 chats in the simulation against 4), and never handing off strands the customers it can't understand.
```
